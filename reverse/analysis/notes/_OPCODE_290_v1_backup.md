# OPCODE 290『ピクチャエフェクト』语义规格 + 「每图片色调」来源确认

> **本文要回答两个问题**：(1) 本作 640 条 290 指令各自是什么语义；(2) 零售标题画面 picture 12001 的 RGB 为什么被恰好乘以 222/255 —— 引擎把每图片色调存在哪。
>
> **证据档位**（全文逐条标注）：
> - **已验证**：有像素级或字节级实测支撑（脚本可重跑）。
> - **高置信推断**：有结构性证据（数值形态、官方文档片段、用法相关性），但没有官方字段表直证。
> - **未确认**：只有观察，没有判定依据。
>
> **原始数据**：`work/_ce_full.json`（550 个公共事件 / 163,828 条指令，含 indent 块结构）、`work/_v2_titlemap_ev2.txt`（TitleMap.mps event2 全 133 条）、零售截图 `work/out/full_21_21_35.png` 与 `work/out/full_21_22_48.png`。
> 官方文档只能拿到搜索引擎 snippet（本机 `web_fetch` 对任何主机都失败：`resolves to a non-public IP address`），出处标在引用处。

## 0. 结论速览

1. **290 的参数个数恒为 7**：`[head, duration, picA, picB, v1, v2, v3]`。`head >> 4` = 效果类型，本作出现 **10 种**（0,1,2,3,4,5,7,8,9,10，缺 type 6）；`head & 0xF` 在 **640/640** 条里恒为 0，即低 4 位本作从不使用。
2. **色调不在 150 里**：150（ピクチャ）确实有カラー三槽，但它在**长格式**的尾部 `args[15..17]`（`argc >= 18` 才会出现）；标题横幅那条 150 是 `argc = 11`（`[4096, 12001, 0, 1, 1, 1, 255, 512, 520, 100, 0]`），**根本不含颜色槽** ⇒ 取默认 100（无变化）。
3. **色调来自同一事件 pc91 的 `290 [80, 30, 12001, 12001, -50, -50, -50]`**：type = 5，RGB 三通道差分 −50，帧数 30。
4. type 5 属 **RGB 族效果**：它是本作**仅有的三个「三参数恒落在 [−100, 100]、且从不引用变量」的类型之一**（另两个是 type 0 / type 1），这与官方文档「点滅A/B 的 RGB 最大 ±200」「RGB 全 0 或 帧数 0 ⇒ 点滅停止」严格吻合。而实测到的两帧是**连续中间值**（不是端点）⇒ 必须是**周期性渐变**，不是一次性 fade ⇒ **点滅B[自動フラッシュ]**（**高置信推断**）。
5. **数值链闭合**：カラー百分率 p（100 = 不变）→ `byte = clamp(round(p * 255 / 100), 0, 255)` → `dst = round(src * byte / 255)`（**alpha 不变**，已验证）。k=222 ⇒ p = 87.06；k=188 ⇒ p = 73.73，二者都落在 [50, 100] 区间内 ✓。

## 1. 参数布局与全量统计

### 1.1 布局（已验证）

    args[0]  head      高位 head>>4 = 效果类型；低 4 位 head&0xF 本作恒 0
    args[1]  duration  帧数（部分类型恒 0 = 立即取最终值 / 停止）
    args[2]  picA      图片番号（可以是 magic number：1600021 = 自身変数#21 的值）
    args[3]  picB      同 picA；当 picA == picB 时就是同一张图
    args[4]  v1
    args[5]  v2
    args[6]  v3        三个含义随类型变化；本作 v3 常作「帧数/持续值」的补充位

    stringArgs 恒为空（640/640 条 s = []）

**magic number 求值**（与 121/122/124 同一套寻址）：`0..999999` 字面量；`1600000+n` = **自身変数 #n**；`2000000+n` = 通常変数；`9000000+n` = システム変数。实测 picA/picB 里出现 `1600021`、`1600026`、`1600040` 等（= self21 / self26 / self40，即「当前窗口/立绘/文字用哪张图」），也出现纯字面量 `10003`、`1202`、`5000`、`50001`。

> 与 `docs/OPCODE_124.md` 的 124（取图片属性）互补：290 是**写**，124 是**读**。

### 1.2 640 条的类型直方图（已验证）

| type (`head>>4`) | 条数 | head 原值 | duration 分布 | picA==picB | 三参数值域 |
|---|---|---|---|---|---|
| 0 | 9 | 0 | 25 × 9 | 9 / 9 | 全部 ∈ [−100, 200]，**无 magic** |
| 1 | 13 | 16 | **0 × 13** | 12 / 13 | 全部 ∈ [−100, 200]，**无 magic** |
| 2 | 126 | 32 | 0 × 124, 3000 × 2 | 124 / 126 | v1/v2 多为 **magic（X/Y 位移）**，v3 恒 0 |

> **结构性关键点（已验证）**：类型 0 / 1 / 5 是**仅有的三个「三参数全部落在 [−200, 200] 区间、且没有一条引用变量」**的类型。
> - type 0：9/9 条 ∈ [−100, 200]
> - type 1：13/13 条 ∈ [−100, 200]
> - type 5：65/65 条 ∈ [−100, 100]
>
> 其余类型的三参数要么大量是 magic number（type 2：123/126 条 v1 是 magic），要么远超颜色值域（type 3 的 999999、type 4 的 512/450）。官方文档对**颜色类效果**的取值规定是「RGB 0～200，全部 100 时无变化」「点滅的 RGB 最大 ±200」—— 与 0/1/5 的值域完全对得上。
> ⇒ **{type 0, type 1, type 5} = RGB 族效果（フラッシュ / 点滅A / 点滅B 的某种排列）**（高置信推断）。

## 2. 逐类型语义

### 2.1 type 0 —— 单次闪光（推断 = フラッシュ）

- 9 条，`duration` **恒 25 帧**，picA == picB 9/9，三参数无 magic。
- 实测只出现四种三元组：`(200,-100,-100)`、`(-100,200,-100)`、`(-100,-100,200)`、`(80,80,80)`，即**「只抬一个通道」或「三通道一起抬」**。
- 用法：战斗/UI 绘制事件里画完角色图后立刻打一发（ev90「X[移]キャラクター欄描画」pc508/523/538、ev178「X[戦]味方欄_単体描画」pc514/564/579、ev179）。
- **语义**：一次性把该图片的カラー推到指定值再回落到 100（官方：「フラッシュ … 指定した赤・緑・青の値」；yado：「ピクチャを１回だけフラッシュさせます」）。**置信度：高**（一次 + 固定 25 帧 + 单通道同时抬升）。
- **未确认**：`-100` 是「不抬这个通道」的哨兵还是「压暗 100」，无法从静态数据判定。

### 2.2 type 1 —— 点滅类复位/停止

- 13 条，`duration` **恒为 0**；只出现在绘制流程的「收尾」位置（ev85「X[移]┣ お店　描画」pc510/517、ev90 pc179、ev95 pc682）。
- 三元组 8 种：`(0,0,0)` ×4、`(-100,-100,-100)` ×3、`(100,100,100)`、(80,-30,-30)、( -30,80,-30)、(-30,-30,80)、(40,40,-30)、(200,-100,-100)。
- 官方对点滅的停止条件原文：「RGB値全てを０に設定する」か、または「フレーム数を０にする」と、点滅は停止します。
- ⇒ **语义**：`duration = 0` 在这条 opcode 里等价于「**停止/复位该图片的カラー效果**」。（高置信推断）
- **未确认**：它到底是「点滅A」还是「点滅B」的通道 —— 本作只用了它的停止语义，无法区分。

### 2.3 type 2 —— 描画座標シフト[最終値]（推断，置信度高）

- 126 条，`duration` 124 条为 **0**（= 立即取最终值），2 条 3000。
- v1/v2 **几乎都是自身変数引用**：`(1600011,1600012,0)` ×15、`(1600070,1600071,0)` ×12、`(1600072,1600073,0)` ×10、`(1600051,1600052,0)` ×9 …（成对的 self 变量 = X / Y），v3 恒 0。
- 典型上下文 ev85 pc230：先 `121 [1600012, 1600089, 2, 12544]` 算出坐标，紧接 `290 [32, 0, 1600021, 1600021, 1600046, 1600012, 0]`，然后 `150` 画。
- 官方手册原例（`work/_yado_0600.txt` 第 710 行附近）：「■ピクチャエフェクト：1 [描画座標ｼﾌﾄ(最终値)] Xｼﾌﾄ 100 / Yｼﾌﾄ 0 **[0]フレーム**」—— **帧数 0** 与这里 124/126 条 dur=0 完全对上；yado.tk 1100_effect：「描画座標シフト[最終値] … 例えば『シフトＸ[100]、シフトＹ[-90]』を実行すると、『処理時間』の時間をかけて、右に『100』、上に『90』移動します」。
- ⇒ **语义**：给该图片叠加一个**绘制坐标偏移**（与原 150 的 X/Y 加算），帧数 0 = 立刻到最终值。与 124 的 `0x4400`（エフェクト補正なし）呼应：带补正读出 X=260、不带补正读出 X=160。
- **未确认**：两条 dur=3000 的样本里 v3 仍是 0，是否还有第四参数未知。

### 2.4 type 3 —— 未确认（形态极集中）

- 211 条，`duration` 以 15 帧最主（127 条）。
- 三元组高度集中：`(0,2,99999)` ×91、`(0,1,999)` ×35、`(6,0,3)` ×14、`(8,0,3)` ×12、`(7,0,3)` ×6、`(0,2,999)` ×5、`(0,0,0)` ×5、`(0,8,8)` ×4 …
- 观察：v1 与 v2 常有一个为 0；v3 常是 **999 / 99999 / 999999**（WOLF 里典型的「无限」写法），只有在 (k,0,3/5/8) 这一族里才是小整数。
- 用法：ev90 pc394（画完文字立绘后）、ev178 pc289、ev234 pc661（ステータス表示）、ev239/ev241（战斗）—— 都在「持续动画」的位置。
- ⇒ **未确认**。只能确定：它作用在单张图上（picA == picB 211/211）、带帧数、且常被设成「无限帧」。**不要凭猜实现**；建议先当空操作（no-op），等有视频或更多证据。

### 2.5 type 4 —— 图片切换 + 位移/缩放 tween（推断）

- 49 条，`duration` **恒 5 帧**，picA ≠ picB **49/49**（本作唯一一个从 A 图迁到 B 图的类型）。
- 三参数：`(512, 200..450, 100/105)` —— 512 = 屏幕宽 1024 的一半（X 居中），第二参是 Y，第三参 100/105 = 缩放百分比。
- 用法：ev245「■夜コマンドメニュー」pc233/234/260/266：`290 [64, 5, 1202, 1203, 512, 300, 100]`、`290 [64, 5, 1200, 1201, 512, 250, 105]`（1200→1201、1202→1203 是菜单按钮的两帧图）。
- ⇒ **语义**：5 帧内把 A 图移动到 `(512, Y)` 并按 `p%` 缩放，然后换成 B 图（或 A/B 交替）。**置信度：中**。

### 2.6 type 5 —— カラー点滅（本文主角）

- 65 条。`duration` 分布：**0 × 36**（= 停止）、15 × 9、25 × 6、50 × 6、30 × 3、20 × 1，另有 4 条为自身変数引用。
- 三参数全部 ∈ [−100, 100]，**无一条引用变量**，三元组几乎总是三通道相等：
  - `(100,100,100)`（回到中性，配 dur > 0）
  - `(0,0,0)`（配 dur = 0，= 官方说的「RGB全部0 ⇒ 停止」）
  - `(-50,-50,-50)`（本文主角，配 dur 30 / 50）
  - 少量 `(20,20,20)`、`(10,10,10)`
- 典型用法（两段一组「先关后开」）：
  - ev64「X[共]万能ウィンドウ描画処理」pc498 `[80, 20, 1600021, 1600021, 100, 100, 100]`
  - ev85「X[移]┣ お店　描画」pc503/511 `[80, 0, 1600021, 1600026, 0, 0, 0]` → pc518 `[80, 15, 1600021, 1600021, 100, 100, 100]`（关掉 → 15 帧淡回中性）
  - ev234「ステータス表示」pc663 `[80, 50, 10002, 10002, -50, -50, -50]`（对 400×90 的黑底面板做 −50 的呼吸/闪烁）
  - **TitleMap.mps event2 pc91 `[80, 30, 12001, 12001, -50, -50, -50]`**（标题横幅）
- ⇒ **语义**：对该图片的カラー做**周期性明滅**，幅度 = (v1, v2, v3)，周期 = duration 帧；`duration <= 0` 或三通道全 0 ⇒ 停止并回到 100。**置信度：高（点滅系）；具体是 点滅A 还是 点滅B：高置信推断为 点滅B[自動フラッシュ]**（§4 给出判定）。

### 2.7 type 7 —— 未确认（像「拡大/回転」类）

- 25 条，duration 10/20/0/15。
- 三元组：`(0,0,0)` ×5、`(8,8,60)` ×3、`(12,12,40)` ×2、`(10,10,40)` ×2、`(6,6,80)` ×2、`(5,5,80)` ×2、`(50,50,0)`、(10,10,10)、(18,18,10)、(16,16,20)、(14,14,30) …
- 特征：**v1 == v2**（25/25），v3 随 v1 增大而减小（8→60、10→40、14→30、18→10），像「振幅 ↔ 速度」的取舍。
- **未确认**。

### 2.8 type 8 / 9 / 10 —— 战斗特效 / カットイン / アイキャッチ（用法明确，字段含义未确认）

- **type 8**（34 条）：恒 `(1, N, 50)` 或 `(1, N, 0)`，全部作用在图片 `5000`；事件 = ev239「■戦闘呼び出し」pc765、ev241「┣ターン開始処理」pc216/334、ev242「┣コマンド処理」pc174。上下文是 `150` 画 `BattleEffect/[Attack]Slash01_panop.png` 后立刻 290。⇒ 战斗特效播放（次数/强度）。

## 3. 150 的カラー槽（「每图片色调」在 150 里的位置）

### 3.1 参数是「按需截断」的可变长表（已验证，16,716 条）

150 的 `intArgs` 长度分布：

| argc | 2 | 3 | 4 | 6 | **11** | 12 | 13 | 14 | 15 | **18** | **19** |
|---|---|---|---|---|---|---|---|---|---|---|---|
| 条数 | 203 | 1839 | 85 | 952 | **11677** | 84 | 55 | 71 | 43 | **434** | **1273** |

- `argc = 11` 是标准形式，一直写到 `args[10]`（BLEND）为止。
- 更长的形式在后面**按固定顺序追加可选槽位**（下表下标是 `intArgs` 的下标；`crates/wolf-game/src/picture.rs` 里讲的是 `args[2..]`，差 2）：

| 6 | **OPACITY（不透明度）** | 255、0、−1000000、188 |
| 7, 8 | **X, Y** | 512、520、0、1600022、1600041、−4 |
| 9 | **SCALE（拡大率 %）** | 100、−1000000 |
| 10 | **BLEND（合成方法）** | 0、−1000000 |
| 11 | EXTRAS（附加整数） | 0、1600005..1600009 |
| **12** | **flags 字** | `0x01000000`（13/14/15 长形式）/ `0x02000000`（18/19 长形式） |

### 3.2 カラー三槽的实测（已验证）

- 出现カラー槽的指令 = `argc >= 18` = **1707 条**（434 + 1273）。
- 三槽共有 **26 种**取值组合，主要几种：

| 三元组 | 条数 |
|---|---|
| (100, 100, 100) | 1377 |
| (0, 0, 0) | 167 |
| (50, 50, 50) | 53 |
| (25, 25, 25) | 28 |
| **(0, 100, 100)** | **18** |
| (1600057, 1600058, 1600059) | 7 |
| (50, 60, 60) | 6 |
| (0, 0, 100) / (0, 100, 0) | 6 / 6 |
| (50, 50, 70) | 5 |
| (1600030, 1600031, 1600032) | 4 |
| (80, 80, 80) | 3 |
| (60, 100, 60) / (100, 60, 60) | 3 / 3 |
| (60, 60, 60) / (150, 150, 150) / (10, 10, 10) | 2 / 2 / 2 |
| (30, 40, 60) / (30, 30, 30) / (40, 40, 30) … | 各 1 |

解读（**高置信推断**）：
1. 值域 `0..200`、`100` 占 80%+ ⇒ 与官方「カラー(RGB, 基本値 100 / 0～200)」定义一致。
2. **非等值三元组确实存在**（(0,100,100)、(50,60,60)、(50,50,70)、(40,40,30)、(30,40,60)）⇒ 这是**逐通道**颜色，不是单一亮度。
3. **引用自身変数的三元组也存在**（(1600057,1600058,1600059) ×7、(1600030..1600032) ×4、(1600054..1600056)、(1600062..1600064)、(1600017..1600019)）⇒ 作者会动态算颜色（例如按昼夜/皮肤色改面板色）。
4. 画纯色块（`<SQUARE>`）时用カラー把白色方块染成 `(50,60,60)` / `(40,40,30)` 这种暗色面板，用 `(0,0,0)` 做纯黑遮罩 —— 与「< 100 就是乘性压暗」的语义完全自洽。

### 3.3 flags 字（idx 12）（现象已验证 / 语义未确认）

- 13/14/15 长形式 100% 是 `0x01000000`；18/19 长形式 434/434 与 1256/1273 是 `0x02000000`（另有 17 条 argc19 是 `0x01000000`）。
- 与「是否带カラー槽」高度相关但**不严格等价**（那 17 条 argc19 带槽却是 `0x01000000`）⇒ **bit 的含义未确认**，实现里建议**按下标位置解析**（`argc >= 18` 才有カラー），不要用 flags 判断。

### 3.4 标题横幅：**没有**カラー槽（关键反证）

    TitleMap.mps event 2, pc90:
      150  args = [4096, 12001, 0, 1, 1, 1, 255, 512, 520, 100, 0]
           strs = ["SystemFile/Button01.png"]
           argc = 11  ⇒  结束于 idx10（BLEND），idx15..17 不存在

- 全库（550 公共事件）**0 条** 150 画图片番号 12001；唯一绘制点就是这个地图事件。
- ⇒ **222 的色调不可能由 150 带来**，只能是 pc91 的 290 type 5。

## 4. 222 / 188 的成因判定（核心）

### 4.1 已测事实

| 项 | 结果 |
|---|---|
| 图 | `SystemFile/Button01.png`，606×35，绘制在 (512, 520) 居中锚点（实测最佳偏移 (209,502) ⇒ 无位移） |
| 混合方式 | **RGB 逐通道乘以 k/255，alpha 完全不变**（alpha=191 的 texel 在 (246,503) 两侧读数都是 63；alpha=0 的 texel 完全一致） |
| k（截图 `full_21_21_35.png`） | **222**（69.5% 的采样；223 ×2745 / 221 ×2115 / 220 ×873 / 224 ×414 属重采样噪声） |
| k（截图 `full_21_22_48.png`，同位置同一张图） | **188**（78.5%） |
| 两图差异 | 仅 bbox x 229..794 / y 503..536（= 横幅本身），画面其余 6766 px 内**完全一致** ⇒ 排除全屏叠加、排除全局调色 |
| 其余 6 张截图 | 找不到横幅（免责声明 / logo / 无横幅时刻） |

### 4.2 为什么这必须是「周期性渐变」（决定性推理）

`290` 在 event2 里位于循环**之前**，只执行一次：

    pc90  150 [4096, 12001, …]                       画横幅
    pc91  290 [80, 30, 12001, 12001, -50, -50, -50]  ← 只执行一次
    pc92  180 [20]
    pc93  170          ← 循环开始
    pc94  180 [1]
    pc95  …键输入…      pc99/102/105 跳标签 'A'
    pc109 498          ← 循环结束
    pc110 212 'A'

- 若效果是**一次性**的（fade / フラッシュ：执行 → 变化 → 回到原位），那么帧 60（≈1 秒）之后与帧 4000（≈73 秒）之后**都应该是同一个终值**。
- 实测两张截图拿到的是 **222 与 188 两个不同的中间值**，且都不等于两端（255 = 100%，128 = 50%）。
- ⇒ 只有**周期性、连续渐变**才能解释：每帧取 [50, 100] 之间的某个值。

### 4.3 点滅A 还是 点滅B

官方原文（silversecond.com/WolfRPGEditor/Help/04ev_effect.html 的 snippet）：

> 「**+ 点滅A[明滅]** … 指定したRGB分（最大±200）の差だけ、指定フレームでカラー変更による明滅（**変化前、変化後、と交互に変化する**）を繰り返します。「RGB値全てを０に設定する」か、または「フレーム数を０にする」と、点滅は停止します。」
>
> 「**+ 点滅B[自動ﾌﾗｯｼｭ]** … 指定したRGB（最大±200）の±分だけ、指定フレームでカラー変更によるフラッシュ（**ウェイトせずに変化してから元に戻っていく**）を繰り返します。「RGB値全てを０に設定する」か、または「フレーム数を０にする」と、点滅は停止します。」
>
> 「+ フラッシュ … 指定した赤・緑・青の値」（yado：「ピクチャを１回だけフラッシュさせます」）

- 点滅A 若是「瞬间切换两端」，会让 k 只取 255 / 128 两个离散值 —— **实测不是**。
- 点滅B「瞬间变化后**逐帧回到原位**」⇒ p 在 [50, 100] 上**连续**取值 —— **与实测完全吻合**。
- ⇒ **type 5 = 点滅B[自動フラッシュ]**（**高置信推断**；不能排除「点滅A 也是渐变实现」这一可能，故不给「已验证」）。

### 4.4 数值链（已验证的部分 + 推断的部分）

    カラー百分率 p  ： 100 = 中性；p = 100 + Δ（Δ = −50 ⇒ p ∈ [50, 100]）
    逐通道字节       ： byte = clamp(round(p * 255 / 100), 0, 255)     ← 需 p 为浮点，p=50 → 128
    绘制            ： dst = round(src * byte / 255)  （RGB 同乘，alpha 不参与）  ← 已验证
    反解            ： k = 222 ⇒ p = 87.06；k = 188 ⇒ p = 73.73      ← 都 ∈ [50, 100] ✓

- `p = 50 → byte = 128` 与「实测最小的 k 是 188、从未出现 128」一致（两张截图都只是**中途**采样）。
- **未确认**：`p > 100`（变亮）时的混合方式 —— 实测样本里没出现过 > 255 的通道，官方只说「全部 200 就变白」，推测是加算/夹取，**不要**用乘法实现。

## 5. 实现建议

### 5.1 数据结构

    /// 単張图片のカラー（百分率，100 = 中性）。これをそのまま保持するのが最小実装。
    pub struct PictureState {
        // …既存フィールド（x, y, scale, opacity, blend, pattern, file/text…）
        /// 150 の idx15..17 / 290 の効果で決まる。100 がデフォルト。
        pub tone: [f32; 3],
        pub effects: Vec<PicEffect>,
    }

    pub struct PicEffect {
        pub kind: u8,          // head >> 4
        pub duration: i32,     // 帧数（0 = 停止/即時）
        pub elapsed: i32,
        pub target: [i32; 3],  // v1, v2, v3（カラー族は RGB 差分/値）
        pub pic_b: u32,        // type 4 の遷移先
    }

### 5.2 実装疑似コード

    fn op_290(pics: &mut PictureTable, cmd, vm) {
        let kind = cmd.head >> 4;
        let dur  = vm.eval(cmd.args[1]) as i32;
        let pa   = vm.eval_picture(cmd.args[2]);
        let pb   = vm.eval_picture(cmd.args[3]);
        let v    = [vm.eval(cmd.args[4]) as i32,
                    vm.eval(cmd.args[5]) as i32,
                    vm.eval(cmd.args[6]) as i32];

        match kind {
            5 => {                                  // 点滅B[自動フラッシュ]（高置信推断）
                let pic = pics.get_mut(pa);
                if dur <= 0 || v == [0, 0, 0] {     // 官方の停止条件
                    pic.remove_effect_of(kind);
                    pic.tone = [100.0, 100.0, 100.0];
                } else {
                    pic.set_effect(PicEffect { kind, duration: dur, elapsed: 0,
                                               target: v, pic_b: pa });
                }
            }
            1 => {                                  // 点滅系の停止/復位（dur は常に 0）
                let pic = pics.get_mut(pa);
                pic.remove_effect_of(kind);
                pic.tone = [100.0, 100.0, 100.0];
            }
            0 => {                                  // フラッシュ（単発）
                pics.get_mut(pa).flash(target = v, frames = dur.max(1));
            }
            2 => {                                  // 描画座標シフト[最終値]
                let pic = pics.get_mut(pa);
                pic.shift = (v[0], v[1]);           // 150 の X/Y に加算、帧 0 は即時
                if dur > 0 { pic.shift_tween = Some((dur, 0)) }
            }
            4 => {                                  // 5 帧移动+缩放，A → B
                pics.tween_and_swap(pa, pb, x = v[0], y = v[1], scale = v[2], frames = dur);
            }
            3 | 7 | 8 | 9 | 10 => { /* 未确认：现阶 no-op（记录日志，勿臆测） */ }
            _ => { /* 未知类型：no-op + 警告 */ }
        }
    }

    /// 毎フレーム（60fps）1 回
    fn tick(pic: &mut PictureState) {
        for e in pic.effects.iter_mut() {
            e.elapsed += 1;
            let t = (e.elapsed % e.duration) as f32 / e.duration as f32;   // 0..1
            match e.kind {
                5 => {                                                      // 点滅B：瞬時に Δ、その後 線形で戻る
                    for i in 0..3 {
                        pic.tone[i] = (100 + e.target[i]) as f32 * (1.0 - t) + 100.0 * t;
                    }
                }
                0 => { /* 単発：t で往復（0→1→0）、終わったら除去 */ }
                _ => {}
            }
        }
    }

    /// 描画時
    fn tone_byte(p: f32) -> u8 { (p * 255.0 / 100.0).round().clamp(0.0, 255.0) as u8 }
    // p <= 100: dst = src * byte / 255      ← 已验证（k=222 ⇔ p=87.06）
    // p >  100: 未确认（不要用乘法）

## 7. 对既有文档的修正

1. **`docs/OPCODE_124.md:207` 有一句是错的**：「本作 **0 条** 290 Effect 用于图片，补正恒为空，所以先让 `0x4400 == 0x4000` 即可」。实际有 **640 条** 290 作用在图片上（picA / picB 都是ピクチャ番号），且 **type 2（描画座標シフト，126 条）会改变 X/Y**、**type 5 / 0 会改变カラー**。⇒ `0x4400`（エフェクト補正なし）与 `0x4000` **迟早要分开**，只是本作恰好没有用 `0x4400` 读 X/Y 的场合（8 条全是读拡大率 idx2/idx3），所以短期可以不分。实现 290 时必须把 `shift` 与 `tone` 存成「效果层」，别直接改基值。
2. **`docs/OPCODE_SPEC.md` §5.49（290）** 里「argc = 7、类型在 arg0>>4、低 4 位恒 0、时长在 arg1、其余 TODO」是对的，本文把它补完：10 个类型的实测语义 + RGB 族判定 + 停止条件。
3. **150 的カラー槽**在 `docs/OPCODE_SPEC.md` 的 150 小节里没有 —— 长格式（argc 12..19）的 idx11..18 表建议按本文 §3.1 补进去。

## 6. 阻塞 M1 首帧的开放问题（按严重度）

### Q1（P0）`401 ChoiceCase` 顺延落进下一个 case —— 选择支的每个分支都被执行

**证据链（已验证）**：

1. c42 的 102 结构是 401[2]（`:114`，はじめから）/ 401[3]（`:120`，つづきから）/ 401[4]（`:128`，おわる）/ 499（`:133`）。
2. `exec.rs:582-591` 用 `ChoiceReply::Index(i)` → `case_target(i as i32 + 2)`；TraceHost 恒 `Index(0)`
   ⇒ 只该走 `case 2`（`:114-119`：`180[12]` → `130 Teleport` → `499 end`）。
3. 但实测（C3）：**f=15 出现 teleport（case 2 的尾巴）**，接着 **f=16..27 平坦 12 帧（= case 3 的 `180[12]`）**，
   **f=28 起 c14（case 3 的 `210[500014]`）把菜单/存档界面拉起来**，一直跑到 f=200 —— 三个 case 连着跑。
4. 原因在 `exec.rs:985-992`：`Control::Case { block }` 一律 `case_target(arg(cmd,0))`。
   当执行流**顺延**到一个 401 时（上一个 case 的 body 刚结束），`case_target` 找到的正是**它自己**这个 case，
   于是「跳进下一个分支」而不是「跳到块尾」。`420` 没有这个 bug（`program.rs:262-271` 的注释说明了为什么：
   420 的 arg 不在 case 表里 ⇒ `case_target` 返回 `None` ⇒ 落到 `end_target`）。

**影响**：标题菜单的「はじめから」会把「つづきから」也跑一遍（真实运行时表现为：新游戏开局后立刻跳进读档菜单；
更严重形态是每个分支都执行一遍，`175 EndGame` 也会被扫到）。**M1 的「选择支切换分支正确」验收项现在不成立。**

**建议修法**：给 `Block` 记「当前进入的 case 的 pc」；执行 401 时若 `inst.pc` 大于该 case 的 body 起点，
说明是顺延到达 ⇒ 直接取 `end_target`。等价做法：预编译时给每条 401 标记「本 case 的 body 起点」，
运行期比较 `inst.pc` 是否等于「刚进入的 case 起点」。

### Q2（P0 视觉）文本图片的 rect 是 1×1

**证据**：`picture.rs::merge_args` 只接受 `w>0 && h>0` 的 window，而 12053/12501 的参数是 `[1,1]`；
`quads()` 的 text 分支 `dst = [x, y, max(0,w), max(0,h)]` ⇒ 1×1。C4 打印的 `text pic 12501 at [715,115,1,1]`
与出图里被裁的公告都指向这一条。

**影响**：所有文本型图片被裁到不可读；83.5% 非黑像素里没有一块是完整文字。

**建议修法**：`1×1`（或 ≤ `MIN_BOX`）应视为「无显式框 ⇒ 由文本排版自适应」，
即 `atlas::texts` 里 `rect.w <= 2 || rect.h <= 2` 时改用「画布宽高（或到屏边）+ 文本实测行数×行高」。
另：`TEXT_PX = 22` 是从中文本实测反推的常量，需与 retail 对照确认（**未验证**）。

### Q3（P1）图片号 `-2` 被求值成 `0`，`is_screen_layer()` 永不触发

**证据**：`exec.rs:789`（`MagicKind::Opaque => 0`）+ `decode_picture` 里图片号也走 `eval_num`。
c42 有 9 个 `num_raw=-2` 的 150 站点（`:17/20/27/30/37/40/43/48/51`），运行时全部变成 picture 0。

**影响**：本作视觉无害（纹理正好 1024×576、位置 (0,0)、scale 100），但「负号 = 整屏层」这条假设
（`picture.rs` 文档里的 **H-PIC-1**）**从未被真实数据验证过**。

**建议**：图片号应像其它实参一样先过 `picture_arg` 的 flag 判断（或对小负数特判保留），
并在 `docs/UNVERIFIED.md`（**该文件当前不存在**，`picture.rs` 注释却在引用它）里登记 H-PIC-1。

### Q4（P1）内置图元没有实现

`<TRI-RIGHT>`（运行时 137 次）、`<SQUARE>`（92 次，mps 侧 351）、`<C>/<L>/<R>`、`<LINE>/<FRAME>/<CIRCLE>`、
`<GRADX-a-b>/<GRADY-a-b>`（§4.3 共 24 种）都需要程序化绘制。

**影响**：`pic 12005` 永远不产生 quad；菜单光标/按钮全部缺失。
**建议**：在 `wolf-render` 里加 `primitive` 模块，按名字分派到三角形/矩形/渐变；

## 8. 一句话结论

M1 的**渲染管线已经成立**（1024×576 全屏标题背景 + 九宫格窗口 + 中文文本，83.5% 非黑像素，0 warning），
但**语义还不成立**：闭包是 62 个事件 / 9 843 条指令 / 38 种 opcode（PLAN 的 4/671/26 全错），
且当前 200 帧画面是「选择支顺延」缺陷（Q1）跑出来的，混进了存档界面元素。
先把 Q1 + Q2 修掉，再以「1 个存活槽 / 1 个全屏 quad」的干净标题画面作为 M1 的验收基准。

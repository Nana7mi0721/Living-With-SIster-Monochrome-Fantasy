
### 7.3 决定性检验：`0x4000` 的 obj 到底是不是「图片番号」

lead 要的那张「arg2 → 该事件里是否存在同号 150 指令」的对照表，实测结果（work/_probe124_37_picnum.py /
_probe124_38_picnum2.py / _probe124_39_picnum3.py / _probe124_40_picvar.py）：

| 检验 | 分子 / 分母 | 比例 | 解读 |
|---|---|---|---|
| 0x4000 的 obj 是**常量**（`0 <= obj < 100000`） | 675 / 719 | 93.9% | 其余 44 条用变量（如 `1600031`）间接给番号 |
| 常量 obj **在同一事件里**也有同号 150 | 109 / 675 | 16.1% | 低，但见下面两条解释 |
| 常量 obj **在全库任意 150 的图片番号集合里**（691 个番号） | **623 / 675** | **92.3%** | ⇒ obj 就是图片番号 ★★★ |
| 作为对照：0x1000/0x1200 的常量非负 obj 落在图片番号集合 | 0 / 0 | — | 40 条 obj 全是负哨兵，与图片番号空间无关 |
| 150 指令用**变量**当图片番号的条数 | 5711 / 20425 | 28.0% | 所以「同事件常量扫描」天生会漏掉三分之一的画图 |

为什么「同事件」命中率只有 16.1% 而全库有 92.3% —— 两个真实原因，都是**支持**假说的：

1. **窗口管理器读别人画的窗口图。** `ev224 ウィンドウ処理` 里有 **0 条 150**，却有 20 多条
   `0x4000` 读 12001 / 12002 / 12003 / 12005 / 12053 / 12054 / 12061 / 12062 / 15000 / 10001。
   这些窗口图片是**调用方事件**（ev63 X[共]メッセージウィンドウ 等）用
   `150 [3165968, 1600021, …]`（番号在变量里）画出来的，管理器只负责查/改它们的属性 ——
   这正是「读属性」而不是「自己画」的典型形态。
2. **立绘闪烁读的是底图。** `ev236 立ち絵瞬き1` 自己画的是 **92** 号（眼睛闪烁图），
   却读 **90** 号 —— 90 号是别人（ev215/218/220/295/326/421/443）画的**基础立绘**，
   Read field 9 = 「基础立绘还在用吗？不用就收工」。若 0x4000 不是「读图片属性」，
   这条指令毫无意义。

按属性下标的命中分布（常量 obj）：

| field | 命中全库图片番号 | 未命中 | 说明 |
|---|---|---|---|
| 0 / 1 / 2 / 3 | 0 / 0 / 0 / 0 | 4 / 1 / 2 / 1 | 这 8 条读的是「别人画的窗口图」（12002 / 12004 / 12005 / 12053 …），番号确实存在，只是不是本事件画的；另有 `803`（リロード按钮）、`3800-3920`（カード）等 |
| 4 | 7 | 0 | 读「当前图案」，番号必在本事件 |
| 5 | 1 | 0 | 同上（唯一 1 条） |
| 8 | 555 | 26 | 26 条是 `8008` / `8117`（各 9 次）+ `467`（2 次）+ 零星，都是**用变量番号画出来的**按钮图 |
| 9 | 60 | 18 | 同上，立绘/立绘系 |

**结论**：0x4000 = 读取图片(ピクチャ)属性的假说，**在不依赖官方文档的前提下也被独立证实**
（92.3% 的常量 obj 精确落在全库图片番号集合里，且未被解释的 52 个也是真实的图片番号 ——
只是那几张图是用变量番号画的）。arg3 就是属性下标（field），见 §5.1 的 9 行表。

# opcode `112` 文字列条件分岐 —— 它必须和 `111` 共用同一套块栈

> 标记规范沿用 docs/FORMAT_SPEC.md：**已验证** / **未验证** / **★已实测纠正**。
> 本文只讲一件事：`112` 在**预编译**阶段必须自己开一个 `BlockKind::Condition` 块。
> 漏了这一步不会报错、不会警告，只会让整段脚本的分支目标错位——本作开场剧情就是被它卡死的。

---

## 0. 一句话结论

`112` 是 `111` 的**字符串形态**：相同的 `401/420/499` 骨架、相同的 `argc = 1 + condCount`、
只是每个条件用「一个字符串变量 vs 一个内联字符串」比较，而不是「3 个 i32 槽」比较。
既然骨架相同，**它就必须在 `crates/wolf-vm/src/program.rs::from_slots` 里开块**；
否则它的 `401` 会挂到外层分支上、它的 `499` 会提前关掉外层分支。

修复后全库的块栈**完全平衡**（孤儿 case / 孤儿 end / 未闭合块全部归零），
且四个计数器与 opcode 普查**逐一对上**（§3）。

---

## 1. 字节码格式（已验证）

| 项 | 值 |
|---|---|
| 站点 | 公共事件 **123** 条、地图页面 **21** 条（BASELINE.json `ce_opcodes` / `mp_opcodes`） |
| `argc` | `1 + (head & 0x0F)`，实测 `{2:93, 3:18, 4:8, 5:4}` ⇒ 条件数 1..4 |
| `strc` | 恒 **4**（4 个内联字符串槽，多余槽是空串） |
| `intArgs[0]` | `head`：低 4 位 = 条件数，bit4 = 条件全不成立时是否走 `420` else |
| `intArgs[1..]` | 每个条件一个字符串变量 magic（`3000000..3999999` 段，可带 `0x1/0x2/0x3 << 28` 寻址位） |
| `stringArgs[i]` | 第 i 个条件比较用的字符串（可含转义，需 `expand`） |
| 语义 | **只支持相等比较**（本指令没有大小序运算符），命中即跳 `401` 的 case 体 |

样例（都是真实数据）：

| 站点 | 字节码 | 含义 |
|---|---|---|
| `ev94 pc235` | `ints=[1, 1600006] strs=['save1','','','']` | self 字符串 6 是否等于 `save1` |
| `ev263 pc11` | `ints=[20, 806906373 x4] strs=['0','1','2','3']` | 4 个条件分支 |
| `SampleMapA 事件 0 pc478` | `ints=[20, 3000016 x4] strs=[...]` | 主角名字四选一（本作开场） |

## 2. 为什么漏掉它会静默错位（★已实测纠正）

`program.rs` 的第一遍扫描维护一个**容错块栈**：遇到 `111/102/170/176/179` 开块，
遇到 `401/420/421/499` 收块。原先 `112` 不在开块指令表里，后果是：

1. `112` 自己的 `401` 被算成**外层分支**的 case（外层 case 表因此多出几项）；
2. `112` 自己的 `499` 提前把**外层分支**关掉，外层块的 `end` 因此提前若干个槽；
3. 于是运行时答完选择肢，`pc` 落到「外层块的 end」，正好插进下一个 case 体中间——
   状态没被初始化，脚本绕回自己的 `213` 标签，形成死循环。

`exec.rs` 那条老的 `112 => eval_string_condition(...)` 分支还会兜底（拿不到 `Control::Block` 时直接 `pc+1`），
这使错误**表现为「永远走 case 1」而不是报错**——最难查的那一类。

## 3. 算术证明：修复后计数器与 opcode 普查一一对上（已验证）

| 计数器 | 修复前 | 修复后 | 应当等于 | 对上 |
|---|---|---|---|---|
| `blocks` | 13,310 | **13,433** | 旧值 + 112 站点 123 | ✅ |
| `conditions` | 10,743 | **10,866** | `111`(10,743) + `112`(123) | ✅ |
| `cases` | 18,460 | **18,555** | `401` 全库普查 18,555 | ✅ |
| `else_cases` | 3,246 | **3,279** | `420` 全库普查 3,279 | ✅ |
| `cancel_cases` | 150 | **153** | `421` 全库普查 153 | ✅ |
| `orphan_cases` | 131 | **0** | 没有 `401` 找不到自己的块 | ✅ |
| `orphan_ends` | 138 | **0** | 没有 `499` 找不到自己的块 | ✅ |
| `implicit_closes` | 66 | **54** | 运行到事件末尾才闭合的块（越少越好） | — |
| `unclosed_blocks` | 3 | **0** | 块栈最后一次完全平衡 | ✅ |

关键一行：**`cases` 从 18,460 涨到 18,555，正好等于 401 的真实条数**，
也就是说现在每一条 `401` 都挂在某个真实的块上，一个都没漏。

## 6. 仍未验证

1. `head` 的 bit4 是不是「条件全不成立时走 else」还是别的标志——本作里 `420` 恒伴随 `112`，
   两种读法在字节码上不可区分。
2. 字符串寻址的高位（`0x1/0x2/0x3 << 28`）语义未确认；当前按原始 32 位 magic 直接取值。
3. `112` 是否允许「同一条件比较多个字符串」的槽位复用（`strc` 恒 4 但有效槽数与条件数的对应关系，
   docs/OPCODE_SPEC.md §5.10 也标为 TODO）——本作 123 条里有效槽位都按序使用，尚未遇到反例。

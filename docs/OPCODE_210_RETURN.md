# 210 / 300 公共事件调用 —— 参数表与返回值路径

> 结论先行：被调用事件把返回值写在**自己的** self 第 6 群，槽号来自事件尾部声明的
> `return_value_id`（magic `1_600_000 + id`）；调用方在 210/300 **参数表的末尾**
> （`a[2 + number_count + string_count]`）用一个 magic 操作数指定"结果落在我哪个变量"。
> 协程结束时 `reap_finished` 做一次
> `caller[dest] ← callee.self[1_600_000 + callee.return_value_id]`；
> 被调用事件没有声明返回值（`0xFFFF_FFFF`）时**不复制**，调用方的变量保持原值。

本文所有数字都是对 `work/_ce_full.json`（Commonevent.dat 550 事件，139,273 条真实指令）
与 `work/_ce_meta.json`（550 个事件尾部元数据）重新统计出来的，复现脚本见 §7。

## §1 一次 210/300 的时序

```
caller                                  child (被调用事件实例)
  pc -> 210/300                                   │
   │  a[0]        = 目标（500000+n / 600000+n / 按标题）│
   │  a[1]        = param_status                    │
   │  a[2..2+num] = 数值实参                        │
   │  a[2+num..2+num+str] = 字符串实参（未投递）    │
   │  a[2+num+str] = 返回目的 magic  ← 本文重点     │
   │                                                │
   ├─ spawn_child：args -> child.self_vars[600+i]    │
   │              child.return_to = Some(dest)      │
   │              caller.wait = Child(id)           │
   │                                                ├─ 跑正文，把结果写进
   │                                                │  self[1_600_000+retid]
   │                                                └─ 172 BreakEvent -> pc = len
   │                                                │
   └─ reap_finished（同一帧内，见 §5.3）：           │
        if child 有 parent 且 parent.wait == Child(child.id):
            if let Some(slot) = return_slot(child.program):   ← retid != 0xFFFF_FFFF
                caller[dest] = child.self_vars[slot]
            parent.wait = None
```

关键点：**返回值不经过栈**。210 不开 Rust 调用栈，子实例是独立协程（docs/OPCODE_SPEC.md §7.1），
返回值的传递完全靠"子实例自己的 self 群 6 + 父实例的 dest 操作数"这两样东西，在子实例被回收的那一刻
一次性搬运。

## §2 参数布局

### §2.1 `param_status`（a[1]）

`wolf-format/src/command.rs:145-155` 取 `params[4..8]`（即第二个 4 字节字）当状态字，
位域在 `command.rs:251-302`（`ParamStatus`）：

| 位 | 宽度 | 含义 |
| --- | --- | --- |
| 0..=3 | 4 | `number_count`：数值实参个数 |
| 4..=7 | 4 | `string_count`：字符串实参个数 |
| 8..=23 | 16 | 未用（本作实测恒 0） |
| 24 | 1 | `return_value_enabled`：要不要取返回值 |
| 25..=31 | 7 | 未用（实测恒 0，故 210 的 a[1] 只可能是 `0x0000_00NN` / `0x0100_00NN`） |

参数总字数 `total_count() = number_count + string_count`，
`command.rs:164-180` 的 `expected_param_len` 也用这个式子反推字节长：
`8 + 4*total + (rv ? 4 : 0)` —— 这正是"目的操作数在参数表末尾"的独立佐证。

### §2.2 目的操作数的位置：a[2 + total_count]

本节是这个任务里唯一一处**现有实现真的算错了**的地方。

旧代码（`exec.rs` `call_arguments`）用：

```rust
let return_to = if status.return_value_enabled() {
    Some(arg(cmd, 2 + status.number_count()))   // ← 少算了 string_count
} else { None };
```

正确位置是 `2 + number_count + string_count`。两种候选在全数据上的打分：

| 定位方式 | 落在合法 magic 上的站点 |
| --- | --- |
| `2 + number_count`（旧） | 16 / 22 |
| `2 + total_count`（新） | **22 / 22** |

* **6 个站点退化成长整数字面量 0**（`E266 pc18`、`E270 pc278/637/711/2071/2119`）：

### §2.3 参数投递现状（实现缺口，未修）

* 数值实参：`spawn_child` 写进 `child.self_vars[magic::SELF_ARG_BASE + i]`，即
  `600 + i`＝第 6 群第 i 槽（magic `1_600_000 + i`）。这条是 Lead 用 9,938 个静态调用点
  定下来的，与本文 §3 的返回值槽**同一个群**。
* 字符串实参：**没有投递**。`call_arguments` 只取 `number_count` 个字，字符串参数
  （magic 3_000_000 段 / 直接 1_600_xxx 引用）既不求值也不写进子实例的字符串 self 群。
  本作 22 个站点会用到它（其中 17 个是"传一个字符串进去、要一个判定结果回来"），
  所以这是一个**已知会产生错误结果**的缺口，不在本次修复范围内，记在这里。
* 参数槽与返回槽共用群 6：如果某事件既收了 N 个实参、retid 又 < N，实参会被它自己的返回值覆盖 ——
  本作 74 个声明里 retid 最小是 0（E549，且它不写该槽），没有观测到真实冲突，因此**未确认**
  原版是否会因为重叠而改走别的群。

## §3 return_value_id

### §3.1 在二进制里的位置

每个公共事件在 `cmds` 之后还有一整套尾部（`work/fs_ce.py:143-171`、`work/parse_ce.py:50-67` 逐字段对齐过，
550/550 事件解析到 `endpos=5,532,174`，文件长 `5,532,175`）：

```
cmds ...
  u1 0x92 之前的占位: u1 0x01 + 5 字节 0
  t_str  memo
  u1 0x8F
  t_str×n argnames, u4 n, n×u1 modes, u4 n2, n2×t_str, u4 n3, n3×[u4], u4 n4, n4×4字节
  u1 0x90, u4 color, t_str×100 (self 变量名)
  u1 0x91, u1 0x01 + 5 字节 0
  u1 0x92, t_str retname, u4 return_value_id, u1 0x92
```

`return_value_id` 就是这份"返回值声明"，`wolf-format` 的
`commonevent.rs:69/225` 已经把它读出来了，只是 `Program` 之前没带。

### §3.2 直方图

550 个事件里 **476 个**是 `0xFFFF_FFFF`（未声明），74 个声明了：

| retid | 事件数 | | retid | 事件数 |
| --- | --- | --- | --- | --- |
| 99 | 33 | | 11 | 3 |
| 10 | 17 | | 4 | 3 |
| 90 | 4 | | 9 | 2 |
| 30 | 4 | | 5 | 2 |
| 0 | 4 | | 95 | 1 |
| | | | 15 | 1 |

retname（`retname` 字段）非空的有 74 个，与声明数一致；`0xFFFF_FFFF` 的事件 retname 一般为空。

### §3.3 语义：retid 是 self **第 6 群**的槽号

即返回槽 = `1_600_000 + retid`，与实参落点同一个群。三条独立证据：

1. **编辑器自己的注释**。`E17 "▲アイテム所持数取得"`，retid = 10，正文第 0 条就是
   `103 Comment "所持数を得る（コモンセルフ10番に入れた値を返す）"`
   ——"把放进**公共 self 10 番**的值返回"，然后它用 `300` 转发子事件结果到
   `1_600_010`（pc1，rv=1）。
2. **正文写的就是这个槽**。`E22 "▲メンバー情報取得[数値]"` retid=30：pc0 `121 a=[1_600_030,0,0,0]`、
   pc12 `121 a=[1_600_030,1,0,0]`、pc21 `300 ... dest=1_600_030`。
   `E23 "▲メンバー情報取得[文字列]"` retid=9：pc0 就是 `300 ... dest=1_600_009`。
3. **全量统计**。74 个声明事件中 **70 个**正文确有写入 `1_600_000+retid`（写入手段：121/122/124 的目标、
   210/300 的 dest 操作数、250 `Database` 的 a[4]）。

### §3.4 目的变量由调用方**任选**，与 retid 无绑定

376 个 rv=1 站点的 dest 操作数，**全部**落在 self 第 6 群（`1_600_000..1_600_099`）：
1_600_005 / 1_600_007 / 1_600_008 / 1_600_011 / 1_600_060 / 1_600_062 / 1_600_091 …
但**不等于** `1_600_000 + 被调事件 retid` 是常态：

```
E270 pc121: 300 "▲先頭空白削除"(retid=9)  -> dest 1_600_007   ← 7 != 9
E270 pc122: 300 "▲文字列数値判定"(retid=4) -> dest 1_600_060   ← 60 != 4
```

也就是说 retid 决定"子事件把结果放哪"，dest 决定"我要把它搬到我哪"。二者相等只是
"包装器把子返回值原样转存到自己的返回槽"这种写法的副产品。

### §3.5 4 个声明的例外（原作数据瑕疵）

声明了 retid 却**从不写**该槽，因此对它们的"取返回值"必然读到 0/陈旧值：

| 事件 | retid | 标题 |
| --- | --- | --- |
| E37 | 90 | ◇ランダムエンカウント処理 |
| E151 | 99 | X[戦]戦闘コマンド設定 |
| E198 | 15 | X┣◆ターン終了処理 |
| E549 | 0 | forSteam[caution]（retname 是垃圾字符串 `ff`） |

## §4 未证实 / 未实现的部分

### §4.1 retid = 0xFFFF_FFFF 时"不复制"是推断

事实：本作有 **8 个** rv=1 站点调用的是**未声明**返回值的事件
（`E262 pc10/24/39→E100`、`E266 pc18→E102`、`E270 pc278→E98`、`E271 pc22→E98`、
`E265 pc35→E104`、`E128 pc40→E117`）。

进一步测量：这 8 个 callee 的正文也**没有任何**写入自我群 6 的指令（逐条扫过它们的 `1_600_xxx` 目标），
所以"复制"和"不复制"在数据上都会得到一个无人初始化的值，只是不复制至少不会覆盖调用方原有的
变量。原文（浏览器ウディタ）到底怎么处理，**未能验证**——本实现选择不复制，理由是它可观测行为最小。

### §4.2 字符串实参未投递

见 §2.3。22 个站点因此拿不到输入；其中 17 个是"判定类"事件，会返回错误结果而不是崩。

### §4.3 8 个悬空的按标题调用

`300` 全量 1,164 个站点里 1,156 个标题精确命中，8 个命中不了（`E270` 的
`'○◆マップをズーム'` ×4 与 `'▲┣[ズ—ム]イベント位置をズーム座標に'` ×4，前者带全角 ◆、
后者用的是 U+2014 em dash 而不是 U+30FC）。本作 `Commonevent.dat` 里没有任何事件标题包含
"ズーム"，所以这是**原作里的死调用**（基本システム里有、这个游戏里没带）。VM 现在的行为是记一条
`LogLevel::Error` 并继续，符合"没有对应事件就什么都不做"。

### §4.4 未做逐帧仿真对比

结论来自静态数据（写入点/读取点/声明三者的对应关系）与单元测试，**没有**把原版游戏跑起来抓
"某次调用后调用方变量值"做二分对比。原版是 DxLib + 闭源运行时，暂时无法做。

## §5 实现改动（crates/wolf-vm）

### §5.1 Program 带上声明

`program.rs`：新增 `pub return_value_id: u32` 字段与
`pub const NO_RETURN_VALUE: u32 = u32::MAX`；`Program::compile` 从
`CommonEvent.return_value_id` 赋值；`Program::from_slots`（地图页）填 `NO_RETURN_VALUE`
（地图事件页没有返回值声明）。

### §5.2 复制

`exec.rs`：

```rust
fn return_slot(program: &Program) -> Option<usize> {
    if program.return_value_id == NO_RETURN_VALUE { return None; }
    Some(Magic::decode(1_600_000i32.wrapping_add(program.return_value_id as i32)).index() as usize)
}
```

`reap_finished` 里改为 `if let Some(slot) = return_slot(...)` 才搬运，并且搬运的
**目的操作数取自子实例自己的 `return_to`**（它在 `spawn_child` 里被写到子实例上，
描述的是"子实例产出的值写到哪"；旧代码读父实例的 `return_to`，永远是 `None`，
所以返回值从来没有被搬运过）。

### §5.3 顺带修掉的时序 bug

`reap_finished` 原来把 `pc >= len` 的实例一律当"已结束"，包括**正阻塞在子协程上的父实例**。
当 `210` 是一个事件的最后一条指令时，父实例的 `pc` 已经等于 `len`，
于是它会在子实例回收**之前**被回收，返回值连同 `WaitState::Child` 一起丢掉
（单元测试里第一帧就出现 `finished=[1, 2]`）。现在的过滤条件加了
`!matches!(i.wait, WaitState::Child(_))`：阻塞中的父实例不算结束，子实例先被回收、
父实例的 `wait` 变 `None`，下一帧才作为普通结束实例被清掉（多活一帧，无副作用）。

### §5.4 测试

`cargo test -q -p wolf-vm` → **66 passed**（原 63 + 3）：

* `common_event_return_value_lands_in_the_callers_variable` —— callee 声明 10、写
  `1_600_010 = 42` 后 `172`；caller `210 a=[500_002, 0x0100_0000, 2_000_000]`；
  断言 `V0 == 42`。
* `common_event_without_declared_return_leaves_the_caller_alone` —— callee 未声明返回值；
  caller 先写 `V0 = 5` 再调用；断言仍是 `5`。
* `return_destination_follows_the_string_parameters` ——
  `210 a=[500_002, 0x0100_0011, 5, 0, 2_000_007]`（num=1、str=1、rv=1）；断言
  `V7 == 42` 且 `V0 == 0`（旧实现会把 dest 读成 `a[3] = 0`）。

另外：`cargo build -q -p wolf-cli` 通过，`./target/debug/wolf-cli.exe verify` 仍是
**PASS — 63/63**（含 `save.*`/`monochrome.*` 各段基线，未被本次改动影响）；
`cargo test -q -p wolf-game` 4 passed。

## §6 与任务口径的差异

任务书说"全游戏 **115** 个调用点在参数状态字里置了 bit24"。核实结果：

* 115 = **Commonevent.dat 里 `210` 的 rv=1 站点数**（确实是 115）。
* 加上 `300` 的 261 个，`211` 的 0 个，一共 **376**；再加地图事件里的 1 个 = **377**。
* 所以"115"是 210 这一半的口径，返回值路径对 300 同样适用（且 300 占了 261/376，是多数）。
  两者语义完全一样，只是 300 的目标要从 `s[0]`（标题）解析，本作 1,164 个 300 站点里 1,156 个能解析。

## §8 字符串实参（task-26 补测）

### §8.1 布局：字符串实参夹在数值实参和返回目的之间

21,655 个 `210`/`211`/`300` 站点零反例：

```
a[0]               目标（500000+n / 600000+n / 210 的 0）
a[1]               param_status
a[2 .. 2+nnum]     数值实参        （在调用方上下文求值）
a[2+nnum .. +nstr] 字符串实参      （见 §8.2）
a[2+nnum+nstr]     返回目的操作数  （仅 bit24=1 时存在）
```

即 `len(a) - 2 - number_count == string_count + (1 if 返回位 else 0)`，21,655/21,655 成立。

### §8.2 一个字符串槽的两种形态

| 形态 | 判据 | 取值 |
| --- | --- | --- |
| 字面量 | `string_enabled(k)` = bit12+k 置位 | `stringArgs[1 + k]` |
| 变量引用 | `string_enabled(k)` 清零且该槽字 != 0 | 该字是 magic，在**调用方**上下文求值（`eval_str`） |

* `stringArgs[0]` 分别是 `210` 的空占位（8,171/8,171 站点都是空串）和 `300` 的被调事件标题。
  所以第 k 个字面量在 `stringArgs[1 + k]`，**不是** `stringArgs[k]`；照 k 取会让 300 把标题当参数传下去。
* 两种判据在本作数据上完全等价：16,110/16,185 个槽字是 0 且使能位=1；使能位=0 的 73 个槽字全部非 0
  （`1600009`×24 · `1600005`×23 · `1600007`×14 · `1600008`×8 · `1600006`×3 · `3000000`×3）。
  实现里两个条件都判，这样「字面量恰好是空串」和「变量 0」不会互相污染。

### §8.3 落点：被调事件的 CSelf5..8

`1_600_000 + n` 是「当前公共事件的 CSelf[n]」（magic 解码成扁平槽 `600 + n`），所以：

| 编辑器输入框 | magic | 扁平 self 槽 | 实现常量 |
| --- | --- | --- | --- |
| 数值输入 1..4 | `1_600_000..1_600_003` | 600..603 | `magic::SELF_ARG_BASE + i` |
| 字符串输入 1..4 | `1_600_005..1_600_008` | 605..608 | `SELF_ARG_STRING_BASE + k` |

CSelf4 是编辑器的空档：**引擎不往它投递实参**（数值实参只到 CSelf3）。本作有 107 处操作数引用
`1_600_004`，但全是事件内部当作普通局部槽在用（ev90 的 `121 [1600020, 1600001, 1600004, ...]` 之类），
没有任何调用点期待它带进实参。

### §8.4 规模（这决定值不值得改）

| 量 | 数 |
| --- | --- |
| 调用点总数（`210`×20,485 · `300`×1,170 · `211`×4） | 21,659 |
| **带字符串实参的站点** | **8,260**（`210`×8,191 · `300`×69 · `211`×0） |
| `string_count` 直方图 | `210` {0:12,294, 1:250, 2:7,941} · `300` {0:1,101, 1:60, 3:9} · `211` 全 0 |
| 被调事件读 `1_600_005` 的站点 | **8,229** |
| 被调事件读 `1_600_006` 的站点 | **7,957** |
| 被调事件读 `1_600_007` / `1_600_008` 的站点 | 10 / 44 |

8,256 个站点解析出了被调事件，4 个 `300` 的标题在本作里不存在（原作死代码）。
最高只用到 3 个字符串实参，**从没出现 CSelf8**，所以上限取 4 是安全的。

按「消费 vs 转发」细分（转发 = 被调方又用 `210/300` 把它传下去，消费 = `112/122/250/101/150/221`）：

| 实参 | 消费 | 转发 | 未用 |
| --- | --- | --- | --- |
| arg#0 → CSelf5 | 442 | 7,787 | 27 |
| arg#1 → CSelf6 | 153 | 7,787 | 10 |
| arg#2 → CSelf7 | 0 | 0 | 9 |

被调方触及这些槽的 opcode：`210`×15,616（转发）· `112` 字符串条件×5,347 · `122` 设字符串×285 ·
`250`×62 · `150`×52 · `221`×2。分槽：CSelf5 {210:7,829, 112:4,882, 122:117, 250:4}、
CSelf6 {210:7,787, 112:457, 122:155, 250:4, 221:1}、CSelf7 {122:13, 250:10, 112:8, 150:3, 221:1}、
CSelf8 {150:49, 250:44}。

结论：绝大多数调用点是**逐层转发的包装器**，真正的消费者埋在末端。丢掉字符串实参不会让任何事件报错，
只会让最末端的 `112` 比较全部失败、`150` 的说明栏全空——正是「消息窗口不显示任何字」的症状。

### §8.5 铁证

1. **字面量路径**：ev109 pc63 `300 [0, 4113, 0, 1600005] s=['X[移]メニュー時文章表示', '外すことができません']`。
   `4113 = 0x1011` ⇒ num=1 / strc=1 / 使能位 0 置位 ⇒ 字面量 `s[1]`。被调 ev101 在 pc35 执行
   `122 [1600005, 2304] s=[BSn, LF]`（把收到的 `\n` 两字符转成真换行）——它读的正是自己的 CSelf5。
2. **文本消费路径**：ev66 `X[共]万能ウィンドウ説明欄変更` pc23 的 `150` 文本参数是
   `\f[\cself[18]]\space[0]<C>\cself[5]`，直接用 cself[5] 当说明栏正文。
3. **转发路径**：包装器 ev264 `○◆メッセージウィンドウ[インタフェ—ス]`（被 7,787 个站点调用）
   pc45 `210 [600101, 17, 1600000, 1600006]`（`17 = 0x11`：num=1 / strc=1 / 使能位清零 ⇒ 转发自己的 CSelf6）、
   pc47 `210 [600104, 18, 0, 0, 1600005]`（转发自己的 CSelf5）、pc48 `210 [600103, 4113, 1600002, 0]`（字面量空串）。
4. **混合路径**：ev119 pc22 `300 [0, 24625, 0, 1600006, 1600005, 1600005] s=[标题, '', '使用対象を', '選択して下さい']`，
   `24625 = 0x6031` ⇒ num=1 / strc=3 / 使能位 (0,1,1) ⇒ arg0 是变量（自己的 CSelf6）、arg1/arg2 是 `s[2]`/`s[3]`。
5. **纯变量路径**：ev6 pc1 `300 [0, 18, 1600000, 1600001, 1600005] s=[标题]`，`18 = 0x12` ⇒ num=2 / strc=1 / 使能位清零，
   唯一的字符串实参是变量 `1600005`，此时 `len(s) = 1` 只有标题。

### §8.6 实现改动（crates/wolf-vm/src/exec.rs）

* `Signal::Call` / `Signal::CallByName` 各加 `strings: Vec<String>`（`Signal` 只在本文件内 match，
  其他 crate 不匹配它）。
* 新常量 `SELF_ARG_STRING_OFFSET = 5`、`SELF_ARG_STRING_BASE = magic::SELF_ARG_BASE + 5`（= 605）、
  `SELF_ARG_STRING_SLOTS = 4`。
* `fn string_arguments(cmd, inst, vars, status) -> Vec<String>`：按 §8.2 逐槽解析，`min(string_count, 4)` 封顶。
  字面量**不做转义展开**——`\cself[..]`、`\.` 之类要留到被调方的 `101`/`150` 才展开，提前展开会二次展开。
* `spawn_child` 在写完数值实参后 `self_vars.set_str(SELF_ARG_STRING_BASE + k, text)`；
  `SelfVars` 本身就是定长 1000 槽（数值 + 字符串各一套），越界忽略，所以不会无限增长。
* `call_arguments` 改成返回 `(Vec<i32>, Vec<String>, Option<i32>)`。

### §8.7 回归测试

  CSelf8 的 44 个读取站点全部在 `150`/`250` 里，且没有任何调用点往 `1_600_008` 送值 ⇒ **CSelf8 在本作是空的**。

* 数值实参上限仍是 `SELF_ARG_BASE + i`（CSelf0..3），超过 4 个的站点本作不存在，未加封顶。

## §9 121/124 二元运算符表纠错（task-26 顺带）

WolfTL `WolfRPG/Command.hpp:51-60` 的注释表把两个运算符写反了：它写 `0x3000 = %`、`0x4000 = ~`。
但 WolfTL **没有任何解码运算符的代码**（grep `0x3000` / `modulo` / `divide` 全无命中），所以那张表从来没人验证过。
数据给出的是：

| kind（arg[3] 高位） | WolfTL 注释 | **实测** | 本作站点 | 铁证 |
| --- | --- | --- | --- | --- |
| `0x0000` | `+` | `+` | 多数 | — |
| `0x1000` | `-` | `-` | 214 | ev48 pc46 `Sys8 = self25 op 8`，若为除法得 3（不合理），减法得 20（等于 Sys8 应为 20） |
| `0x2000` | `*` | `*` | 469 | ev63 全篇 `16*rateX` 几何 |
| `0x3000` | `%` | **`/`** | **438** | ev48 pc30 `Sys116/32` = 1024/32 = **32**（= rateX）；若取模得 0，窗口尺寸全 0 |
| `0x4000` | `~` | **`%`** | **107** | ev48 pc172 `self20 %= 10000` 后 `+= 20000` 重编码道具号；ev94 pc291 `self67 = self60 % 3600` 再 `/60` 秒转分 |
| `0x6000` | 未定义 | `rand(min, max)` | 1,101 | 已在 §3.2 确认，本次不动 |
| `0x5000` / `0x7000` / `0x8000` / `0x9000` | `&` / `\|` / `^` / `<<` | 沿用 | 本作 0 站 | 无法用数据校准 |

补充反证：ev48 的三条旧処理分支里 `Sys23 = Sys8 / 2` 恒成立（12/2=6、24/2=12、30/2=15），
取模会得到 0/0/0，ルビ字号直接消失。

实现（`crates/wolf-vm/src/exec.rs` `fn binary_op`）：`0x3` → `wrapping_div`，`0x4` → `wrapping_rem`，
除零/模零都保留左操作数（与原实现一致）。测试：`binary_operator_table_matches_the_editor`、
`set_variable_divides_where_the_old_table_took_a_remainder`。

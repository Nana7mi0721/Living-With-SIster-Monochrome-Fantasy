
# 可变数据库（CDataBase / SysDatabase / DataBase）运行时规格

> 目标读者：要在 Rust 里重写 `Living With SIster Monochrome Fantasy` 运行时的程序员。
> 本文只讲**数据层与 opcode 250 的寻址语义**。二进制布局的完整字节级规格见 `docs/FORMAT_SPEC.md` 第 6 章；
> opcode 250 的指令编码见 `docs/OPCODE_250.md`。本文是这两者的补充：**它解释「类型号 / 行号 / 列号」这三个整数到底怎么落到文件里的某个格子**。

标记约定：

- **【已验证】** = 用 `work/` 下的探针脚本对真实文件跑通，EOF 精确对齐。
- **【已实测】** = 从真实数据统计出来的数字（脚本见附录 A），但属于经验规律而非格式定义。
- **【未验证】** = 有假设、没跑通，写明了下一步怎么破。

## 0. TL;DR

### 0.1 六条结论

1. **.dat 文件里的类型编号 = 类型在文件中的出现顺序**，文件本身**没有** per-type id 字段（每个类型前是固定分隔符 `FE FF FF FF`）。**【已验证】**
2. 但 opcode 250 的 `arg0`（类型号）**不等于** .dat 的类型索引。全库 2,592 个 250 站点里，按整数直接寻址只有 62.0% 落在正确表上；22.8% 需要靠指令里带的**类型名字符串**纠正；15.2% 没有类型名可用。**【已实测】**
3. 列号同理：只有 25.8% 的站点整数列号与字段名一致；11.0% 需要靠**字段名字符串**纠正；其余 61.0% 没有字段名可依。**【已实测】**
4. 因此寻址的**唯一可靠锚点是配方自带的标签字符串**（`stringArgs[1]` = 类型名，`stringArgs[3]` = 字段名），整数只是 fallback。
5. 三个哨兵值：
   - `row == -1` ⇒ **返回该表行数**（不是读某一行）。全库 29 处，全部紧接 `179 LoopTimes`。**【已验证】**
   - `row < -1` ⇒ 出现在**写**操作上，语义是"清空/复位这个工作表"；出现在读上返回 0。**【已实测】**
   - `column < 0` ⇒ 夹到 0（列是 don't-care 或陈旧值）。**【已实测】**
6. **"row 100" 不是真实行号**。它是"先按整数寻址"读到了**另一张表的同名格子**（CDataBase 类型 3 属性耐性 row 0 col 1 == 100）造成的假象；正确答案是 12。**【已验证】** 详见第 6 章。

### 0.2 给 Rust 实现的 5 条硬性要求

| # | 要求 | 理由 |
|---|---|---|
| R1 | `arg0` 必须**先 magic 求值**再当类型号 | 有 52 个站点把自我变量 1600090 当类型号；另有 4 个 1600040 |
| R2 | 解析顺序必须是 **标签优先 → 整数 fallback**，不能反过来 | 反过来必中 row-100 陷阱（第 6 章），且 CE112 的 `(5,-1,0)` 会拿到 16 而不是 10 |
| R3 | `row == -1` 在读路径上返回 `row_count(resolved_type)` | 29 处循环上界全靠它 |
| R4 | `row` 越界时要 **clamp 到本单位最后一行**而不是报错/返回 0 | 脚本里存在 row 恰好越界一格的站点；列负值夹到 0 |
| R5 | 存档 vardb 的类型号/字段配置直接覆盖到 **同一套** 编号空间 | 存档与 .dat 的 30 个类型、51 个字段、17 行完全一致（第 2.6 节） |

### 0.3 名词对照

| 本文用词 | 代码/文件里的东西 |
|---|---|
| 容器 | `(flags >> 8) & 3`：0 = CDataBase（可变DB），1 = SysDatabase（系统DB），2 = DataBase（通常DB） |
| `arg0` | 250 的第 0 个参数，编辑器里的"类型号"（会漂移） |
| `arg1` | 250 的第 1 个参数，行号（data_id），可为变量、-1、-2 |
| `arg2` | 250 的第 2 个参数，列号（item_id），可为变量、负值 |
| `arg3` | 250 的第 3 个参数，flags（bit8..9 容器，bit12 读写，低位是字段种类/运算） |
| 类型名标签 | 指令串表 `stringArgs[1]` |
| 字段名标签 | 指令串表 `stringArgs[3]` |

## 1. 三个容器与文件布局

### 1.1 .dat 布局（回顾，详细见 FORMAT_SPEC 第 6 章）**【已验证】**

三个文件的共同骨架：

```
offset 0    : 10 字节 magic  00 57 00 00 4F 4C 55 46 4D 00   ("..OLUFM" + 尾 0)
offset 10   : u1  m_version   三个文件都是 0xC2
offset 11   : u4  type_count
offset 15   : type_count 个类型，逐类型：
                u4  FE FF FF FF            类型分隔符（不是 id！）
                u4  data_id_method          见第 2 章
                ??? 仅当 data_id_method == 0x0001D4C0 时多一个 t_str（本作从不出现）
                u4  property_count
                u4  property_id[property_count]   字段定义（1000+ 数值 / 2000+ 字符串）
                u4  row_count
                row_count 行，每行：
                    先 nint 个 s4   （nint = property 中 < 2000 的个数）
                    再 nstr 个 t_str（nstr = property_count - nint）
文件末尾    : 1 字节 0xC2（== m_version）
```

**关键点（这条最容易写错）**：行**不是自描述的**，行内没有 per-row 的整数个数、没有行 id、没有行名。每行的宽度由该类型的 property 列表**静态决定**：先整块 s4 再整块 t_str。谁要是在行首多读一个 u4 当计数，就会一路错位到文件尾。**【已验证】**（第一次就是这么错的，报 `unpack_from requires a buffer of at least 852393 bytes`）

三个文件的实测尺寸与类型数：

| 文件 | 大小 | m_version | type_count | 解析结束位置 | 行数分布 |
|---|---|---|---|---|---|
| CDataBase.dat | 81,832 | 0xC2 | 30 | 81,831 | 见 9.1 |
| DataBase.dat | 94,967 | 0xC2 | 40 | 94,966 | 见 9.1 脚注 |
| SysDatabase.dat | 11,607 | 0xC2 | 28 | 11,606 | 见 9.1 脚注 |

三个文件的解析结束位置都恰好是 `size - 1`（最后一字节是 0xC2）。**【已验证】**

### 1.2 .project：权威的 schema（明文，在 .dat 旁边）**【已验证】**

`BasicData/` 下除了 .dat 还有三个同名 `.project` 文件，**明文未加密**：

| 文件 | 大小 |
|---|---|
| CDataBase.project | 170,977 |
| DataBase.project | 174,721 |
| SysDatabase.project | 35,972 |
| SysDataBaseBasic.project | 2,417 |

布局（三个文件都精确走到 EOF）：

```
u4 type_count
每个类型：
    t_str name                     类型名
    u4    field_count
    field_count 个 t_str field_name
    u4    data_count               行数（== .dat 的 row_count）
    data_count 个 t_str data_name   行名（.dat 里没有行名！这是唯一来源）
    t_str description
    u4    field_type_list_size     实测恒为 100，不是 field_count
    field_type_list_size 个 u1 field_type
    u4 n1 ; n1 个 t_str unknown1
    u4 n2 ; n2 个 (u4 k ; k 个 t_str string_args)      ← 选项列表就在这里
    u4 n3 ; n3 个 (u4 k ; k 个 u4 args)
    u4 n4 ; n4 个 s4 default_value
```

- `t_str` = `u4 长度（含结尾 NUL）+ 内容`，所以每个名字都要去掉结尾的 `\x00`。
- 实测不变量（30 + 40 + 28 个类型全部成立）：`field_type_list_size == 100`，`n1 == n2 == n3 == n4 == field_count`，`field_type[i] == 0` 对所有 `i >= field_count`。**【已验证】**
- **.project 只有 schema，没有数据值**。值在 .dat 里。schema 在 .project，values 在 .dat —— 记住这个分工，否则会以为 .dat 里丢了行名。

`field_type` 的取值：

| 值 | 含义 | 本作实例 |
|---|---|---|
| 0 | 数值 | 绝大多数 |
| 1 | 字符串，且是个**文件名** | CData#0 fi3 `歩行グラフィック画像`（string_args[0] == "CharaChip"）、fi4 顔画像（"Picture"） |
| 2 | **引用**：值是另一张 DB 的行 id | CData#6 `メンバー1..6`（指向 CData#0 的行 = 主人公データID） |
| 3 | **选择项**：`string_args` 是选项列表 | DataBase#11 属性耐性（"500%", "400%" …） |

注意 `field_type` 和 property_id 是**两套独立的编码**：`property_id` 决定"这一列是数值还是字符串"（1000+ / 2000+），`field_type` 决定"编辑器把它当数值框、文件名框、外键还是下拉框"。两者可能不一致（例如 CData#0 的 fi3/fi4 在 property 里是 2003/2004 = 字符串，field_type 是 1，一致）。**【已验证】**

### 1.3 类型 id = 列表位置，没有 per-type id

`FE FF FF FF` 在 30/40/28 个类型前**全部**出现，且其后**没有**任何类型 id 字段。类型 id 就是它在列表里的下标（0 起）。**【已验证】**

行 id 也不是字段：行按顺序存，行的"id"就是它的下标。存档里的 `VariableRow::index` 另外记录，但本作 9 个存档实测 `index == 位置` 全部成立（6,507 行零例外）。**【已实测】**

## 2. data_id_method：类型头的那个 u4

### 2.1 四个取值（来自 `_wolfref/common.ksy` 的 enum，与实测吻合）

| 值 | 名字 | 含义 |
|---|---|---|
| 0 | manual | 行 id 由人工指定，跟别的表无关 |
| 1 | same_as_first_string_data | 行 id 取自**本类型第一个字符串字段**的值 |
| 2 | same_as_preceding_type_data_id | 行 id 继承**上一个类型**的 id 空间 |
| >= 10000 | from_type_in_db | 行 id 来自**另一张表**；数值编码 = `容器 * 10000 + 该容器内的类型下标` |

### 2.2 实测分布 **【已实测】**

| 容器 | method 分布 |
|---|---|
| CDataBase.dat（30 类型） | 0 ×15、1 ×3、2 ×8、20002 ×1、20003 ×1、20004 ×1、30000 ×1 |
| DataBase.dat（40 类型） | 0 ×28、1 ×9、2 ×3 |
| SysDatabase.dat（28 类型） | 0 ×28（全部） |

`0x0001D4C0`（STRING_INDICATOR，即"类型头后多一个 t_str"那个分支）在三个文件里**一次都没出现**，属于实现了但走不到的防御分支。**【已验证】**

### 2.3 from_type_in_db 的分解 **【已验证】**

`容器 * 10000 + 类型下标`，容器编号沿用 `common.ksy` 的定义（**注意不是 flags 的那套 0/1/2**）：

| 编码 | 数值 | 容器 | 目标类型 | 语义自洽性 |
|---|---|---|---|---|
| 20002 | 2*10000+2 | DataBase（2） | #2 アイテム | `┣所持アイテム個数` 的行 = アイテム 的行 ✓ |
| 20003 | 2*10000+3 | DataBase（2） | #3 武器 | `┣所持武器個数` ✓ |
| 20004 | 2*10000+4 | DataBase（2） | #4 防具 | `┗所持防具個数` ✓ |
| 30000 | 3*10000+0 | CDataBase（3） | #0 主人公ステータス | `×主人公一時DB` 是每角色一份 ✓ |

### 2.4 行数**绝不能**由 id 源推导 **【已实测，重要】**

| 类型 | method | 本表行数 | id 源行数 | 是否相等 |
|---|---|---|---|---|
| CData#7 ┣所持アイテム個数 | 20002 → DataBase#2 | 40 | 40 | ✓ |
| CData#8 ┣所持武器個数 | 20003 → DataBase#3 | 10 | 40 | ✗ |
| CData#9 ┗所持防具個数 | 20004 → DataBase#4 | 10 | 40 | ✗ |
| CData#17 ×主人公一時DB | 30000 → CData#0 | 20 | 17 | ✗ |

结论：`data_id_method` 只定义**行 id 的取值范围**（哪些 id 是合法的），行本身是**显式存储**的，可以稀疏、可以比源表少（10 个武器槽 vs 40 个武器定义）、也可以比源表多（20 个临时行 vs 17 个角色）。

> 实现要求：从 .dat 头里读 `row_count`，**不要**去查 id 源。任何"用源表行数校验/推导"的代码都会在类型 8/9/17 上崩。

### 2.5 存档 vardb 的编码与 .dat 不同

存档里的可变数据库段（`VariableDatabase`）用**另一套头编码**：

```
unknown = s4 头字 u
  u >= 0  ⇒ 等价 manual，field_count = u
  u == -1 ⇒ 等价 same_as_first_string_data，随后 u4 field_count
  u <= -2 ⇒ 随后 s4 dis（真正的 data_id_method）+ u4 field_count
然后 field_count 个 u4 property_id
然后 u4 row_count
每行：先全部数值 s4（property_id < 2000 的，按 config 顺序），再全部字符串 t_str（>= 2000 的）
```

本作 9 个存档 × 30 个类型**全部**是 `u == -2` 形式，第二个 s4 与 .dat 的 method **逐类型完全一致**（含 20002/20003/20004/30000）。**【已验证】**

### 2.6 结论：**不存在独立的运行时编号空间** **【已验证】**

同一份 .dat 的 30 个类型、51/100/… 个字段、17/16/… 行，在 9 个存档里 byte-identical（配置列表逐 u4 相同）。所以：

- 存档里的 `type_index` 就是 .dat 的类型下标，不需要映射表；
- 存档里的 `row.index` 就是 .dat 的行的下标；
- 唯一需要映射的是**指令里的 arg0 → .dat 类型下标**（第 3 章）。

## 3. 类型号漂移（arg0 ≠ 文件类型下标）

### 3.1 实测解析率（2,592 个 250 站点）**【已实测】**

| 维度 | 整数正确 | 标签纠正 | 无标签可用 |
|---|---|---|---|
| 类型 | 1,606 (62.0%) | 591 (22.8%) | 395 (15.2%) |
| 列 | 670 (25.8%) | 285 (11.0%) | 1,581 (61.0%) |

共有 **770 个站点**的地址会被标签纠正。其中只有 12 个的 row 是字面量（其余 row 是 magic 变量，静态无法比较），而这 12 个里有 **9 个**落到**不同的值**上，全部是决定性的：

| 站点 | 整数地址 | 标签纠正后 | 整数答案 | 正确值 |
|---|---|---|---|---|
| CE88 pc222 | (CData, 3, 0, 0) | (CData, 6, 0, 0) | 100 | 0 |
| **CE105 pc9** | **(CData, 3, 0, 1)** | **(CData, 6, 0, 1)** | **100** | **12** |
| CE105 pc12 / pc15 / pc20 / pc23 / pc26 | (CData, 3, 0, 2..6) | (CData, 6, 0, 2..6) | 100 | -1（空槽） |
| CE112 pc21 | (CData, 5, -1, 0) | (CData, 8, -1, 0) | 16 | 10 |
| CE112 pc24 | (CData, 6, -1, 0) | (CData, 9, -1, 0) | 1 | 10 |

前两行合起来就是历史上那个 "row 100" 的全部来源。

### 3.3 同一个 arg0 可以是两张不同的表 **【已验证】**

- CData `arg0=3` 与 `arg0=6` **都**表示 パーティー情報（文件类型 6）：CE105/CE79 用 3 读，CE104 用 6 写。别"修正"任何一个。
- CData `arg0=6` 还表示 所持防具個数（12 个站点，如 CE52/CE99）；CData `arg0=3` 还表示 状態耐性（1 个）。
- Data `arg0=13` 同时是 用語設定（46 站点）和 敵グループ（12 站点）——必须靠标签或列区分。

所以映射表只能是 **(容器, arg0) → 候选集合**，最终选哪个由标签决定。

### 3.4 标签不是可靠的语义来源，但**是可靠的寻址锚点**

同一个 arg0 会带几十种不同的类型名标签（因为编辑器从不回写历史 id），所以不能"从标签反推游戏逻辑"。但反过来——**标签和文件里的字段名/类型名对得上**，这才是它的价值。规范化时要做的替换（实测必需）：

| 原字符 | 归一为 | 说明 |
|---|---|---|
| 尾部 `\x00` | 去掉 | .project 的 t_str 全部带 NUL |
| U+2014 `—` | `-` | 全角破折号，标签里写 `メッセ—ジ` |
| U+2015 `―` | `-` | 同上（两个码点都有出现） |
| U+3000 全角空格 | 半角空格 | |
| 首尾空白 | trim | |

## 6. "row 100" 结案

### 6.1 现象

早期实现里大量 CData 读取的 row 是 **100**，而 CData#0 只有 17 行 ⇒ 全部 unanswered，状态面板画不出来。

### 6.2 根因链 **【已验证】**（Lead 定位，本文用字节复核）

1. CE98 pc26 按名字调 CE105，返回值落到 SV14；
2. CE105 用 **arg0 = 3** + 标签 パーティー情報 + col 1 + 标签 メンバー1；
3. 旧实现**先按整数**寻址：(CDataBase, 类型 **3**, row 0, col 1)；
4. 而 CDataBase 文件类型 **3** 是 **属性耐性**（100 个字段，40 行，row 0 全是 100）：

   ```
   CData#3 row0 ints[:6] = [100, 100, 100, 100, 100, 100]
   ```

   于是 (3, 0, 1) = **100**；
5. CE90 拿到 表示主人公ID = 100，之后所有 [0, 100, col] 的读都越界 ⇒ 全部 unanswered。

### 6.3 正确答案是 12

```
CData#6 row0 = [0, 12, -1, -1, -1, -1, -1]
                 钱  ↑ col1 = メンバー1 = 12
```

⇒ (CDataBase, 6, 0, 1) = 12 = 主人公ステータス 的玩家行。

**100 从来不是"运行时的第 100 行"，它是另一张表 row 0 col 1 的普通数值。** 两个数字差 88，但各自在表里都是合法格子 —— 这就是为什么这个 bug 不会当场崩，只会让画面全空。

### 6.4 真正的 100 是**参数号**：100 = "只重算"

**【已验证】** 这是全库唯一语义合法的 100。

CE70 X[移]パラメータ増減（686 条指令，形参 ['主人公データID', '対象パラメータ', '増減値', 'メッセージ有り?']）：

```
pc6   111 a=[1, 1600001, 100, 5]      if 対象パラメータ >= 100
pc8   注释：再計算　以外で
pc9   111 a=[1, 1600002, 0, 2]
pc11  注释：もし増減が0なら何もしない
…
pc665 111 a=[1, 1600001, 100, 2]      if 対象パラメータ < 100
pc667 注释：一時値再計算
pc668-670 300 调 X[移]一時ステ計算<初期化 / 装備補正 / 状態補正>
```

- 比较对象是 **1600001 = 第 2 个形参（対象パラメータ）**，不是第 1 个（主人公データID）。
- 全库 7 处把 100 当参数号传给参数库：CE7 pc3、CE9 pc38/pc64、CE10 pc9、CE11 pc14、CE12 pc14、CE200 pc81。例如 300 a=[0, 4, 1600000, 100, 0, 0] = 调用 パラメータ増減(角色 = SV0, 参数 = 100, 增减 = 0)。
- 语义：**参数号 0..99 = 真实列号；>= 100 = "不改值，只重算派生值"**。

CE71 X[移]パラメータ取得 给出的参数号 → (容器, 列) 映射（返回值放 SV99）：

| パラメータ | 目标 |
|---|---|
| 22, 23 | CData#0 col 5（HP） |
| 10, 11 | CData#0 col 4（レベル） |
| 20, 21 | CData#0 col 53（現Lvの取得経験値） |
| 30, 31, 32 | CData 类型 21（= ×主人公一時DB，运行 id 21）col 2（攻撃力） |
| 33, 34 | 类型 21 col 4 / col 5（精神攻撃 / 精神防御） |
| — | 防御力 = 类型 21 col 3；敏捷性 = 类型 21 col 6 |

### 6.5 全库没有字面 100 的行/列 **【已验证】**

2,592 个 250 站点里，arg1 == 100 或 arg2 == 100 的站点数 **= 0**。

另有 179 处 opcode 121 SetVariable 把常数 100 写进自我变量（图 id、坐标、计数器等）——那是**运行时的变量值**，静态追不到；从 CE105 / CE79 / CE5 的语义看，合法行号只可能是 0..16。

### 6.6 结论与防重犯

| 错误做法 | 后果 |
|---|---|
| 先按整数寻址，找不到再试标签 | 命中另一张表同址格子，静默返回错值（100 vs 12） |
| 用 arg0 直接做 .dat 数组下标 | 类型 3 ⇄ 6、5 ⇄ 8、6 ⇄ 9、17 ⇄ 18 ⇄ 19 全部错位 |
| 用 arg2 直接做字段下标 | 类型 0 的 60 个运行列里有 9 个超出 51 个字段 |

正确做法是 **R2：标签优先**。

### 7.2 row < -1 ⇒ 复位哨兵（18 处：17 写 + 1 读）**【已实测】**

17 处**写**的 flags 全是 0x10000（bit12 = 0），语义是"清空/复位这个工作表"：

| 站点 | 地址 | 目标表 |
|---|---|---|
| CE82 pc4 | (CData, 16, -2, 47) | × お店一時処理用 |
| CE86 pc9 / CE110 pc11 / CE111 pc11 / CE112 pc12 / CE152 pc6 / CE153 pc11 / CE154 pc11 | (CData, 19, -2, 0) | 万能ウィンドウ一時DB |
| CE157 pc28 | (CData, 14, -2, 6) | ×┣ コマンド処理リスト |
| CE188 pc195 | (CData, 18, -2, 11) | ×┗ お宝リスト（运行 id 18 → 类型 15） |
| CE189 pc16..pc21 | (CData, 10..17, -2, 5) | 战斗 DB 复制链（7 连发） |
| CE191 pc30 | (CData, 22, -2, 0) | 万能ウィンドウ一時DB |

唯一的**读**：CE270 pc34 (Data, 21, -3, -3) flags 0x11200（解析为 26 メッセージウィンドウ種類）。

实现规则：

- 写 + row < -1 ⇒ **不改任何格子**（它同时带 -1 作为 arg4 源值，但目标是整表清空；本作只需保证"不写坏别的格子"）。
- 读 + row < -1 ⇒ 返回 0 / 空串。
- 不要当"最后一行"。db.rs 的 row.min(len-1) 夹取如果作用在 -2 上会读到**倒数第二行**——这是错的；**先判哨兵再夹取**。

### 7.3 负列

26 个站点出现负列，取值集合 {-3, -2, -1}，主要在 arg0 = 10（5 处）、13（5 处）、11（3 处）、12（3 处）。例：

- CE58 pc10 250 [1, 1600000, -1, 69632, 1600011] s=['', ┣ 技能習得Lv]
- CE267 pc24 250 [24, 1600021, -3, 70111, 1600007]

规则：**夹到 0**。

### 7.4 越界 clamp

crates/wolf-game/src/db.rs:455 的写法（沿用即可）：

```rust
let row = row.min(table.rows.len().checked_sub(1)?);
```

代码注释原文的理由：脚本会用负数行当"最后一行"哨兵，而且有时会给出**恰好越界一格**的行号；夹取比 unanswered 安全，因为 unanswered 会让调用方拿到 0 并继续跑错分支。

但**必须先处理 -1 / < -1 哨兵，再夹取**（见 7.2 的坑）。

### 8.2 读路径（顺序不能换）

```rust
fn database(&mut self, op: &DbOp) -> Option<DbValue> {
    let container = Container::from(op.container);
    let row       = op.data_id;              // arg1，已 magic 求值
    if op.direction == DbDirection::Write { return self.database_write(op, container, row); }

    // ① 标签优先解析出 (类型, 列)
    let (db_type, column) = resolve_cell(&self.databases, self.stats, op, container);

    // ② row == -1 ⇒ 返回解析后表的行数，不看列
    if row == -1 {
        let count = self.databases.row_count(container, db_type).unwrap_or(0);
        return Some(DbValue::Num(i32::try_from(count).unwrap_or(i32::MAX)));
    }

    // ③ row < -1 ⇒ 复位哨兵在读路径上返回 0 / 空
    if row < -1 { return Some(DbValue::Num(0)); }

    // ④ 正常取值：引擎 cell 层优先，其次 .dat
    if let Some(value) = lookup_cell(&self.databases, container, db_type, row, column) {
        return Some(value);
    }

    // ⑤ 兜底：记录诊断，返回 None（调用方拿到 0）
    self.note(format!(
        "250 DatabaseAccess: {container:?} ({db_type}, {row}, {column}) flags {:#x} labels {:?}/{:?} unanswered",
        op.flags, op.type_label.as_deref().unwrap_or(""), op.field_label.as_deref().unwrap_or("")
    ));
    None
}
```

### 8.3 写路径

```rust
fn database_write(&mut self, op: &DbOp, container, row) -> Option<DbValue> {
    if row < 0 { /* -1 / -2 都出现在写路径上：都不改格子 */ 
        return None;
    }
    let (db_type, column) = resolve_cell(&self.databases, self.stats, op, container);
    let current = lookup_cell(&self.databases, container, db_type, row, column)
                      .map(|v| v.as_num().unwrap_or(0))
                      .unwrap_or(0);
    let next = combine_cell(op.op, current, op.source.as_ref().and_then(|v| v.as_num()));
    match op.source {
        Some(DbValue::Str(text)) => self.databases.set_text(container, db_type, row, column, text),
        _ => self.databases.set_num(container, db_type, row, column, next),
    }
    None   // 250 的写形态不产生返回值
}
```

- `op.op` 来自 flags 的低位（0 = 覆盖，1 = 加，2 = 乘，……见 docs/OPCODE_250.md）。
- 写操作也**必须**先做标签解析，否则 CE104 写"メンバー1"会写到 属性耐性 里。

### 8.4 标签解析的具体实现

```rust
// crates/wolf-game/src/db.rs:376
pub fn resolve_labels(&self, container, db_type: i32, column: i32,
                      type_label: Option<&str>, field_label: Option<&str>) -> (i32, i32) {
    let mut resolved_type = db_type;
    if let Some(label) = type_label {
        let key = normalise_label(label);
        if let Some(table) = self.table(container) {
            if let Some(t) = table.types.iter().find(|t| t.name == key) {
                resolved_type = t.index as i32;
            }
        }
    }
    let mut resolved_column = column;
    if let Some(label) = field_label {
        let key = normalise_label(label);
        if let Some(table) = self.table(container) {
            if let Some(t) = table.types.get(resolved_type as usize) {
                if let Some(i) = t.fields.iter().position(|f| f.name == key) {
                    resolved_column = i as i32;
                }
            }
        }
    }
    (resolved_type, resolved_column)
}
```

三个约束：

1. **类型名匹配不到就退回整数**（实测 15.2% 的站点没有类型名可用）。
2. **列名匹配是"在解析后的类型里找"**，不是全局找——同一个字段名可能出现在多个类型。
3. `table(Sys)` 返回 None（SysDatabase 没有 .project 的字段名装载）⇒ 容器 1 的列名解析目前是 no-op。实测容器 1 只有 7 个站点、列名标签也只出现 0/1 这种小整数，影响为零。**【已实测】**

标签归一化（db.rs:434）：

```rust
fn normalise_label(label: &str) -> String {
    label.trim_end_matches(char::from(0))
         .replace('—', "-")     // U+2014
         .replace('―', "-")     // U+2015
         .replace('　', " ")    // U+3000
         .trim()
         .to_owned()
}
```

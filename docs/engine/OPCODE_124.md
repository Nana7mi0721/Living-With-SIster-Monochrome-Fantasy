# opcode 124 SetVariableEx（ウディタ「変数操作＋」）语义规格

> 目标：把 **opcode 124 `SetVariableEx`** 的语义写到「Rust 程序员照抄就能实现」的程度。
> 这是当前 M1（标题画面）唯一还看得见的功能缺口：标题跑 200 帧触发 **108 次** 124，全部落到
> 「sub-op not reverse-engineered; value kept」，于是所有依赖它的判断恒假。
> 数据来源：**本作二进制实测**（work/_ce_full.json = 550 公共事件 / work/maps_full.json = 9 张 .mps 的全部事件，
> 合计 **1,045 条 124**，其中公共事件 579 + 地图事件 466）+ 官方编辑器文档 YADOT-WOLF
> （work/_yado_0600.txt，页面更新 2026/06/06，cp932 抓取）+ 数据流交叉验证（work/_probe124_*.py）。
> 置信度标记：**★★★ 已确证**（注释 + 功能必然性双重支撑）、**★★ 高**（多条独立样本自洽）、
> **★ 中**（单点样本 + 结构自洽）、**未定**（列候选与判别方法，不要凭直觉实现）。
> **标「未定」的请走 fallback（返回 0 或保持变量不变）并留一行日志。**

## 0. 结论速览

```
sub-op 分解：sub = (type << 12) | modifier
  0x1000 = type 1 (キャラ)                modifier 0
  0x1200 = type 1 (キャラ)                modifier 0x200  マップズーム反映
  0x2000 = type 2 (位置=画面座標系)        本作 0 次，未实测
  0x3000 = type 3 (その他)                modifier 0
  0x4000 = type 4 (ピクチャ)              modifier 0
  0x4400 = type 4 (ピクチャ)              modifier 0x400  エフェクト補正なし
```

| sub | 含义 | argc | 全库 | 公共事件 | 地图事件 | 置信度 |
|---|---|---|---|---|---|---|
| `0x1000` | 取**角色**属性（坐标 / 朝向 / 画面坐标 / 事件ID …） | 4 | 39 | 37 | 2 | ★★★ |
| `0x1200` | 同上，**画面坐标按マップズーム反映** | 4 | 1 | 1 | 0 | ★★ |
| `0x2000` | 取画面像素坐标处信息（px座標のイベントID 等） | 4 | **0** | 0 | 0 | 未实测 |
| `0x3000` | 取**その他**（地图号 / BGM / 鼠标状态 / 鼠标坐标 / 处理中事件号 …） | **3** | 278 | 174 | 104 | ★★★ |
| `0x4000` | 取**图片(ピクチャ)**属性（XY / 倍率 / 图案 / 光标悬停 / 使用中 …） | 4 | 719 | 359 | 360 | ★★★ |
| `0x4400` | 同上，**ピクチャエフェクト补正なし** | 4 | 8 | 8 | 0 | ★★ |
| 合计 | | | **1,045** | 579 | 466 | |

三条必须先记住的硬结论：

1. **永不阻塞、永不返回栈值。** 124 是纯查询：算出一个 `i64`，直接写进 `args[0]` 指定的存储槽，然后
   `pc += 1`。没有 wait、没有 branch、没有 branch_depth 变化（全库 1,045 条 branch_depth 全为 0）。
2. **只有 5 种 sub 值，且只有 0x3000 是 argc=3。** argc=3 的形状是 `[dst, sub, field]`（没有 object 槽）；
   argc=4 是 `[dst, sub, obj, field]`。实现按 `args.len()` 分派即可，别假设固定 4 槽。
3. **不存在复合赋值。** 1,045 条的 `dst` 高 4 位**全为 0**（`dst >> 28 == 0`），即编辑器里的
   「代入演算子」== `=`、「結果を±999999に収める」== 未勾选。所以实现就是纯覆写；
   若将来遇到高 4 位非 0 的样本，说明 124 用了别的编码，需重新反推（见 §9.5）。

## 1. 参数编码

### 1.1 形状

```
argc = param_count - 1          （既有 loader 已处理；见 docs/FORMAT_SPEC.md §3）

argc == 4:  args = [dst, sub, obj, field]
argc == 3:  args = [dst, sub, field]        // 只有 0x3000 会这样出现（278/278）

dst   : 魔法存储字（magic storage word），高 4 位 = 0
        1600000+n = 自変数 n              （本作 124 的绝大多数目标）
        2000000+n = 通常変数 n
        9000000+n = システム変数 n
        1100000+n = マップイベントの自変数（地图事件侧）
        细节见 docs/OPCODE_SPEC.md §2
sub   : = (type << 12) | modifier，低 8 位恒为 0
obj   : 被查询对象编号，**通常是魔法值**（可以是变量引用，如自変数 1600021 / 1600031 / 1600040）
field : 属性下标，小整数（本作 0..10）
```

### 1.2 obj 必须是「求值后」的对象编号 ★★★

`obj` 不是常量字段，而是和普通数值参数一样要过 magic-value 求值器：

- `0x1000` 的 obj 是**角色 ID**，可以是 `-1/-2/…/-7`（负数哨兵），也可以是 `1600000+n`（自変数里存的事件 ID）。
- `0x4000/0x4400` 的 obj 是**ピクチャ番号**。本作图片号会到 **5 位数**（`12004`、`12500`、
  `3149840` 这类），且大量样本用变量间接给出：
  - ev224 pc322 `124 [self13, 0x4000, 1600031, 8]` —— 图片号存在自変数 self31 里；
  - ev521 全员：`124 [self10, 0x4000, 201..233 / 301.. / 401.. / 501.. / 601.. / 701.., 8]`。
- 因此**不要**用 `(uint8_t)int_args[1]` 这类截断（docs/OPCODE_SPEC.md §5.19 里针对 150 的那句
  对本作是错的，图片号到 5 位数，必须用完整 i32）。这里同理，obj 必须走 `eval_num()`。

### 1.3 目标写入语义

`dst` 是普通数值存储槽，行为与 `121 SetVariable` 的赋值完全一致（**不**做 ±999999 钳制）。
`dst` 指向不可写的槽时，按「静默丢弃 + 一条 warn 日志」处理。

## 3. `0x1000` キャラ（argc=4）

### 3.1 角色指定（obj）

| obj 值 | 目标 | 备注 |
|---|---|---|
| `>= 0` | 该 **マップイベントID** 的角色 | 该事件不存在时：**什么都不发生（连变量都不写）** ★★★ |
| `-1` | 执行中的マップイベント | 若当前是**公共事件**：取「呼び出し元マップイベント」；若没有调用元（自动/并行启动的公共事件）：**所有属性都返回 -1** ★★★ |
| `-2` | 主人公（パーティ先頭） | |
| `-3` … `-7` | 仲間 1 … 5 | |

官方原文（YADOT）：「-2 主人公（パーティの先頭にいるキャラ）/ -3 仲間１ / … / -7 仲間５」；
「マップイベントからコモンイベントを呼び出していない場合は、変数に保存する値が全て「-1」になります」。
「存在しないイベントＩＤの場合は、イベントは実行されず、何も起きません」。

### 3.2 属性（field）

index 空间与新版官方列表前 11 项一致（本作未用 10 之后的项），实测命中 {2,3,5,6,7,10}。

| field | 语义 | 单位 | 本作次数 | 置信度 | 证据 |
|---|---|---|---|---|---|
| 0 | X座標（標準） | マス（整数 tile） | 0 | ★★★（官方） | 官方表第 1 项 |
| 1 | Y座標（標準） | tile | 0 | ★★★ | 同上 |
| 2 | **X座標（精密）** | 0.5 マス = tile×2 | 2 | ★★★ | ev37 pc2 读「-2,2」、ev126 pc103 读同一字段，都存进「直前の座標」再比较，用于判断「是否移动过一格」；官方：精密 = 0.5マス単位 |
| 3 | **Y座標（精密）** | tile×2 | 2 | ★★★ | 同上（ev37 pc3 / ev126 pc104） |
| 4 | 高さ | 像素 | 0 | ★★ | 官方表第 5 项 |
| 5 | **向き** | 1..9（小键盘布局） | 2 | ★★★ | Map002.mps ev3(爆弾) / ev5(接近攻撃) pc3-4：`self3 = 0x1000(-2,5)`；`111 self3 != 8`（8=下）。官方方向表 7 8 9 / 4 ■ 6 / 1 2 3 |
| 6 | **画面X座標（キャラ中央）** | 像素 | 16 | ★★★ | ev212 pc94「表示座標演算」用于算气泡位置；ev270 按 -2..-7 遍历全队 |

## 4. `0x1200` キャラ（マップズーム反映，argc=4）

modifier `0x200` = 「マップズーム反映」。**index 空间与 §3 相同**，只是画面坐标类取值按
当前【マップエフェクト】缩放率换算：

```
画面X(ズーム反映) = zoomX + (画面X_100% - zoomX) * zoom% / 100
画面Y(ズーム反映) = zoomY + (画面Y_100% - zoomY) * zoom% / 100
```

本作只有 1 条：ev270 pc1107 `[1600071, 0x1200, -2, 7]` → 随后 `111 self71 != 0`。
按 §3 的 field 表，7 = 画面Y座標(足下)，故这条 = 「主人公の画面Y座標（ズーム反映）」★★。
实现建议：本作标题画面 zoom == 100%，直接等于 field 7 的值（恒等映射）即可。

## 5. `0x4000` / `0x4400` ピクチャ（argc=4）

### 5.1 属性（field）

实测命中 {0,1,2,3,4,5,8,9,10}；其中 **8 占 588 条 / 9 占 85 条**，是这条 opcode 的绝对主力。

| field | 语义 | 值域 | 本作次数 | 置信度 | 证据 |
|---|---|---|---|---|---|
| 0 | **X座標**（表示位置，含エフェクト補正） | 像素 | 4 | ★★★ | ev224 pc593-601 用 idx0 加 idx2/idx3 拼出 X 边界与 `その他(20)`（鼠标X）比较 |
| 1 | **Y座標** | 像素 | 1 | ★★★ | ev224 pc279-286 用 idx1 拼 Y 区间与 `その他(21)` 比较 |
| 2 | **拡大率(横)** | % | 19 | ★★★ | ev63 pc145 读 `0x4400(pic,2)` → pc147 `self23 = self10` → `150` pc131 arg9；ev94 pc408 同形并送入 pc410 arg9 |
| 3 | **拡大率(縦)** | % | 12 | ★★★ | 与 idx2 成对（19:12）；ev63 pc146 `0x4400(pic,3)` → pc148 `self24 = self11` → `150` pc131 arg17；ev94 pc409 同形并送入 pc410 arg17 |
| 4 | **パターン番号**（現在表示中のコマ） | 0..n | 7 | ★★ | ev412 pc121 `self13 = pic(1110).idx4` → pc122 立刻用 `150 […, arg5=self13, …]` 重画同一张图，即「把当前图案读出来原样写回」，该槽正是 150 的图案/コマ槽 |
| 5 | 未定 | — | 1 | 未定 | SampleMapA#26 pc218 |
| 8 | **マウスカーソル重なってる [1=YES / 0=NO / -1=图片不存在]** | -1/0/1 | **588** | ★★★ | 见 §5.3 |
| 9 | **ピクチャが使用されている [1=YES / 0=NO]** | 0/1 | **85** | ★★★ | 立ち絵瞬き1 pc28/41/54：画眼コマ → `180 [1]` 等帧 → `124 [self50, 0x4000, 90, 9]` → `111 [1, self50, 0, 2]`（若 ==0）→ `150 [2, 92, 0]`（删立绘）→ `172`（结束事件）。语义就是「立绘已不再使用 → 收工删闪烁图」；13 个使用该字段的事件全是渲染/动画类（立ち絵瞬き1/2、文字エフェクト射精、コマンドカットイン、ウィンドウ処理…），没有一个是判鼠标的 |
| 10 | **文字列、表示完了？ [1=完了 / 0=表示中 / -1=未使用或非文字列]** | -1/0/1 | 2 | ★★ | ev270 pc2308 注释「文章の表示が終わっていないなら消す」→ pc2309 `124 [self60, 0x4000, self40, 10]` → pc2310 判断（self40 = 消息窗口图片番号） |

> **字段 2/3 的歧义已关闭（2026-11-21）：返回的是 `150` 的缩放百分比，不是原图像素尺寸。**
> CE63、CE94 都把读出的 2/3 原样写进 `150` 的横向/纵向缩放槽；YADOT 文档也明确把
> 「画像サイズ」和「拡大率」列为两个不同概念。实现不得再用素材宽高替换这两个字段。
>
> `0` 是合法缩放值，不能全局改写成 `100`。只有具体调用点按 `150` 的缩放模式解释它；
> CE216 pc34 的战斗 AP 条把 `1600012`（当前 AP）直接作为长度/缩放，空 AP 时 `0`
> 必须得到空槽。CE63 pc134 的「拡大率0＝標準サイズに合わせる」描述的是该处系统头像
> 缩放设置，不是所有 `150` 的通用规则。

> ⚠ **field 8 的 -1 必须单独处理。** 官方：「ピクチャが存在しない → -1」。本作 588 条里 **539 条**是
> `111 [17, var, 1, 2]`（`var != 1` ⇒ 未悬停就跳过）。若实现把「图片不存在」返回 0，行为正确；
> 返回 -1 同样满足 `!= 1`，也「碰巧」正确 —— 但**千万别**归一成 1 或 true。

### 5.2 `0x4400` = 同 field 空间 + 「エフェクト補正なし」

官方原文：「「｢エフェクト｣補正なしの値を得る」にチェックを入れると、【ピクチャエフェクト】で設定した
補正値を含めない値を取得する事ができます」，例子是 X=160 的图片被エフェクト位移 +100 后，
带补正得 260、不带补正得 160。

⇒ **`0x4400` 的 field 编号与 `0x4000` 相同，只差「是否叠加ピクチャエフェクト」**（不是另一套字段）。
本作 8 条全部用 idx2/idx3（ev63 pc145/146、ev90 pc205/206、ev94 pc410、ev178 pc250 …），
都是「按当前倍率算框 / 算显示位置」的场合 —— 作者特意要「不含补正」的原始值。

实现：本作**0 条 290 Effect 用于图片**，补正恒为空，所以先让 `0x4400 == 0x4000` 即可，
等实现 Effect 再区分。

### 5.3 field 8（悬停）的判定规则

588 次调用分布在 **34 个事件**里，其中 46 处所在事件名直接是
「カーソル重なり判定」「カーソル変更」「カード選択処理」「サブメニュー処理」「戦闘カード選択処理」
「音量調整」「パンツ詳細表示監視」「妹クリック判定（夜」…，
前一条注释常常就是图片番号的说明（`ピクチャ803　リロード！`、`ピクチャ3610　カード1`、`ゴム`、`ティッシュ`），
后面紧跟 `111 [17, …]`「没悬停就跳过」——这是**カーソル当たり判定**，不是「使用中」。

```
输入：pic = 图片番号（求值后），mouse = (mx, my)（画面像素）
1) pic 未使用（不在当前显示列表）        -> -1
2) 取该图片当前的绘制四边形：
   - 普通显示：矩形 (X, Y, X + W*scaleX/100, Y + H*scaleY/100)
   - 角度 != 0 或 自由変形：四个角点组成的四边形（官方：判定范围会「多少広くなる」）
3) mouse 落在四边形内（**含透明像素区域**）-> 1，否则 0
4) 屏幕裁剪：落点在 (0,0)-(1024,576) 之外一律 0（本作 1024×576）
```

开发期可先做简化版（AABB + 忽略旋转），因为本作按钮基本都是未旋转矩形：
`mx >= x && mx < x + w*scale/100 && my >= y && my < y + h*scale/100`。
**M1 标题画面**只要这一条近似正确，「菜单按钮能被点」就成立了。

## 6. 实现伪代码（Rust）

### 6.1 分派骨架

全部 sub 共享「求一个值 → 写进 dst → pc+1」，差别只在取值函数。注意返回值用 `Option<i64>`：
`None` 表示「不写变量」（对应官方「存在しないイベントIDの場合は何も起きない」）。

```
// crates/wolf-vm/src/exec.rs  —— opcode 124
let dst  = cmd.args[0];
let sub  = cmd.args[1];
let val: Option<i64> = match sub {
    0x3000 => {                       // argc == 3
        let field = cmd.args[2];
        other_get(vm, field)
    }
    0x1000 | 0x1200 => {              // argc == 4
        let obj   = vm.eval_num(cmd.args[2]);   // 角色ID：可能是负哨兵，也可能是变量
        let field = cmd.args[3];
        char_get(vm, obj, field, /*zoom=*/ sub == 0x1200)
    }
    0x4000 | 0x4400 => {              // argc == 4
        let pic   = vm.eval_num(cmd.args[2]);   // 图片番号：可能是变量，到 5 位数
        let field = cmd.args[3];
        pic_get(vm, pic, field, /*no_effect=*/ sub == 0x4400)
    }
    _ => {                            // 0x2000 等本作 0 次的 sub
        tracing::warn!("124: sub {sub:#06x} not implemented; variable kept");
        return Ok(());                // 不动变量
    }
};
if let Some(v) = val {
    vm.store_num(dst, v);             // 与 121 的「=」完全同一条写入路径，不钳制
}
vm.pc += 1;
```

### 6.2 `other_get`（0x3000）

```
fn other_get(vm: &mut Vm, field: i64) -> Option<i64> {
    Some(match field {
        0  => vm.map.current_id() as i64,                       // 現在のマップ番号
        1  => vm.audio.current_bgm_id(),                        // 再生中BGM番号（無ければ -1）
        7  => vm.input.mouse_left_state(),                      // 0/1/2
        8  => vm.input.mouse_right_state(),
        9  => vm.input.mouse_middle_state(),
        10 => vm.input.wheel_delta(),                           // ±
        11 => vm.input.event_id_at_mouse(vm),                   // 無ければ -1
        12 => vm.input.event_id_at_mouse_ext(vm),               // 無ければ -1
        18 => vm.interp.running_trigger_event_number(),         // コモンなら +500000，無ければ -1
        20 => vm.input.mouse_x(),                               // 画面px
        21 => vm.input.mouse_y(),
        17 => 0,          // 未定（§9.1），先返回 0 并留日志
        _  => { tracing::debug!("124/0x3000 field {field} unused in this game"); 0 }
    })
}
```

`mouse_*_state()` 的三态必须是：**本帧按下=2 / 按住=1 / 未按=0**（官方原文），
不能只给 bool —— 本作 `111 …== 2` 判断「刚按下」的地方到处都是（ev225 pc55 等），
若恒返回 1 会导致「按住不放会重复触发」或「永远不触发」。

`field 18` 的实现要点：维护一个「当前正在执行的非并行事件编号」栈；
并行协程（run_condition 2/3）查它时若栈空返回 -1；公共事件要 `+500000`
（本作 `111 self10 == 500065` ⇒ 公共事件 65）。

### 6.3 `char_get`（0x1000 / 0x1200）

```
fn char_get(vm: &Vm, obj: i64, field: i64, zoom: bool) -> Option<i64> {
    // 1) 解析出「角色」；解析失败（事件不存在）=> None => 不写变量
    let ch = match obj {
        id if id >= 0     => vm.map.event_by_id(id as u32)?,   // 地图事件
        -1                => vm.interp.current_char_ref()?,     // 実行中イベント；コモンで呼出元無し => 全値 -1
        -2                => vm.party.leader.clone(),
        -3..=-7           => vm.party.member((-obj - 3) as usize)?,
        _                 => return None,
    };
    Some(match field {
        0 => ch.tile_x() as i64,                     // 標準（マス）
        1 => ch.tile_y() as i64,
        2 => ch.precise_x() as i64,                  // 精密 = 0.5マス = 標準*2
        3 => ch.precise_y() as i64,
        4 => ch.height_px() as i64,
        5 => ch.direction() as i64,                  // 1..9
        6 => if zoom { ch.screen_x_zoomed(vm) } else { ch.screen_x() },          // 中央
        7 => if zoom { ch.screen_y_zoomed(vm) } else { ch.screen_y() },          // 足下
        8 => ch.screen_x_zoomed(vm),
        9 => ch.screen_y_zoomed(vm),
        10 => ch.event_id() as i64,                  // 本作ここ = イベントID（新版は 12）
        _ => { tracing::debug!("124/0x1000 field {field} unused"); 0 }
    })
}
```

`screen_x()` = キャラ左右中央の画面X、`screen_y()` = **足下**の画面Y（官方注記）。
ズーム反映版：`zoom_origin + (screen - zoom_origin) * zoom_pct / 100`；
本作タイトル画面の zoom = 100% ⇒ 恒等。

**一个必须做对的细节**：`obj == -1`（実行中イベント）且当前是**没有调用元**的公共事件时，
官方行为是「全属性都写入 -1」，**不是**「不写变量」。所以 `current_char_ref()` 返回 None 时
应当 `Some(-1)`，而「地图事件不存在」才是 `None`。

fn pic_get(vm: &Vm, pic: i64, field: i64, no_effect: bool) -> Option<i64> {

### 6.5 悬停判定 `hit_test`（field 8，588 处调用）

```
fn hit_test(vm: &Vm, p: &Picture) -> bool {
    let (mx, my) = (vm.input.mouse_x(), vm.input.mouse_y());
    if !(0..1024).contains(&mx) || !(0..576).contains(&my) { return false; }  // 屏幕外

    let w = p.src_w * p.scale_x / 100;
    let h = p.src_h * p.scale_y / 100;
    let (x, y) = (p.draw_x(false), p.draw_y(false));

    if p.angle == 0 && !p.free_transform {
        // 简化版：AABB（本作按钮几乎都是未旋转矩形）
        mx >= x && mx < x + w && my >= y && my < y + h
    } else {
        // 旋转/自由変形：四角点内判定（官方：判定範囲は多少広くなる）
        point_in_quad((mx, my), p.corners())
    }
    // 注：透明ピクセルも「重なっている」と判定する（官方注記）。
    //     像素级 alpha 测试不做。
}
```

### 7.3 决定性检验：`0x4000` 的 obj 到底是不是「图片番号」

lead 要的那张「arg2 → 该事件里是否存在同号 150 指令」的对照表，实测结果（work/_probe124_37_picnum.py /
_probe124_38_picnum2.py / _probe124_39_picnum3.py / _probe124_40_picvar.py）：

| 检验 | 分子 / 分母 | 比例 | 解读 |
|---|---|---|---|
| 0x4000 的 obj 是**常量**（`0 <= obj < 100000`） | 675 / 719 | 93.9% | 其余 44 条用变量（如 `1600031`）间接给番号 |
| 常量 obj **在同一事件里**也有同号 150 | 109 / 675 | 16.1% | 低，但见下面两条解释 |
| 常量 obj **在全库任意 150 的图片番号集合里**（691 个番号） | **623 / 675** | **92.3%** | ⇒ obj 就是图片番号 ★★★ |
| 作为对照：0x1000/0x1200 的常量非负 obj 落在图片番号集合 | 0 / 0 | — | 40 条 obj 全是负哨兵，与图片番号空间无关 |
| 150 指令用**变量**当图片番号的条数 | 5711 / 20425 | 28.0% | 所以「同事件常量扫描」天生会漏掉三分之一的画图 |

为什么「同事件」命中率只有 16.1% 而全库有 92.3% —— 两个真实原因，都是**支持**假说的：

1. **窗口管理器读别人画的窗口图。** `ev224 ウィンドウ処理` 里有 **0 条 150**，却有 20 多条
   `0x4000` 读 12001 / 12002 / 12003 / 12005 / 12053 / 12054 / 12061 / 12062 / 15000 / 10001。
   这些窗口图片是**调用方事件**（ev63 X[共]メッセージウィンドウ 等）用
   `150 [3165968, 1600021, …]`（番号在变量里）画出来的，管理器只负责查/改它们的属性 ——
   这正是「读属性」而不是「自己画」的典型形态。
2. **立绘闪烁读的是底图。** `ev236 立ち絵瞬き1` 自己画的是 **92** 号（眼睛闪烁图），
   却读 **90** 号 —— 90 号是别人（ev215/218/220/295/326/421/443）画的**基础立绘**，
   Read field 9 = 「基础立绘还在用吗？不用就收工」。若 0x4000 不是「读图片属性」，
   这条指令毫无意义。

按属性下标的命中分布（常量 obj）：

| field | 命中全库图片番号 | 未命中 | 说明 |
|---|---|---|---|
| 0 / 1 / 2 / 3 | 0 / 0 / 0 / 0 | 4 / 1 / 2 / 1 | 这 8 条读的是「别人画的窗口图」（12002 / 12004 / 12005 / 12053 …），番号确实存在，只是不是本事件画的；另有 `803`（リロード按钮）、`3800-3920`（カード）等 |

| 5 | 1 | 0 | 同上（唯一 1 条） |
| 8 | 555 | 26 | 26 条是 `8008` / `8117`（各 9 次）+ `467`（2 次）+ 零星，都是**用变量番号画出来的**按钮图 |
| 9 | 60 | 18 | 同上，立绘/立绘系 |

**结论**：0x4000 = 读取图片(ピクチャ)属性的假说，**在不依赖官方文档的前提下也被独立证实**
（92.3% 的常量 obj 精确落在全库图片番号集合里，且未被解释的 52 个也是真实的图片番号 ——
只是那几张图是用变量番号画的）。arg3 就是属性下标（field），见 §5.1 的 9 行表。

## 8. M1 标题画面的 108 次 124

### 8.1 为什么会是 108 次

- **标题事件本身（ev42）里没有 124**，它的 210 调用闭包 {42, 549, 14, 132} 里也没有。
- 108 次全部来自 **run_condition = 2/3 的并行公共事件**（每帧都在跑）：主犯是
  `ev224 ウィンドウ処理`（读 12004 / 12005 / 12002 / 1600031 的 field 8 / 0 / 1 / 3）、
  `ev512 / ev41 マウス感知`（0x3000 的 7 / 8 / 9 / 10）、以及 `ev521 アルバム` 系列。
- 所以「108」是**每 200 帧的并行事件流量**，不是「标题画面有 108 个功能点」。
  但因为所有 `111` 判断都读到「没被写入的旧值」，标题按钮的悬停/点击**全部失效**。

### 8.2 最小实现清单（按这个顺序做，做完标题就能点）

1. **`0x4000` field 8**（悬停，588 处）+ **`0x3000` field 7/8/9/10**（鼠标三态 + 滚轮）——
   只这两组就覆盖标题画面几乎全部交互。

### 9.2 已关闭：pic field 2/3 是拡大率

**结论：field 2 = 横向缩放百分比，field 3 = 纵向缩放百分比。**

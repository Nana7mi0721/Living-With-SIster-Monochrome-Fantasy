## 2. `217 時刻表示`：一个"加分钟"的画图协程

### 2.1 调用约定

`217` 不吃命名参数，它的"加多少分钟"从 **Ev Self 组 6 槽 0** 读（magic `1600000`
= `SELF_ARG_BASE = 6 * 100 = 600` 的平铺 self 下标）。调用方一律：

```
210 [500217, 1, <delta>]     ; 事件 217，1 个实参，delta 分钟
```

共 **568 个调用点，分布在 52 个事件**里。delta 直方图（C2）：

```
{1:14, 2:27, 3:8, 4:3, 5:14, 10:186, 15:308, 20:1, 30:2, 60:5}
```

调用最多的是 `452 DLC恋愛曜日処理`(97)、`301 曜日＆修練処理`(63)、`252`(35)、`305 メインシナリオ`(27)。
⇒ **注意**：`start_event(217)` 时 self 组 6 槽 0 是 0，等于"加 0 分钟"，画面只是重画一次。要测增量必须
用 `start_program_with_self(program, bank)` 并把 `bank.set(600, delta)`。

### 2.2 逐条语义（C1，annotate）

```
pc0  103  "日数表示"                                   ; op103 = 注释/标签，不是指令
pc1  111  [17, 2000617, 1, 2]                          ; if var2000617 == 1 → 6211 画 "？天"
pc3  150  6211 "\f[18]？\f[14]天"
pc6  111  [17, 2000493, 1, 2]                          ; elif var2000493 == 1 → 同样 "？天"
pc8  150  6211 "\f[18]？\f[14]天"
pc11 150  6211 "\f[18]\v[160]\f[14]天"                 ; else：天数 = 变量 160

pc16 121  [2000005, 1600000, 0, 256]   ; 分 += self600        （256 = 0x100 复合赋值 +=）
pc17 111  [1, 2000005, 60, 1]          ; if 分 >= 60
pc19 121  [2000004, 1, 0, 256]         ;   时 += 1
pc20 121  [2000005, 60, 0, 512]        ;   分 -= 60           （512 = 0x200）
pc21 111  [1, 2000004, 24, 1]          ; if 时 >= 24
pc23 121  [2000004, 24, 0, 512]        ;   时 -= 24
pc24 121  [2000006, 1, 0, 256]         ;   星期 += 1
pc25 111  [1, 2000006, 7, 1]           ;   if 星期 >= 7
pc27 121  [2000006, 0, 0, 0]           ;     星期 = 0

pc34 111  [18, 2000005, 0, 2, 2000005, 9, 3]           ; case1: 分 == 0 ; case2: 分 <= 9 ; else
pc36 150  6200 "\f[24]\v[4]:\v[5]0"                    ;   23:00 → "23:00"
pc39 150  6200 "\f[24]\v[4]:0\v[5]\n"                  ;   23:05 → "23:05\n"
pc42 150  6200 "\f[24]\v[4]:\v[5]"                     ;   23:10 → "23:10"

pc45 111  [19, 2000006,0,2, 2000006,1,2, 2000006,2,2]  ; 星期 0/1/2
pc48 150  6210 "\c[0]\f[18]周一"                       ;   0 = 周一（\c[0] = 白）
pc51 150  6210 "\f[18]周二"
pc54 150  6210 "\f[18]周三"
pc57 111  [19, 2000006,3,2, 2000006,4,2, 2000006,5,2]  ; 星期 3/4/5
pc59 150  6210 "\f[18]周四"
pc62 121  [2000008, 25, 0, 0]                          ;   4（周五）→ 置周末标志
pc63 150  6210 "\f[18]周五"
pc66 103  "土日"                                       ;   5 分支的注释就叫"土日"
pc67 121  [2000008, 25, 0, 0]                          ;   5（周六）→ 置周末标志
pc68 150  6210 "\c[1]\f[18]周六"                       ;   \c[1] = 蓝
pc71 150  6210 "\c[2]\f[18]周日"                       ;   6 = 周日，\c[2] = 红
pc76 121  [1600000, 0, 0, 0]                           ; 清 self600，避免重复消费
```

### 2.3 三条 ★已实测纠正

**(a) `121` 的 arg[3] 是复合赋值，不是布尔。** `256 = 0x100` 是 `+=`、`512 = 0x200` 是 `-=`
（`docs/OPCODE_SPEC.md:605`，与 `crates/wolf-vm/src/exec.rs:1419` 的实现一致）。所以 pc16 是 **`分 += delta`**
而不是"分 -= delta"——实测 `23:55 + 45 分钟 → 0:40`，时间**变晚**，语义确认。

**(b) 进位是 `if`，不是 `while`。** 这是引擎的真实缺陷，实测两次：

| 输入 | 输出 | 说明 |
|---|---|---|
| `12:00` + 130 分 | `13:70` | 只进位一次：`0+130-60 = 70`，时只 +1 |
| `12:00` + 230 分 | `13:170` | `0+230-60 = 170`，分钟已非法 |
| `23:55` + 10 分 | `0:05` | 正常跨午夜（时 24 → 时 0、星期 +1） |

⇒ **`217` 的正确实现就是照抄单次 `if`**；任何"顺手写成 while 更稳健"的改动都会让同一段剧情的时间与零售不符。
调用点的 delta 最大是 60，60 分钟刚好等于一次进位，所以本作正片不会暴露这个缺陷——但测试里必须钉住它。

**(c) 显示格式的补零与换行怪癖。** 6200 号图片（时钟）：

| 分 | 字符串 | 屏幕 |
|---|---|---|
| `== 0` | `"\f[24]\v[4]:\v[5]0"` | `23:00` |
| `1..=9` | `"\f[24]\v[4]:0\v[5]\n"` | `23:05` **+ 一个尾随换行** |
| 其余 | `"\f[24]\v[4]:\v[5]"` | `23:10` |

**已验证**：小时**不补零**（`03:00` → `"3:00"`）；`1..=9` 分支的尾随 `\n` 是真实数据里就有的，`6200` 的
文本属性会带上它，画出来看不出来（图元内换行且无后续行），但**逐字节比对时必须保留**。

### 2.4 `2000008 = 25` 到底是什么

逐星期实测（清空其他变量后只跑一次 `217`，C4 覆盖）：

| 星期 | 0 一 | 1 二 | 2 三 | 3 四 | 4 五 | 5 六 | 6 日 |
|---|---|---|---|---|---|---|---|
| `2000008` | 0 | 0 | 0 | 0 | **25** | **25** | 0 |

**★已实测纠正**：不是"周六周日 = 25"，而是**周五与周六**置位；pc66 的注释 `土日`（周六/周日）说明它的语义是
"**明天是周末**"。`217` **没有任何清零点**（全库只有 pc62、pc67 两处写 `2000008`），所以它是一个纯置位标志，
由别的子系统负责复位。

## 3. `329 ┗就寝処理`：就寝时把时间推到第二天早上

关键路径（C3）：

```
pc375 111  [1, 2000004, 6, 1]        ; ★ if 时 >= 6
pc377 121  [2000006, 1, 0, 256]      ;   星期 += 1
pc378 111  [1, 2000006, 7, 1]        ;   if 星期 >= 7
pc380 121  [2000006, 0, 0, 0]        ;     星期 = 0
pc385 121  [2000004, 7, 0, 0]        ; 时 = 7
pc386 121  [2000005, 45, 0, 0]       ; 分 = 45
...
pc433 111  [17, 1600000, 1, 2]       ; if 传进来的"是否已处理" == 1
pc435 121  [1600000, 0, 0, 0]        ;   清标志
pc436 210  [500317, 1, 1]            ;   调 317，实参 1
pc439 121  [1600000, 0, 0, 0]        ; else 分支
pc440 210  [500317, 1, 0]            ;   调 317，实参 0
```

**★已实测纠正**：pc375 是 **`时 >= 6`**，不是"时 <= 6"。依据是 `docs/OPCODE_SPEC.md:341` 的运算符表
（`1 = greater_or_equal`），并由行为反证：`03:30` 就寝**星期不变**（还是同一天熬夜），`23:30` 就寝星期 +1
（跨日）。若按 `<= 6` 实现，03:30 就寝会白白多推一天。

`329` 结算是两段式的：先写死 `7:45`，再把控制交给 `317`；`317` 会覆盖成 `8:00` 或 `9:00`，然后自己再调
若干次 `217` 累加分钟（§4）。所以"就寝后几点起床"**不是 `329` 说了算**。

就寝矩阵（C4，23:30 就寝、跑到实例清空）：

| 就寝星期 | 0 一 | 1 二 | 2 三 | 3 四 | 4 五 | 5 六 | 6 日 |
|---|---|---|---|---|---|---|---|
| 醒来星期 | 1 | 2 | 3 | 4 | 5 | 6 | 0 |
| 醒来时刻 | 8:30 | 8:30 | 8:30 | 8:30 | **9:30** | **9:30** | 8:30 |
| `2000008` | 0 | 0 | 0 | 25 | 25 | 0 | 0 |

**已验证**：`2000008` 是"被 `217` 顺手置位"的残留值——周四就寝推到周五 → 25；周五 → 周六 → 25；
周六 → 周日 → 0（周日分支不置位）。它不参与起床时刻决策，只作为"明天是周末"的输出。

## 4. `317 ■■早朝処理`：8:00 / 9:00 的分岔 与 9:30 的真正来源

### 4.1 两条分支

```
pc120 111  [2, 2000006, 5, 1, 2000006, 0, 1]   ; case1: 星期 >= 5 ；case2: 星期 >= 0（恒真）
pc123 121  [2000004, 9, 0, 0]                  ;   case1 → 时 = 9
pc124 121  [2000005, 0, 0, 0]                  ;           分 = 0
...
pc622 121  [2000004, 8, 0, 0]                  ;   case2 → 时 = 8
pc623 121  [2000005, 0, 0, 0]                  ;           分 = 0
```

**已验证**：分岔判的是**加一之后的星期**。反证：`03:30` 就寝时星期不加一，`wd=4` 得到 8:30（4 < 5）；
而 `23:30` 就寝时 `wd=4` 加一到 5，得到 9:30。若判"就寝前的星期 >= 4"，03:30/wd=4 就会错误地变成 9:30。

⇒ 简化表述：**醒来星期 ∈ {周六, 周日} → 9:00 分支，否则 8:00 分支。**

### 4.2 为什么最终是 9:30 而不是 9:00（C5 逐帧轨迹）

`317` 自己会调 `217` 加分钟（共 9 个调用点，全部 delta = 15）。target 场景（`wd=5` 周六、23:30 就寝）实测：

```
frame   76  (23:30 wd=5) -> (7:45 wd=6)    ev329 pc385/pc386 写死 7:45，pc377 星期 +1
frame  176  (7:45 wd=6)  -> (9:00 wd=6)    ev317 pc123/pc124 写 9:00
frame  196  (9:00 wd=6)  -> (9:15 wd=6)    ev317 pc420  op210 [500217, 1, 15]
frame  284  (9:15 wd=6)  -> (9:30 wd=6)    ev317 pc613  op210 [500217, 1, 15]
frame 1396  实例清空，终态 (9:30 wd=6) flag8=0，instructions 8,088，warnings 0
```

**已验证**：`9:30 = 317 写的 9:00 + 两次 delta=15`。这是文档必须钉住的因果链——只写"317 设 9:00"会与屏幕
不符。

### 4.3 屏幕终态（C5）

```
pic 6200 Text "\f[24]9:30"
pic 6210 Text "\c[2]\f[18]周日"
pic 6211 Text "\f[18]1\f[14]天"
```

`6210` 是"周日"，正是"星期 6 = 周日"的独立佐证。

## 7. 一句话结论

游戏内时钟**不是被帧驱动的**：它由常时协程 `217` 按"加分钟"推进（单次进位、`if` 不 `while`），

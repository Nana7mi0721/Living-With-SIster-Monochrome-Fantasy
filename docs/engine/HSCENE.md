⇒ **要「一场 H」从玩法入口开始，最短链是 `ce246 → 333（立绘）+ 346（cutin）`。** 注意 **文字特效（350/351/353/354/357/358）和 367 瞬き 不是被任何事件调用的**——它们的 `run_condition = 2`，属于「常驻自动事件」，由引擎按变量条件挂起（`Game` 的 `auto_events.sync`）。这一条在实现上意味着：**H 场景的文字层不依赖调用链，依赖 run_condition==2 的调度器**（`00b7967` 那次提交做的正是这件事）。

### 1.4 为什么 `run --event <id>` 单跑不出来（**已验证**，C6）

H 事件的第一条指令几乎都是读全局变量（`2000xxx` 段）或写 self 变量，未预设时立刻 `499`/`172` 跳出：

| 命令 | frames_run | instructions | pictures | 说明 |
|---|---:|---:|---:|---|
| `run --event 365` | 1 | 26 | 4 | 唯一能单跑出脸部四层的成员 |
| `run --event 343` | 1 | 23 | 2 | `#2040 cutin_165` 淡入两条后 172 |
| `run --event 354` | 1 | 3 | 0 | 第一条就 172 |
| `run --event 407` | 1 | 5 | 0 | 只有一条 Erase |
| `run --event 333` | 1 | 4 | 0 | `111 [1, 2000458, 1, 2]` 读全局 458，未命中直接跳出 |

⇒ **M3 的验收入口只能是 `--load-save`（中期状态）或 `--map-run`（从头跑地图事件页）**。这不是引擎缺陷，是原作的事件契约。

1. `ATLAS_SIZE` 提到 4096（64 MB RGBA，桌面 GPU 允许），或做多页 atlas + 每帧重绑。

### 5.3 容量预算

一场 s10 场景同屏最多需要（C1 的 live 清单）：整屏层 5（1024x576，各 0.59 Mpx）+ 立绘 1（540x540）+ 脸部 3（540x540）+ 效果/动作 5（540x540）+ 画框 1 + cutin 1（240x160）+ 小按钮/图标 ≈ 12（60x36 ~ 76x36）+ 文本图 17（不计入 atlas）。

```
整屏 5 x 0.590 = 2.95 Mpx
540² 10 x 0.292 = 2.92 Mpx
小图 12 x 0.003 = 0.04 Mpx
────────────────────────────
合计 ≈ 5.91 Mpx  >  2048² = 4.19 Mpx  ⇒ 单页装不下
              <  4096² = 16.8 Mpx  ⇒ 单页 4096 富余很多
```

⇒ **4096 单页就够，不必做多页**。64 MB 显存换掉一整类静默丢失，划算。

### 5.4 风险

1. **atlas 变大后 `Renderer::set_atlas` 的纹理上限**：2048 是「所有适配器都保证能开的尺寸」，4096 在极老的集显上可能失败。做法：先试 4096，失败回退 2048 并打 Warning（而不是沉默）。
2. **整除推断会误判**：`full_w % full_h == 0` 对 1080x540 这种「本来就是整幅图」的尺寸也成立。缓解：只在 `pattern_index > 1` 或 `picture.split == (1,1) && full_w >= 3*full_h` 时启用。
3. ~~`--load-save` 的 split 未复核~~ —— **已由 C17 复核完毕：存档存的是 4x1 / 4x1 / 9x1，正确**。这条风险注销。

### 5.5 明确不做

- 不做 H 场景的**交互推进**（`123` 的真实玩法路径）。M3 只要求「一张能看的图」。
- 不做 `hword` 文字特效的动画（§3.3 的 Move 语义未定，且零售里是停放态）。
- 不做 290 的视觉修复（§3.7 那 552 条是数据流问题，不是渲染问题）。
- 不做 DLC（`445` 的 70 张 `DLC_data`）——它单独就是一个 M4 的量。

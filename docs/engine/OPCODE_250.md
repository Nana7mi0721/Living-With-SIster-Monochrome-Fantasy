### 0.1 给 Rust 实现（crates/wolf-game / crates/wolf-vm）的 5 条硬要求

1. **容器用 `(flags >> 8) & 3` 判**，不要用 bit9 或 bit12。bits89 == 2 时 bit9 恰好为 1（所以
   「bit9 = DataBase」碰巧成立），但 SysDatabase 只置 bit8、bit9 == 0，会漏判。
2. **方向用 bit12 (0x1000) 判**：1 = 读（DB 单元格 → arg4 变量），0 = 写（arg4 → DB 单元格）。
   不要用 bit16（那是「有没有类型名标签」的记账位）。
3. **arg1 必须当魔法数字求值**。当前 `crates/wolf-vm/src/exec.rs:1578` 只对 arg0 和 arg4 调了
   `Magic::decode(...).is_storage()`，arg1 / arg2 原样透传 —— 而实测前 16 热单元格里有 4 个的 arg1
   是 `1600000+` 的自身变量（如 `[19,SV32,0,...]`、`[21,SV0,0,...]`）。
4. **类型 / 列用「标签优先」策略解析**（§6 给伪代码）。用 arg2 当 .dat 字段下标会在 `画像/音声設定`、
   `システム設定`、`状態設定` 等类型上直接读错字段。
5. **op != 0 的写必须实现成单元格算术语义**（加/减/乘/除/余/最大/最小），不能当普通赋值。本作物品、金钱、
   HP 的钳制习惯用法全靠 op6 / op7（见 §3.4）。

## 2. 参数语义总表

| 参数 | 读（bit12=1） | 写（bit12=0） | 运行时是否需要求值 |
|---|---|---|---|
| arg0 | DB 类型号 | DB 类型号 | **需要**（>=1600000 时是自身变量，实测 `[1600090,1600010,29,0x41200,...]`） |
| arg1 | 行 / 记录号 | 行 / 记录号 | **需要**（实测 `[19,SV32,0,0x50000,...]`、`[21,SV0,0,0x50000,...]`） |
| arg2 | 列 / 项目号 | 列 / 项目号 | **需要**（实测 `[2,SV0,SV28,0x10020,...]`） |
| arg3 | 位域（常量） | 位域（常量） | 不需要 |
| arg4 | 目标变量（必须可写） | 源值（字面量 / 变量 / 字符串变量） | **需要** |

【已验证】bit12=1 的 1,781 条里 arg4 **从来不是字面量**（self 1,755 / strvar 23 / var 3）；
bit12=0 的 882 条里字面量 279、负数 23、strvar 21、self 543、无 arg4 16。
—— 「读的目标必须是变量、写的源可以是常量」这条统计本身就独立证明了 bit12 的方向语义。

### 2.1 arg1 / arg2 的负值：两套独立机制，不是「夹到 0」【★已实测纠正】

⚠️ 早先版本这里只写了「-1 / -2 / -3 = 当前行 / 循环当前项 / 最后一项」，并建议
「负行号夹到 0；负列号夹到 0 或 字段数-1」—— **错的**。逐站点复测（550 个公共事件共
2,592 条 `250`，其中负行 47 条、负列 26 条；`work/_pd_84_row2value.py` /
`work/_pd_89_negcol.py`，站点明细见 `docs/BATTLE.md` §2.5）：

| 轴 | 值 | 条数 | 方向 | 语义 |
|---|---|---|---|---|
| arg1 | `-1` | 29 | **全部读**（bit12=1） | **查该类型的行数**（row count 元查询），arg2 don't-care。CE48 pc153 `[0,-1,33,0x11000,SV10]` → SV10=17（主人公ステータス），下一条 `179 [SV10]` 就是循环上界 |
| arg1 | `-2` | 17 | **全部写**（flags 恰 0x10000） | **把该类型行数设为 arg4**（set row count），0 = 整表清空。CE191 pc30 `[22,-2,0,65536,2]` 然后手写 row 0/1；CE157 pc28 `[14,-2,6,65536,0]` 注释『全部消去』 |
| arg1 | `-3` | 1 | 读 | **未验证**：疑似"取该行名字 / 文本列"。CE270 pc34 `[21,-3,-3,0x11200,SV90]`，SV90 随后被当作类型号用 |
| arg2 | `-1` | 4 | 读 | **首个空槽 / 首个可用索引**。CE58 pc10 `[1,1600000,-1,69632,SV11]`，前一条注释『最初に見つかった空欄箇所を記憶する変数』 |
| arg2 | `-2` | 19 | **全部写** | **清空该行全部字段**。CE75 pc169 `[5,1600000,-2,65536,0]` 注释『強制全回復』；战斗拷贝一律 `[10..14, row, -2, 65536, SV5]` |
| arg2 | `-3` | 3 | 读 | **未验证**：疑似"取该行名字"，与行数 + 循环配合做按名查找（CE265 命中后记住行号；CE267 同形状） |

实现要点（写进 `Game::database()` 的 250 处理器，而不是 `Databases` 的行列寻址层）：

~~~
match (is_write, row) {
    (false, -1) => return Some(row_count(cont, ty) as i32),          // arg2 忽略
    (true,  -2) => { set_row_count(cont, ty, value); return None }, // value = arg4
    (_, r) if r < -2 => return None /* 未验证：0 + 诊断 */,
    _ => {}
}
if !is_write && col == -1 { /* 未实现：首个空槽 */ }
if is_write  && col == -2 { /* 清空该行所有字段 */ }
if col < -3 { /* 未验证 */ }
~~~

⚠️ **负值不能夹到 0**：`row=-2` 夹成 0 会把整表写到 row 0；`row=-1` 夹成 0 会把行数查询
变成"读第 0 行"。两者都不报错，只会静默产出错数据。

### 3.2 bits 8..9 = 容器（决定性证据）【已验证】

取 `(flags >> 8) & 3`，在 **type 标签能唯一命中 (容器, 类型) 的 2,195 条**上交叉列表：

| bits8..9 | 容器 | 条数 |
|---|---|---|
| 0 | **CDataBase** | 1,445 |
| 1 | **SysDatabase** | 3 |
| 2 | **DataBase** | 747 |
| 3 | （保留，本作从不出现） | 0 |

**100% 分离、零例外。** 三条 SysDatabase 的 250 全部是 `flags & 0x300 == 0x100`。

~~~
CE63  pc119 [24,1600049,0,332032,1600008] 332032=0x51100 → bits89=1 → SysDatabase#24 顔グラフィック名
CE267 pc24  [24,-1,0,69888,1600020]       69888 =0x11100 → bits89=1
CE267 pc27  [24,1600021,-3,69888,1600007] 69888 =0x11100 → bits89=1
~~~

⚠️ **不要用 bit9 判**：bits89==2（DataBase）时 bit9 恰为 1，所以「bit9=1 ⇒ DataBase」碰巧成立；
但 bits89==1（SysDatabase）时 bit9==0，会被误判成 CDataBase。
⚠️ **更不要用 bit12 判容器**（早期一度这么写过，是错的）。

### 3.3 bit12 = 读 / 写 方向【已验证】

`flags & 0x1000`：**1 = 读**（DB 单元格 → arg4 变量）；**0 = 写**（arg4 → DB 单元格）。

最小对（除 flags 外五个参数完全一致，事件标题直接写着「変更 / 取得」）：

~~~

CE73 X[移]パラメータ取得(文字列)  pc10 [0,1600000,0,331776,1600005] flags=0x51000 bit12=1 → 读 キャラ名

CE122 X[移]一時ステ計算<初期化>   pc14 [21,1600000,0,327680,1600010] flags=0x50000 → 写 主人公一時DB
CE70  X[移]パラメータ増減        pc23 [21,1600000,0,331776,1600010] flags=0x51000 → 读 主人公一時DB

CE37  ◇ランダムエンカウント処理
      pc20 [18,65,0,65552,1600010] flags=0x10010 → 写（遇敌计数 += 1）
      pc21 [18,65,0,69632,1600023] flags=0x11000 → 读（读进自身变量 23）
      pc22 111 比较 1600023 与 100000
      pc26 [18,65,0,65536,1600023] flags=0x10000 → 写回（清零）

佐证（全量 2,663 条）：bit12=1 一侧 arg4 从不出现字面量（读的目标必须可写）；bit12=0 一侧字面量 279 条。

### 3.4 bits 4..6 = 计算方法（op）【0/1/2/6/7 已实测 · 3/4/5 高置信推断】

`op = (flags >> 4) & 7`，取值 0..7 全部出现过：

| op | 条数 | 语义 | 置信度 | 证据 |
|---|---|---|---|---|
| 0 | 2,316 | **代入**（方向由 bit12 决定） | 【已验证】 | 占 87%，读/写两侧都有 |
| 1 | 205 | **加算**：cell ±= arg4 | 【已实测】 | CE50「アイテム増減」pc30；CE53「所持金増減」pc5；CE70「パラメータ増減」 |
| 2 | 22 | **减算** | 【已实测】 | CE76 pc94，注释「残り2ターン以上なら1減らす」、arg4=1 |
| 3 | 25 | **乘算** | 【高置信推断】 | CE124 pc37 / pc41（MaxHP·MaxSP 乘百分比），CE119 pc254（技能攻撃力影響度） |
| 4 | 5 | **除算** | 【高置信推断】 | CE124 pc38 / pc42 紧跟 op3 之后 ÷100，把百分比还原 |
| 5 | 5 | **余算**（取模） | 【高置信推断】 | CE132 pc189 op1(+1) → pc190 op5(2) = 0/1 翻转开关 |
| 6 | 59 | **最大值**（cell = max(cell, arg4)） | 【已实测】 | 全部配注释「0個以上、最大所持数以下になるように調整」后跟 arg4=0 |
| 7 | 26 | **最小值**（cell = min(cell, arg4)） | 【已实测】 | CE50 pc33 arg4=最大所持数；CE53 pc8 arg4=999999 |

#### 本作的核心习惯用法：三指令钳制【已实测】

~~~
CE50 X[共]アイテム増減（武器/防具 CE51/CE52 完全相同形状）
  pc30  250 [4,SV0,0,0x10010,SV1]     op1  個数 += 增量
  pc31  103 ## 0個以上、最大所持数以下になるように調整
  pc32  250 [4,SV0,0,0x10060,0]       op6  個数 = max(個数, 0)
  pc33  250 [4,SV0,0,0x10070,SV10]    op7  個数 = min(個数, 最大所持数)
  pc35  250 [4,SV0,0,0x11020,SV99]    op2  個数 -= 1（扣掉本次消耗）

CE53 X[共]所持金増減
  pc5   250 [6,0,0,0x50010,SV0]      op1  所持金 += 增量
  pc7   250 [6,0,0,0x50060,0]        op6  钳到 >= 0
  pc8   250 [6,0,0,0x50070,999999]   op7  钳到 <= 999999
~~~

⇒ **Rust 实现必须把这三种 op 实现成「对同一单元格的读改写」**。若按普通赋值处理，
本作购买物品 / 加减金钱 / 加减 HP 会立刻全错（op6 会把格子写成 arg4=0）。

#### op 与方向的关系【已实测】

| op | bit12=1（读） | bit12=0（写） |
|---|---|---|
| 0 | 1,547 + 97（含无 bit16 的 97） | 632 + 40 |
| 1 | 83 + 12 + … | 59 + 32 + … |
| 4 / 5 / 6 / 7 | 0（op4/op5/op6/op7 全在写侧，op3 有 21 条在写侧） | 全部 |

读侧的 op != 0 语义未实测（实测样本都是「读一个百分比进变量」）。**建议实现**：读侧一律按
`dst = cell` 处理（忽略 op），因为本作读侧 op1/op3 的目标变量随后都被 121 重新赋值，
op 的实际效果不可观察。【未验证】

### 3.5 bits 16 / 17 / 18 = 编辑器记账位（运行时无语义）【已验证】

## 6. 解析算法（给 crates/wolf-game 直接用）

### 6.1 主流程伪代码

~~~rust
struct DbRef {
    cont: Container,   // CDataBase | SysDatabase | DataBase
    ty:   usize,       // 容器内类型下标
    row:  i32,
    col:  usize,
    is_write: bool,
    op:   u8,          // 0..7
    string_write: bool // argc == 4
}

fn resolve(cmd: &Command, vars: &mut Vars) -> Option<DbRef> {
    let flags = cmd.arg(3) as u32;

    // 1 容器 bits 8..9  0=CDataBase 1=SysDatabase 2=DataBase
    let cont = match (flags >> 8) & 3 {
        0 => Container::CDataBase,
        1 => Container::SysDatabase,
        2 => Container::DataBase,
        _ => return None,
    };

    // 2 方向与算法
    let is_write = (flags & 0x1000) == 0;
    let op = (flags >> 4) as u8 & 7;
    let string_write = (flags & 0x2) != 0;

    // 3 类型 标签优先 arg0 兜底
    let tlabel = norm(cmd.str(1));
    let ty = if !tlabel.is_empty() {
        match db.find_type_unique(cont, &tlabel) {
            Some(i) => i,
            None => identity_or_clamp(cont, eval_magic(cmd.arg(0), vars)),
        }
    } else {
        identity_or_clamp(cont, eval_magic(cmd.arg(0), vars))
    };

    // 4 行 必须求值
    //    ⚠️ 负值不是行号（§2.1）：-1 = 查行数（读）、-2 = 设行数（写，新行数 = arg4）。
    //    必须原样透传给 Game 层的 250 处理器；clamp 掉会写到错误的行上。
    let row_raw = eval_magic(cmd.arg(1), vars);
    let row = clamp_row(row_raw, db.row_count(cont, ty));   // 仅在 row_raw >= 0 时使用

    // 5 列 标签优先 arg2 兜底
    let flabel = norm(cmd.str(3));
    let col = if !flabel.is_empty() {
        match db.find_field_unique(cont, ty, &flabel) {
            Some(i) => i,
            None => clamp_col(eval_magic(cmd.arg(2), vars), db.field_count(cont, ty)),
        }
    } else {
        clamp_col(eval_magic(cmd.arg(2), vars), db.field_count(cont, ty))
    };

    Some(DbRef { cont, ty, row, col, is_write, op, string_write })
}
~~~

### 6.2 归一化与兜底规则

| 步骤 | 规则 | 理由 |
|---|---|---|
| 标签归一化 | `.replace('\u2014','-').replace('\u2015','-').replace('\u3000',' ')` 再 trim、去尾部 NUL | 数据里同时存在 U+2014 / U+2015 破折号与 U+3000 全角空格 |
| 类型名唯一性 | 三容器里唯一重名的类型只有 属性耐性 (DataBase#11 与 CDataBase#3)，已被容器位分开 | 剩余 2 条歧义可忽略 |

### 6.3 RuntimeDb 设计建议

## 附录 C · 落地记录：标签落库（Lead 追加，已验证）

§6 给出的"标签解析"在 `crates/wolf-game/src/db.rs` 落地为：

```rust
pub fn resolve_labels(&self, container: Container, db_type: i32, column: i32,
                      type_label: Option<&str>, field_label: Option<&str>) -> (i32, i32)
```

* `Databases::load` 顺带读 `DataBase.project` / `CDataBase.project` / `SysDatabase.project`（走法精确到 EOF：174721 / 170977 / 35972 B）。
* 解析顺序：先按**类型名**在表里定位（`Database::type_name`），再在该类型里按**列名**定位（`Database::field_name`）；
  任一步解析不出来就把那一半退回数值 id。`Sys` 容器不参与（它没有 `Database` 表）。
* 读路径先试数值对（99% 的站点数值对就是对的），只在**未命中**时才试标签；写路径直接用标签解析后的格子，
  避免在错的 type 里落下一个野格子。
* 计数：`GameStats::database_labels`（开口 600 帧实测 10 次）。

**为什么必须靠标签**：8 个站点发 `250 [18, 0, 22, ...]`、标签 `システム設定` / `装備可能欄数`，
而实际要取的是 `DataBase` **type 17, col 22 = 5**。编辑器编号把空分隔 type 14 算进去、文件不算，
所以 arg0 会整体漂移；`dbdump --names` 可以直接看到 `type 18` 在文件里是空表（0 列）。
这 8 处是 ev48 pc158、ev85 pc29、ev93 pc38、ev102 pc38、ev109 pc14、ev123 pc15、ev147 pc21、ev185 pc49。

**仍未回答的是行、不是标签**：`CData (0, 100, 0/1/4/21/48/49)` 与 `(0, -1, 33)`。
`CDataBase` type 0 是 51 列 / 17 行 / `data_id_method 1`（行 id 由运行时自动分配），行 100 属于存档里

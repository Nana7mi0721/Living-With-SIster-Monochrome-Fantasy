> 目标：`Living With Sister Monochrome Fantasy`（WOLF RPG Editor v3.x，Steam appid 2429860）
> 数据根：`work/full/`（与用户 `Data/` 同构，本文所有资源路径都相对它）

## 0. 结论速览

### 0.1 七条一句话结论

1. **战斗不是调用栈驱动的，而是"门控变量 + run_condition"驱动的。**
   CE242（1438 slots）与 CE243（1316 slots）是全库 550 个事件里 **0 个静态调用者**的 `call_only` 事件，
   只能被 `condvar` 门控启动。真正的调度器是变量 `2000350` 的三态（0 空闲 / 1 等玩家命令 / 2 执行回合）。
   详见 §1.3。
2. **唯一真正的战斗入口是 CE239 `■戦闘呼び出し`（1108 slots）。**
   它有 **104 个外部调用站点 / 24 个调用者事件**，全部来自菜单类任务事件（討伐依頼 / 地域貢献 / 温泉イベント / DLC），
   没有一个是地图事件。详见 §1.1。
3. **CE188 `X◆戦闘処理`（262 slots）是回合主循环。**
   它调 CE189 初始化 → CE190 布阵 → CE191 收行动内容 → CE194 算行动顺 → CE195 执行一回合 → CE198 收尾，
   循环体在 pc81–126；出口是 pc254 的 `210 [1600030]`（动态跳回调用方）。详见 §1.4。
4. **胜负由脚本自己算，引擎不内置。** CE244 `┗終了判定`（432 slots，22 个调用站点）写
   `2000352`（勝ち負け，1 胜 / -1 败 / -2 第三态）与 `2000343`（戦闘終了）。详见 §1.6。
5. **战斗闭包 = 103 个事件 / 17,071 slots / 14,701 条真实指令 / 30 种 opcode，opcode 层面零缺口。**
   30 种全部已在 `crates/wolf-vm/src/exec.rs` 实现（38 个 match arm）。详见附录 B。
6. **真缺口不在 opcode，在 `250 Database` 的行语义 + 转场绘制 + CLI 入口。**
   负行号共 47 个站点（`-1` = 查行数 ×29 / `-2` = 设行数 ×17 / `-3` = 未验证 ×1）、
   负列号 26 个站点；行号 `100+n`（战斗槽哨兵）会被 `db.rs` 的 `usize::try_from(row)`
   全部变成 `None`；`160/162` 转场未绘制；
   `capture` 子命令没有 common-event 入口。详见 §4。
7. **三阶段切片：A 只读数据视图（CE189）→ B 单回合脚本化（CE188）→ C 可玩战斗。** 详见 §5。

### 0.2 缺什么（一句话）

> **要让战斗"跑起来"只需补三件事**：① `250` 的行哨兵语义（`-1` 查行数 / `-2` 设行数 / `100+n` 运行期槽）；
> ② `160/162` 转场绘制（否则开场是黑屏）；③ 一个能直接启动 common event 的入口（CLI 的 `Entry::CommonEvent`）。
> **不需要**新增任何 opcode、不需要新增任何 DB 容器、不需要重写调度器。

## 1. 事件图

战斗要分三层看：**谁进来**（入口，§1.1）、**引擎怎么把它跑起来**（门控，§1.3）、
**脚本自己怎么走完一回合**（流水线，§1.4–1.6）。三层混在一起看会得出错误结论
（例如把 CE242 当成"没人调用所以是死代码"）。

### 1.2 三层入口（谁把谁拉起来）

```
  [菜单任务事件 24 个 / 104 站点]
            |  210 -> 500239   (code 210, 字面量事件 id)
            v
        CE239 ■戦闘呼び出し   (1108 slots, argn=4)
            |  300 'X◆戦闘処理'
            v
        CE188 X◆戦闘処理      (262 slots, argn=4)  <--- 回合主循环
            |
            +-> 引擎 run_condition 调度（不是调用）
                 2000350 == 1  ->  CE242 ┣コマンド処理  (1438 slots)
                 2000350 == 2  ->  CE243 ┣敵の行動      (1316 slots)
                 2000350 == 2  ->  CE241 ┣ターン開始処理 (635 slots, run=1 auto_start)
                 2000340 == 1  ->  CE240 ┣戦力処理      (47 slots, run=2 parallel)
```

三条边的性质完全不同，实现时不能混：

| 边 | 机制 | 现有实现 |
|---|---|---|
| 任务事件 → CE239 | `210` 字面量 `500239` | `exec.rs:1793` 已支持 `500_000..=599_999 => raw-500_000` |
| CE239 → CE188 | `300` 名字调用 | `exec.rs:1957` 走 `Signal::CallByName` |
| 引擎 → CE240/241/242/243 | `run_condition` + `condvar` 比较 | `auto_events.rs:151 sync()` 边沿触发 + `game.rs:80 ENGINE_AUTO_START` |

### 1.3 门控变量与 run_condition 状态机

战斗家族 74 个事件里，只有 **4 个**不是 `run=0 / condvar=2000000 / condval=0`（纯 call_only）：

| 事件 | 标题 | run | condvar | condval | slots | 调用者 |
|---|---|---|---|---|---|---|
| **240** | `┣戦力処理` | 2 (parallel_process) | 2000340 | 1 | 47 | **0 个静态调用者**（`sync()` 边沿触发） |
| **241** | `┣ターン開始処理` | 1 (auto_start) | 2000350 | 2 | 635 | **0 个静态调用者**（`ENGINE_AUTO_START` 硬编码，每帧都跑） |
| **242** | `┣コマンド処理` | 0 (call_only) | 2000350 | 1 | 1438 | **0 个静态调用者** |
| **243** | `┣敵の行動` | 0 (call_only) | 2000350 | 2 | 1316 | **0 个静态调用者** |
| 239 | `■戦闘呼び出し` | 0 | 2000000 | 0 | 1108 | 104 站点 |
| 188 | `X◆戦闘処理` | 0 | 2000000 | 0 | 262 | 2 站点 |
| 244 | `┗終了判定` | 0 | 2000000 | 0 | 432 | 22 站点 |
| 232 | `ステータス簡易表示` | 0 | 2000035 | 1 | 732 | 533 站点（带条件） |
| 其余 66 个 | — | 0 | 2000000 | 0 | — | 纯 call_only |

**关键反常点**：CE242 与 CE243 是 `run_condition == 0`（call_only），**却在全库 550 个事件里找不到
任何一条 `210`/`211`/`300` 指向它们**（三种解码分别验证：`210` 的 500000/600000 偏移、
`211`、`300` 的名字表）。它们**只靠 `condvar/condval` 被引擎启动**。

**【已验证】** 全库写 `2000350` 的只有 5 个事件：

| 事件 | 站点 | 值 | 时机 |
|---|---|---|---|
| CE239 | pc98 | 0 | 开场复位 |
| CE239 | pc1043 | 0 | 收尾复位 |
| CE241 | pc628 | 0 | 回合开始处理自己清 0 |
| CE242 | pc14 | **1** | 进入"等玩家命令" |
| CE242 | pc208/309/471/556/616/754/944/967/1054/1131/1191/1400/1433 | **2**（13 处） | 玩家命令选定 → 转入"执行回合" |
| CE243 | pc1314 | 2 | 敌方行动完仍停在 2 |
| CE244 | pc312/374/418 | 0 | 判出胜负后清 0 |

写 `2000340` 的：`CE239 pc695 = 1`（启动战力计算）、`CE239 pc1046 = 0`（复位）。

⇒ **状态机（这就是引擎需要提供的那一层）**：

```
              ┌──────────────────────────────────────────────┐
              │  2000350 = 0   空闲（战斗未开始 / 已结束）      │
              │     CE241/242/243 全都不跑                     │
              └───────────────┬──────────────────────────────┘
                              │ CE242 pc14 写 1
                              ▼
              ┌──────────────────────────────────────────────┐
              │  2000350 = 1   等玩家命令                      │
              │     CE242 在跑（run=0 + condvar 2000350==1）    │
              │     CE243 / CE241 停                           │
              └───────────────┬──────────────────────────────┘
                              │ CE242 写 2（13 处）
                              ▼
              ┌──────────────────────────────────────────────┐
              │  2000350 = 2   执行回合                        │
              │     CE243 在跑（condvar 2000350==2）            │
              │     CE241 也在跑（run=1 + condvar 2000350==2）  │
              │     CE241 自己 pc628 写 0 退回空闲              │
              └──────────────────────────────────────────────┘
```

`2000340`（戦闘中）是 CE240 的单独门：CE239 在 pc695 写 1，收尾 pc1046 写 0。
CE240 只有 47 slots，做"战力比"的增量计算（写 `2000192 戦力比味方` / `2000193 戦力比敵`）。

## 6. 验证方法（没有官方运行时怎么证明对）

### 6.1 四条独立的证据链

| 链 | 做什么 | 能证明什么 | 不能证明什么 |
|---|---|---|---|
| **① 脚本级不崩** | `wolf-cli run --event <id> --frames N` | 解释器能吃下这段脚本、没有 panic、指令数单调 | **不能**证明数值对 |
| **② 数值快照对比** | 跑完 dump 全部 `2000000..2000799` 与 `1600000..1600099` 的变量，与手工按脚本推的期望值逐条比 | 变量层语义对 | 不能证明画面 |

| **④ 逐帧录屏对比** | 官方游戏在固定输入序列下 PrintScreen 每 10 帧一张 → Rust 侧同输入同帧号出 PNG → mean abs diff | 画面忠实度 | 需要人肉对帧号 |

**【已验证】** 现有的 M1/M2 已经用过 ③ 和 ④ 的雏形：

`docs/M2_SLICE.md` 记录了标题→新游戏→存档→读档全链。战斗沿用同一套方法。

### 6.2 战斗专用验证命令（**capture 的坑**）

**【已验证】** `capture` 子命令**没有** `Entry::CommonEvent` 分支

所以 `capture --event 239` 会**静默忽略** `--event`，走 `Entry::Boot`
（`game.boot()` + label `"boot map (TitleMap.mps event 2)"`，:1472-1476），
渲染出来是 `Kagura/bg.png + Kagura/inusuku.png` 的厂商 logo（1024×576，非黑像素 17.8%）。

### 6.3 数值快照的具体做法

```
# 1) 跑指定帧数，把变量全量 dump 成 JSON（需要给 wolf-cli 加 dump-vars 子命令）
wolf-cli run --event 188 --frames 500 --dump-vars work/out/vars_b188_500.json

# 2) 手工按 CE188 骨架推期望值（work/_battle_spine.txt 就是推的依据）
#    例：pc36 250 (20, 72, 0, 65536, 1600000) ⇒ 期望 self[1600000] == CDataBase#20 row72 col0
#        pc171 250 (18, 32, 0, 65536, 1)       ⇒ 期望 CDataBase#18 row32 col0 == 1

# 3) diff 两个 JSON（key 排序后逐字段）
```

**为什么这是最可靠的**：脚本是确定性的（没有随机数），同一输入同一帧数必然同一变量状态。
一旦某条 `250` 的读/写语义错了，快照 diff 会精确指到**哪一行哪一列**。

### 6.4 存档往返的具体做法

`docs/vendor/WolfSave` 有 `JsonDumper.h`（321 行）与 `JsonReader.h`（241 行），
是 MIT 的 C++ 参考实现。往返测试：

```
1. 官方游戏存一个档（或用 WolfSave 自带样本）
2. WolfSave.exe --dump save.dat > save.json        # C++ 侧权威 dump
3. Rust: wolf-save 读 save.dat → 内部 struct → 写回 save2.dat
4. WolfSave.exe --dump save2.dat > save2.json
5. diff save.json save2.json                       # 必须完全一致
6. 官方游戏读 save2.dat                            # 必须能正常读档
```

**【已验证】** 存档格式已完全破解（见 docs/SAVE_SPEC.md）：
`seeds=[b[0], b[3], b[9]]`、MSVC rand、从 `0x14` 起按步长 1/2/5 异或、解完 `0x14` 处 = `0x19`、
末字节 = `0x19`、`b[2]` = 校验和、`0x14` 起 `u1=0x19` + `u2 名字长度` + UTF-8 标题 +
`u2 fileVersion=0x8C`、正文从 `0x44` 开始。战斗变量（`2000340..2000598`）在 `vardb` 段里。

### 6.5 逐帧录屏对比的具体做法

```
1. 官方游戏固定输入序列（例：从标题 → 新游戏 → 第 3 个菜单项 → 第 1 个任务 → 战斗）
2. 每 10 帧 PrintScreen 一张，命名 frame_0000.png .. frame_0300.png
3. Rust 侧用同一输入脚本（wolf-cli play 的 --press-frame N / --answer N 已支持）
4. 同帧号出 PNG，算 mean abs diff
5. 阈值：M1 已实测标题画面 0.012，战斗画面因为动画多，**建议阈值放到 0.05**
```

**已知不可比的部分**（必须显式豁免）：

| 项 | 原因 |
|---|---|
| 文字抗锯齿 | 官方用 LOLITA + DxLib 点阵渲染，我们用 glyphon/cosmic-text，字形栅格化必然不同 |
| `290 Effect` 的粒子 | 官方 DxLib 特效与 wgpu 实现不保证逐像素一致 |
| `160/162` 转场的中间帧 | 缓动曲线未知（【未验证】） |
| BGM/SE 时序 | 音频时钟不与渲染帧对齐 |

### 6.6 交叉验证数据层

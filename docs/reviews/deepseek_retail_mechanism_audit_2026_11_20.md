## 1. 「开始咯 / 继续咯」与 Map003 时序

### 1.1 CE42 的真实分支

CE42 的 `102 [19]` 只有三个占位选项，实际行为由 `401` 的索引分派：

| 可见行 | `102` 索引 | `401` 分支 | 实际动作 |
| :--- | ---: | ---: | :--- |
| 开始咯 | 0 | 2 | `180[12]` → `130 [-1,60,34,3,1]` → `Map003` |
| 继续咯 | 1 | 3 | `180[12]` → `210 [500014,1,-1]` → CE14 读档画面 |
| 还是算了 | 2 | 4 | `180[12]` → `175` 结束游戏 |

新游戏分支没有 `210` CE14 调用，没有 `220/221`，也没有按存档存在性改变目标分支。
CE42 只在打开选择窗口前把 `Sys3/Sys4` 设为 `512/1000`，把原生 `102`
窗口放到 576 高屏幕之外；菜单文字实际由 CE43 的图片 3/4/5 提供。

### 1.2 CE43 只是绘制器

CE43 在槽 3/4/5 画 `menu1_b..menu3_b.png`，按 `Sys20` 把对应一行重画为
`menu*_a.png`。它在 `pc27` 执行 `172 BreakEvent`，后面的鼠标检测代码不可达。
因此 CE43 本身没有「图片 3/4/5 到 `401` 分支 2/3/4」的映射；把槽号直接当分支号是错误的。

对当前安装做的一次隔离输入探针显示：菜单出现后直接把指针移到视觉第三行并点击，
实际仍执行当前高亮的第 0 项（新游戏方向），没有打开 CE14，也没有写存档。
这证明至少该次点击不是按 CE43 视觉行热区分派。原版原生 `102` 的完整鼠标/滚轮命中矩阵
仍未穷尽，因此当前 Godot 版本的三行独立热区应视为**移植层的交互重建**，不能宣称
已由脚本数据或本次探针证明为原版逐像素行为。

### 1.3 Map003 的等待精确拆解

Map003 事件 1（`ニューゲーム処理`）的关键槽位：

| pc | 指令 | 是否阻塞 |
| ---: | :--- | :--- |
| 8 | `180[1]` | 1 帧 |
| 9 | 画 `cg/blackscreen.jpg`，30 帧淡入 | 否 |
| 12 | `180[1]` | 1 帧 |
| 13 | 以 20 帧擦除菜单图 3..5 | 否 |
| 14 | 按 `V300` 选图：case1=`V300==1`；case2=`V300==0` | 立即 |
| 16 | case1：`Picture/title01.jpg` → picture -1 | 立即 |
| 19 | case2：`SystemGraphic/TitleGraphic.png` → picture -1 | 立即 |
| 22 | `180[50]` | **50 帧** |
| 24 | 以 30 帧擦除 picture -1..-2 | 否 |
| 26 | `180[50]` | **50 帧** |
| 28 | `130 [-1,62,38,1,1]` → `SampleMapA` | 帧边界传送 |

按 60 Hz 固定逻辑帧计算：

- 两条 `180[50]` 合计 **100 帧 = 1.6667 秒**。
- 加上 `pc12` 的 1 帧，进入传送前的显式等待是 **101 帧 = 1.6833 秒**。
- 若从 `pc8` 起算，则是 **102 帧 = 1.7000 秒**。

30 帧黑幕淡入、20 帧菜单图擦除和 30 帧标题图擦除都与 `180` 并行，不是额外串行等待。
因此“两段各 50 帧”确实是作者脚本节奏；但不应把整段称为恰好 100 帧的完整黑屏，
因为淡入淡出与前后的 1 帧等待也在其中。

### 1.4 复刻版现状

`godot/core_cs/GameSession.cs` 中仍保留 `PickChoice` 的
`title + index==1 + HasSave → 快捷读档` 分支，但这是测试/宿主兼容路径。
交互标题菜单走 `SelectTitleChoice`，直接把索引交给 VM，因此点击“继续咯”会进入
CE42 → CE14，而不是被快捷路径截断。该点与数据行为一致。

## 2. 全新标题封面与四个变量

### 2.1 变量含义与全新值

变量名来自 `SysDatabase` type 14；全新进程未写槽读为 0：

| 变量 | 名称 | 全新值 | 作用 |
| :--- | :--- | ---: | :--- |
| `V300` | `タイトル2` | 0 | TitleMap/Map003 的封面选择；程序数据内无写者 |
| `V499` | `タイトル画面演出` | 0 | CE42 菜单底图覆盖/随机演出结果 |
| `V503` | `温泉イベントクリア` | 0 | 仅当 `V499==0` 时开门到 `TitleGraphic1..5` 随机演出 |
| `V550` | `引き継ぎポイント` | 0 | `>=10` 选 `TitleGraphic6`；`>=2` 才是 NG+ 继承菜单门槛 |

`TitleMap` 用 `221` 分别从 `save/system2.sav`、`save/system.sav` 读取这些系统变量；
缺档在新 VM 初值下仍为 0，因此下列分支不受“缺档返回 0 还是保留旧值”的宿主实现差异影响。

### 2.2 三个画面阶段不是同一张图

| 阶段 | 全新状态实际画面 | Picture 槽 |
| :--- | :--- | ---: |
| TitleMap 确认前 | `Picture/title01.jpg` 加 `SystemFile/Button01.png` 提示条 | 12000 / 12001 |
| 确认后 CE42 菜单 | `SystemGraphic/TitleGraphic.jpg` | -2 |
| 选「开始」后的 Map003 过渡 | `SystemGraphic/TitleGraphic.png`，上面叠加黑幕淡入 | -1 |

CE42 的 `-2` 是实际可见层：确认前它被正号 12000 标题图遮住，12000 用 30 帧淡出后，
`-2` 成为菜单全屏底图。`V499=1..5` 会立即覆盖为 `TitleGraphic1..5.jpg`；
`V550>=10` 只影响未被覆盖时的 `TitleGraphic.jpg` / `TitleGraphic6.jpg` 选择。

Map003 的 case 顺序与 TitleMap 相反：

- TitleMap：`V300==1` → `TitleGraphic.png`；`V300==0` → `title01.jpg`。
- Map003：`V300==1` → `title01.jpg`；`V300==0` → `TitleGraphic.png`。

所以全新状态在确认前看 `title01.jpg`，确认后的菜单看 `TitleGraphic.jpg`，
点「开始」的过渡反而看 `TitleGraphic.png`。不能把其中一个阶段的结论外推到全部阶段。

### 2.3 解锁分支

- `V300` 在全部 `programs.json` 脚本中没有写入者，不是正常的通关/DLC 累计变量；
  只有外部存档、工具或补丁把它置 1，才会切换 TitleMap/Map003 的封面分支。
- `V503` 只由温泉事件相关脚本写为非零，不能让全部六张标题图永久解锁；
  它只在 `V499==0` 时给 CE42 的 20% 随机块开门。
- 当 `V503>=1`、`V499==0` 且随机命中时，CE42 以 4% 的单图概率选
  `TitleGraphic1..5` 之一，并把结果写入 `V499`；否则写 `V499=6`，保留默认底图。
- `V550>=10` 是装饰性标题美术阈值；真正触发继承菜单的是 `V550>=2`，且还受到
  SampleMapA 继承点数的后续换算影响。

## 3. 字体绑定与缺字回退

### 3.1 配置与覆盖

- `Game.dat` 的四个字体槽均为 `LOLITA`，这是 Windows 字体**族名**，不是文件路径。
- 当前安装的根目录与 `Data/` 都带有同一份 `Lolita.ttf`；`Game.exe` 会私有扫描并注册
  `*.ttf`/`*.ttc`，随后 DxLib 按族名创建字体。
- `programs.json` 与 `database.json` 的实际出货文本共有 2702 个 CJK 字符；
  `Lolita.ttf` 缺字 0。GB2312 的 6763 个汉字也缺字 0。

因此，**正常出货文本不会触发任何中文字体回退**。问题中“Lolita 缺简体字”的前提
对当前这版数据不成立。

### 3.2 人为缺字时会发生什么

隔离 GDI 探针用 `Lolita.ttf` 的 `LOLITA` 族名创建字体，结果显示：

- Lolita 有字的码点正常返回字形；
- Lolita 无字的基本区码点返回与未分配码点相同的 `.notdef` 位图；
- 当前系统的 `SystemLink` 没有 Lolita 条目，未观察到自动链接到 SimSun/MS Gothic；
- 07yasashi、GenJyuuGothicXPB、MSGOTHIC 只是被通用 TTF 扫描注册，
  没有出现在 `Game.dat` 的四个槽位，也没有证据被 `AddSubstitutionFontToHandle` 显式加入。

DxLib/WOLF 的字体创建失败回退只处理“整个字体族无法创建”的情况，其后备是默认字体或
MS Gothic 一类系统字体，不是逐字形中文回退。故对语料外字符，当前证据更支持：
**Lolita 缺字 → `.notdef`/方框，而不是自动绑定 07yasashi 或某款简体中文字体**。

### 3.3 对复刻版的含义

`godot/presentation_gd/UiSkin.gd` 现已把 `Data/Lolita.ttf` 放在第一优先级，
系统 CJK 字体仅作为 Godot 缺字回退。这能保持出货文本的字宽和换行；但对玩家名、
输入框、未来新增文本等语料外字符，Godot 会显示系统字形，而原版更可能是方框。
若追求逐字完全一致，应另加“严格模式：缺字显示 tofu”；若优先可玩性，则保留当前系统回退并记录替换字符。

## 4. 旧文档勘误

1. `docs/release/ASSET_AUDIT.md` 曾称 `TitleGraphic1..6.jpg` “会被加载但不会显示”。
   该断言不成立：CE42 的 `-2` 在标题图淡出后可见，`TitleGraphic6` 已在通关后截图
   `010_标题_通关后_三行菜单.png` 中做过像素级强匹配。
2. `docs/milestones/M1_CLOSURE.md` 把 `SystemGraphic/TitleGraphic.png` 称为 WOLF
   示例标题图不准确。320×240 的 WOLF 示例资产是 `SystemFile/TitleGraphic.png`；
   本作的 `SystemGraphic/TitleGraphic.png` 是 1024×576 的 V300 条件分支图，
   且全新 Map003 过渡实际会绘制它。
3. “全新始终显示 `Picture/title01.jpg`”只适用于 TitleMap 确认前；CE42 菜单与 Map003
   过渡会切换成 `TitleGraphic.jpg` / `TitleGraphic.png`。
4. `V503` 不能泛化为 DLC 解锁旗标；它是温泉事件完成标记。

## 5. 残余风险与未决项

1. **构建边界**：当前安装已是中文补丁/DLC 构建，未对纯日文初版做同等级对比；
   本报告不能证明中文补丁安装器没有替换过标题或字体资源。
2. **PE 边界**：`Game.exe` 的静态导入、关键字符串和选定立即数 xref 未发现标题/新游戏钩子，
   但没有完成 `.text` 全量语义反编译，无法绝对排除运行时计算出的通用引擎钩子。
3. **输入边界**：CE43 没有可执行的行点击映射；原版原生 `102` 在鼠标、滚轮、键盘下的完整
   命中矩阵仍需更多输入探针。当前 Godot 的三行热区是重建行为，不应写成已逐项实证。
4. **时序边界**：50 帧结论来自脚本与 60 Hz 固定逻辑帧语义，没有对原版窗口逐帧采样；
   `270[84]`、`201[-2]` 和后续 CE264 的副作用仍需单独核查。
5. **字体边界**：GDI 探针是当前机器、64 位 GDI 环境的结果，不是原版 32 位窗口截图；
   `SystemLink` 随 Windows 版本/语言包变化。Lolita 未登记条目的结论不能保证所有用户环境相同。
6. **路径边界**：脚本混用 `save/system.sav` 与 `Save/System.sav`；Windows 不区分大小写，
   但大小写敏感文件系统上的移植可能误判“有档/无档”。

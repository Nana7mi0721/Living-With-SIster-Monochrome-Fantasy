# M1 闭包与标题画面验收基准（v2 · 启动链路实测版）

> 目标读者：负责把《Living With Sister Monochrome Fantasy》的标题画面在 Rust 运行时里跑通的人。
> 本文是 **M1 的验收基准**：启动链路的真实入口、三个 splash 的资产与时序、标题画面终态的可像素比对规格、
> 与真实截图的对应关系、以及事件 42 菜单的真实定位和仍未验证项。
> 每个数字都注明由哪条命令产出（§0.2 的命令编号 C1–C9），可逐条复现。
> 标记沿用 docs/FORMAT_SPEC.md 的规范：**已验证** / **未验证** / **★已实测纠正**。

**v2 重写说明（必读）**：v1 把 `common event 42` 当成启动链路，因此把「200 帧末 6 张图 / 10 个 quad / 39 753 指令」
当成了标题画面规格。那是两处错误叠加的产物：(a) 入口错了 —— 真实入口是 `MapData/TitleMap.mps` 的**地图事件 2**，
事件 42 只是链路末端的三选项菜单；(b) 当时的 trace host 把选择支永远答成第 0 项，而 `401 ChoiceCase` 结束后会
顺延进下一个 case，于是「はじめから」把「つづきから」的整条菜单事件也跑了，才产生 3261 条 picture 指令。
两处都已在当前代码修正（见 §1）。**v1 的 §3（200 帧末屏幕）与由它派生的所有数字作废**，其余章节（闭包、150 形态、
资产表、开放问题）仍然有效，本文以引用方式保留。

### 4.4 提示条的亮度因子 = 222/255（C9 已定位，仍未实现）

对 Button01 覆盖的矩形 `x[209..814] y[502..536]`（606×35 = 21 210 px，其中 alpha > 0 的 **10 858** 个）
做**物理模型拟合**（把 alpha 通道显式拆成两项，而不是拿一个标量去回归）：

```
real ≈ c1*(alpha*ink) + c2*((1-alpha)*bg) + c3
   c1 = 0.87076   (= 222.045/255)
   c2 = 1.00015
   c3 = -0.042
   残差 mean 0.000 / std 0.219 / max 0.53
```

- **c1 = 222/255、c2 = 1、c3 = 0** ⇒ 真实像素就是「源色乘 222/255 后按原 alpha 合成到底图上」。
  逐整数扫一遍更清楚（同一模型只改因子）：

  | 因子 f | 残差 mean | 残差 max |
  |---|---|---|
  | 221/255 | 0.256 | 1.27 |
  | **222/255** | **0.075** | **0.53** |
  | 223/255 | 0.262 | 1.25 |

- **c2 = 1.00015 是关键**：底图项的权重**没有被削弱**。如果这是「图片不透明度 = 222」，混合会变成
  `a'*ink + (1-a')*bg`（`a' = a*222/255`），底图项权重会掉到 `(1-a')`、拟合出的 c2 就不是 1。
  ⇒ **这是「乘在源色上的亮度/颜色因子」，不是 alpha 意义上的 opacity**，与 `150` 的 OPACITY 字段（=255）无关。
- 交叉验证（最强证据）：把该因子手动应用到我方出图的提示条矩形上，
  与真实 `ScreenShot_..._35.png` 的 **>24 差异从 4 470（0.758%）降到 0（0.000%），max 1.0、meanabs 0.0065**。
  ⇒ 我方渲染器除了这一个因子以外，**已经逐像素等于真实游戏**。

**这个因子从哪来（未定）**：最可能是 `pc91 290[80,30,12001,12001,-50,-50,-50]` ——
`kind = 80>>4 = 5`、`duration = 30`、目标 picture 12001（`args[2]=args[3]=12001`），
后面三个 `-50` 疑为 RGB 偏移/百分比。「乘源色不改 alpha」正好符合一个**亮度/淡入类效果**的形态。
但 222/255 不落在任何整数帧步长上（20 帧：`255*17/20=216`、`255*18/20=229`；30 帧：`255*26/30=221`），
所以它更像一个**固定的合成系数**，或一条尚未测到的曲线上的采样点。
⇒ 仍记为 Q-v2-1；M1 可以先按「提示条出图后乘 222/255」实现，不必等 `290` 语义。

### 4.4b 附：splash 的淡入是 20 帧线性 —— 由像素反解出来

## 6. 事件 42 菜单的真实定位（sys3 / sys4）与 OFFSET

### 6.1 三个写入点

| 位置 | 指令 | 效果 |
|---|---|---|
| `c42 pc111` | `121 [9000003, 512, 0, 0]` | `sys9000003 = 512` |
| `c42 pc112` | `121 [9000004, 1000, 0, 0]` | `sys9000004 = 1000`（**屏幕外的哨兵值**） |
| `TitleMap ev2 pc129` | `121 [9000004, 150, 0, 0]` | `sys9000004 = 150`（可见） |

`pc127/128` 的官方注释就写在这条写入之前：

```
127  103  " "
128  103  "選択肢ウィンドウの表示位置をやや下に移動"      ← 「把选择支窗口往下挪一点」
129  121  [9000004, 150, 0, 0]
```

⇒ **`9000004` 就是选择支窗口的 y，`9000003` 是 x**（x = 512 = 1024/2 = 屏幕水平中心）。

### 6.2 谁最后写：调度顺序

```
TitleMap pc126  210[500042]  → spawn c42，caller 进 WaitState::Child
c42      pc111  sys3 = 512
c42      pc112  sys4 = 1000
c42      pc113  102 Choices  → 子实例阻塞在这里
TitleMap pc127..131  （父流程继续）→ sys4 = 150
```

`210` 是「建子实例 + 父等待」（`exec.rs:1323`），所以**父在子阻塞于 102 之后才继续**，最终值 = `(512, 150)`。
若要复刻，应是「菜单窗口水平居中、顶边（或中心）在 y=150」。

### 6.3 我们现在的行为

- `crates/wolf-game/src/choice.rs` 自己排版：`LINE_HEIGHT 30` / `PADDING 14` / `CHAR_WIDTH 16` / `MIN_WIDTH 120`，
  面板**水平居中**（`layout()`），几何是**推断**的，文件头注释原文：
  「The original game's exact placement is still unknown (open item H-MENU-1 in docs/UNVERIFIED.md)」。
- **代码里没有任何地方读 `9000003`/`9000004`**（`grep -rn 9000003 crates/` 无命中）⇒ 这两个系统变量目前只被写。
- 巧合：C3（`--menu-only --frames 400`）实测面板在 `[452, 229, 120, 120]`，其中 **x = 452 = 512 - 120/2**，
  与「x 居中」自洽；但 **y = 229（垂直居中）≠ 150**。
- C3 里看到的 10 个 quad 与 3 个 text picture 的 picture 号都是 `-100` / `-2`：
  `-100` 是 `main.rs:1299` 里 `choice::overlay` 叠上去的**渲染器自己造的面板**，不是脚本画的；
  `-2` 是 `c42 pc17/pc20` 的 `150`（标题图组），现在能保住负号并命中 `is_screen_layer()`（v1 的 Q3 已修）。

### 6.4 OFFSET 说明（为什么 `--menu-only` 看起来「菜单离屏」）

- 单独跑 `c42` 时没人执行 `pc129`，`sys4` 停在 **1000**（屏幕高 576 之外）。
  如果渲染器老老实实读 `sys4`，菜单就会画在屏幕外 —— 这正是 v1 看到的「`--menu-only` 菜单离屏」。
- 真实链路里 `sys4` 被改成 **150**，所以菜单可见。
- **现在两者没区别，因为我们两边都没读**：`choice.rs` 自己垂直居中。要让 `--menu-only` 与真实一致，
  应实现「菜单布局读 `9000003/9000004`」，且 `9000003` 按中心 x 解释（Q-v2-2）。

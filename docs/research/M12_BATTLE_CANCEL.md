## 1. 结论

M11 task-98 已证明「真实 2 成员菜单确认 → CData type14 → CE157 → CE242」；M12 补上同一菜单的**取消/返回/连续确认**验收：

- 在 CE191（`行動内容のセット`）的窗口按取消，窗口重新打开，**不登记任何指令**；
- 在 CE192（`味方コマンド選択`）的指令窗口按取消，CE192 退出（`self1600099 = -1` 的取消分支），**不写指令行、不启动 CE157**；
- 取消之后继续用确认键操作，菜单仍能登记两条不同指令行并启动两次 CE157。

以上全部由真实 `CE188` 事件链驱动，只使用数据库格子构造 2 人队伍；测试**没有**调用 `set_battle_wiring`、`set_battle_round_loop` 或 `set_battle_menu_command_queue`。**没有生产代码改动**：端口原有的 123 键码层已经能走通这些分支，M12 只是把行为固定下来。

## 2. 菜单的真实分支（数据证据）

调用链（`CommonEvent.dat` 实测标题）：

```

  pc107 300 'X[共]万能ウィンドウ描画処理'   args=[2, 0, 2, 0]

  pc117 1600020 == 10/11 (决定/取消) -> ...
  pc110 1600020 == 12 (サブ)        -> 1600010 = -300

```

CE65 的返回值经 `300` 的返回值目标写回调用者：CE191 收 `1600015`，CE192 收 `1600020`。

| 输入 | CE65 返回 | CE191 行为 | CE192 行为 |
| --- | ---: | --- | --- |
| 决定（有选择） | 选项值 | 进入 CE192 | `pc208` 调 CE157，登记一行 |
| 取消 | −100 | 循环并重开同一窗口 | `pc147` 命中 → `1600099 = -1` → `BreakEvent` |
| サブ / 左右 | −300 | 视为「离开此窗口」，继续到 CE192 | 同样命中取消分支 |

## 3. 测试流程与实测

### 3.1 `cancel_at_the_action_window_reopens_without_registering`

1. `start_event(188)`，交替按决定键直到 CE65 的选择循环（pc78）出现且 CE192 未启动——这是 CE191 的窗口。
2. 断言此时命令表为空、没有 CE157。
3. 按一次取消，随后 60 帧无输入。
4. 断言：窗口重新出现（CE65 存活）、CE192 从未启动、CE157 从未启动、CData type14 没有命令行、`warnings == 0`。

### 3.2 `cancel_in_the_member_command_window_backs_out_and_a_later_confirm_still_registers`

1. 真实菜单推进到 CE192 启动；断言命令表为空。
2. 30 帧无输入：CE192 仍停在窗口等待——证明后面的退出只能来自取消。
3. 在 CE192 的第一个 CE65 选择循环按一次取消；断言 CE192 结束、命令表仍为空、CE157 不存活。
4. 之后交替按决定键，直到出现 2 行；断言：

```
command_rows = [(1, activator 0, ability code 26), (2, activator 1, ability code 25)]
ce157_starts = 2
warnings = 0
```

这两行与 `m11_battle_menu_live.rs` 在无注入下得到的真实菜单行完全一致，说明取消没有污染后续确认。

## 4. 边界

- CE191 的 row1 `-1` 是独立逃跑出口：`pc72` 命中后 `pc74` 写 `1600099=1` 并 `pc75 BreakEvent`，不进入 CE192/CE157。CE192 的 `-100/-300` 只是取消/返回，不要与逃跑混同（C# `BATTLE_ESCAPE_TEST_OK`，§4.39/D-49）。
- 测试驱动的是 opcode 123 的**键码层**（10 决定 / 11 取消 / 12 サブ），也就是 CE65 实际轮询的层。零售的鼠标到键码转换（`125 AutoInput` 等脚本链）不在本验收范围内；现有 `m6_night_menu.rs` 等用真实指针验证的是别的窗口。
- 未覆盖战斗中的目标选择窗口取消、指令窗口左右切换的完整逐项验收；本次只固定了「取消不登记」与「取消后可继续确认」两条边界。
- 没有生产代码改动，因此不改变任何既有战斗路径的字节行为。

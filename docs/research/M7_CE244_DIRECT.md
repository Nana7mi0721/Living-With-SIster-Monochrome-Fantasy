## 结论

- 不需要任何引擎改动。直接调用 Game::start_event(244) 即可让 CE244 完整结算。
- 目标状态 可达：2000352 in {1, -1} 且 2000343 = 1 都能在一帧内得到。
  - 2000354 != 16（含冷启动、11、20、0 等）→ 2000352 = 1（省略/胜利）。
  - 2000354 = 16 → 2000352 = -1（败北）。

- 直接进入 CE244 就是最小可测试 bypass。

## 对照 2000350 循环 bootstrap

- CE244 内没有任何读取 2000350 的指令，只在终点写 0。
- 循环在调用方：只有 CE242 会把 2000350 置 1（docs/research/M7_BATTLE_ROUND.md / docs/HANDOFF_M7.md），而 CE242 自身要求 2000350 == 1；CE188 没有 210 CALL 500244。
- 实测对比：
  - 裸 Game 里预设 2000350=1，同一帧会自动启动一条 event 242 @ pc6 协程（auto-event 调度被解锁），但 2000352 仍由 CE244 写成 1、2000350 归 0；同时多一个 running 协程和一条无关诊断（201 SetMoveRoute: ... no map layer yet）。
  - 裸 Vm（无 auto-event 调度）里预设 2000350=1，CE244 仍结算为胜利并把 2000350 清零 —— 直接证明 CE244 不依赖该 bootstrap。
- 最小 bypass 两种形态：
  1. 直接 start_event(244)（本测试采用，不引入额外协程）；
  2. 先 2000350=1 再走 shipped 调度链（会启动 CE242，代价是多一个运行中的协程）。

## 发现：111 的 value 操作数按字面量比较，导致胜利/失败展示分支恒死

- docs/OPCODE_SPEC.md 5.9 把三元组定义为 [variable(magic), value(s4), operator]，value 是 s4 字面量；crates/wolf-vm/src/exec.rs:2207 实现为 let value = arg(cmd, 2 + 3 * i); 直接与 eval_num 后的左值比较，不对右值再 eval_num。
- pc36 [1, 2000349, 1600010, 2]（2000349 == self 1600010）：只有当 2000349 里恰好写着魔法数 1600010 时才为真。自然状态下 self 变量实际值是 11（被 pc3 写入、2000354=20 路径被 pc6 改成别的），永远不等于字面量 1600010，因此 pc37-53 的战斗结束图片 + InputKey 展示分支在本解释器里是死代码，结算直接从 pc258 落到胜利/省略。
- 即便强行进入（写 2000349=1600010），pc44 [17, 2000192, 2000193, 0]（2000192 > 2000193）的右值 2000193 也按字面量比较：5 > 2000193 恒假，于是总是走 else 的 JumpLabel 敗北 → 2000352=-1。
- 实测：2000349=11 → 2000352=1；2000349=1600010 → 2000352=-1（两者 2000343=1、warnings 0）。
- 这可能是本解释器与原始引擎的语义差异（若原引擎对 rhs 也做 eval_num），但修改 exec.rs 不在本任务写范围内；此处仅记录并加测试锁定行为。若后续修 111 rhs 语义，本测试会失败并提醒重核。

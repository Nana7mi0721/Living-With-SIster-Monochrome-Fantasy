# M9 多人队伍战斗（multi-member party battle）调研与结论

任务：shared task-49（M9 W1 residual）。目标是把战斗接线从"单个行动成员"扩展到真正的
多人队伍循环，而不破坏已交付的单人 day4 路径。

**一句话结论：数据层已经是完整的多成员数据（四个行动点池 2000345/346/347/348，八个
命令各自的成员/技能主体），但"多条命令 / 多个回合"的战斗在出货事件图里根本跑不起来——
每一场普通战斗都在第一个命令回合内被 CE244 结算完毕，加上唯一的回合起点事件 CE241 是
开机只跑一次（`ENGINE_AUTO_START = &[241]`，game.rs:98），所以没有"第二回合"可接。
因此这是一个**数据层 + 结构层 blocker**，不是单纯缺一段接线。引擎侧的最小多回合驱动器
已在 battle_wiring.rs 实现（默认关闭，需 `set_round_loop(true)` 开启；对任何"一回即决"
战斗是 no-op），供未来真正的多回合战斗复用。**

## 1. 数据模型：队伍本来就是 4 人

CE239（■戦闘呼び出し，run=0，1108 条命令）在战斗初始化时写入四个"行动点池"：

| 变量 | CE239 写入点 | 普通战斗初值 | 含义 |
|------|--------------|--------------|------|
| 2000345 | pc546 | 5 | 成员1 行动点 |
| 2000346 | pc554 | 4 | 成员2（カナ）行动点 |
| 2000347 | pc555 | 3 | 成员3（ユイ）行动点 |
| 2000348 | pc556 | 2 | 成员4（カスミ）行动点 |

pc547 的 `IF 2000598 == 1` 分支（pc549-551 把 346/347/348 清零）只服务 DLC——2000598
仅由 DLC 事件 CE452 写（pc5769=1 / pc5772=0），普通 day4 战斗永远走 pc554-556 的四池
分支。**也就是说：即使种子队伍只有 1 人，战斗数据里已经按 4 人准备好四个行动点池。**

CE244（┗終了判定，432 条）的团灭判定 pc378-385 逐一检查这四个池 `<= 0`；任何一个
成员池耗尽都会被统计。这进一步证明数据是 4 人模型。

## 2. CE242 命令分派：`self1600000` 是"命令索引 1..8"，不是"行动成员槽位"

早期 M7/M8 文档把这个形参描述成"行动角色槽位 1..3，其余走 DLC 追加处理"，并说
pc143 把 1/2/3 路由到**同一个**主队主体。这是**错的**。对 CE242（┣コマンド処理，run=0，
1438 条）做块级重解析后，pc143 / pc970 / pc1194 / pc1403 是四个独立的 `111` 分派头，
共 **8 个彼此不同的命令主体**：

| 命令索引 | 分派点 | 主体 pc 范围 | 主体标签 | 消耗的池 |
|:---:|:---:|:---:|---|:---:|
| 1 | pc143 | 145–474 | ユカリ応急処置 / 攻撃（ナルミ | 2000345 |
| 2 | pc143 | 476–760 | スキル（兄 / スキル（ユカリ | 2000345 |
| 3 | pc143 | 761–969 | 攻撃（カナ | 2000346 |
| 4 | pc970 | 972–1056 | スキル（カナ | 2000346 |
| 5 | pc970 | 1057–1133 | スキル（ユイ | 2000347 |
| 6 | pc970 | 1134–1193 | スキル（カスミ | 2000348 |
| 7 | pc1194 | 1196–1402 | スキル（ユイ | 2000347 |
| 8 | pc1403 | 1405–1435 | （显示/防御类通用主体） | 无具名池 |

（命令索引即玩家在命令菜单里选择的"技能/攻击"，实际招式代码存在 2000496；CE239 pc581
在命令阶段之前把它种为 4＝普通攻击。）

CE239 pc711 的原文把设计说得很直白：
「战斗为每回合1次选择角色行动。不断重复，率先夺取全部战力的阵营获胜。」
＝**每回合只选择一个角色的行动，重复，先耗尽全部战力的一方失败。** 所以"多人"是
**跨回合依次让不同成员出手**，而不是在一次 CE242 调用里塞进多个成员。

## 4. 精确 blocker：为什么"多命令 / 多回合"在出货数据里跑不起来

### 4.1 敌方战力槽极小，一击即决
CE239 初始化敌人战力 gauge（2000342）：
- pc180 `2000341 = 1600070 - 1600071`（我方可战 − 敌方攻击），随后夹取；
- pc193 `1600011 = 2000341 / 2`；pc194 `2000341 = 2000028 / 4`；
- **pc195 `2000342 = 2000341 - 1600011 = 2000028 / 8`**（约为队伍战力 1/8）；
- pc202 仅当 `2000445 == 1`（BOSS）才 `2000342 = 2000446`（大值覆盖）。

而一次攻击在 CE242 主体里 `pc287 121[2000342,1600015,0,512]`＝`2000342 -= 1600015`
（伤害 1600015 通常远大于 `2000028/8`）。所以**普通战斗第一击就把敌方 gauge 清零 →
CE244 立即结算**。上面 8 个 cmd 全部 `v343=1 / v352=1`，观察不到第二回合。

### 4.2 回合起点 CE241 是开机只跑一次
`2000350` 的三态：1＝命令阶段（CE242 活），2＝行动阶段（CE243/CE241），0＝空闲。
- `=1` 只由 CE242 pc14 写；
- `=2` 由 CE242 各主体末尾与 CE243 pc1314 写；
- **`2 -> 0` 只由 CE241 pc628 写**（pc629 `self1600050 = 2000349` 回合倒计时显示，pc632 2000477=0）。
- CE241 无任何静态调用者（事件图里没有 210 500241）；它是 `run_condition=1` 的
  `ENGINE_AUTO_START = &[241]`（game.rs:98），注释明确："开机跑一次，pc628 把自己的
  条件变量 350 清零后结束，永不驻留"。

结果：出货流程最多执行**一个**命令回合就停在 2000350=2，CE242 需要 350==1 才能再起，
而没有任何东西把 350 从 2 拉回 0 —— 这正是 `docs/BATTLE.md` §5.3.1 的 self-boot 悖论的
多回合版本。

### 4.3 auto_events 只在 {1,2} 内交替
`crates/wolf-game/src/auto_events.rs`：`GATED_CALL_ONLY = [242, 243]`（条件变量驱动），
CE242 条件 `2000350 == 1`、CE243 条件 `2000350 == 2`。它只会在 1↔2 之间交替两个事件，
**从不把 350 恢复成 0**。回合边界必须由引擎补。

### 4.4 实测"强行多回合"失败
尝试在战斗激活后每帧补 2000342、并压制 2000029/2000215/2000598，仍无法拖出第二回合：
CE244 的胜利在 pc36（`2000349 == 1600010` 阈值块）内由 pc44（`2000192 > 2000193`）触发，
而 CE240 每帧用共享暂存 1600010/1600011 覆盖这些量，逐帧的变量补丁无法截住 VM 单步内的
写入。结论：靠种子变量伪造多回合是死路。

## 5. 引擎侧改造（crates/wolf-game/src/battle_wiring.rs）

在原有单发接线基础上扩展了一个**诚实的**多回合驱动器：

- 新增 `round_loop`（`new()` 默认 **false**＝单发；`set_round_loop(true)` 才启用多回合；
  且对"一回即决"战斗恒为 no-op）、`command_schedule`（默认 `[1, 3]`）、`command_cursor`、
  `turn_starts`。
- `tick()` 除保留默认单发（`set_round_loop(false)`）行为外，round-loop 分支：
  1. 340 上升沿且 350==0、无 241/242/243 存活 → 用下一个命令索引启动 CE242；
  2. 350==2 且无回合事件存活 → 启动**真实 CE241**（pc628 把 350 归 0）；
  3. 350==0 且无回合事件存活且已跑过 → 用下一个命令索引启动下一个 CE242。
- 诚实契约：不硬编码 350=1/0（只启动脚本，由 CE242/CE241 自己按原始逻辑写 350）；
  不伪造菜单输入（招式已在 2000496）；不种 2000352/2000343（它们是 CE244 的结算输出）。

验证：默认（round_loop=false）下，含 `m7_battle_target_scheduler` 在内的一切既有回归
保持原行为；本测试 `single_shot_wiring_settles_in_one_command_round` 断言一场真实战斗仍然
只跑一个命令回合并正常结算（`rounds == 1、v352 ∈ {1,-1}、v343 == 1、warnings == 0`），
即默认单发行为不变。多回合驱动器（`set_round_loop(true)`）对单回合战斗为 no-op，需由
后续在 game.rs 加一行 `Game::set_battle_round_loop` 才能从生产入口开启（game.rs 不在本任务
写入范围）。

## 6. 最小修复建议（若要真正实现多回合战斗）

不建议硬编码。按"最小且忠于数据"的顺序：

1. **数据/关卡侧**：让多回合战斗由 BOSS 路径触发（CE239 pc202 `2000445==1` 把敌方 gauge
   设成 2000446 的大值），这样第一击不清零、CE244 在首回合不结算，回合循环才有对象。
   这是不改引擎、最贴近原设计（"先耗尽全部战力"才分胜负）的路径。
2. **引擎侧**：维持本文件"每个 350 回到 2 后启动真实 CE241 再启动下一个 CE242"的驱动器
   （已实现），并把玩家逐回合的真实命令索引通过 `set_command_schedule` 从菜单线程传入。
3. **若确实需要 CE241 每回合重入**：由于现状只在开机跑一次，可把 CE241 从
   `ENGINE_AUTO_START` 单发改为"每当 350==2 且战斗未决时由 wiring 启动"——这正是本
   wiring round-loop 分支 2 所做的，已经不需要改 game.rs。

以上三条中，1 是"让多回合在真实数据里成立"的必要条件；2/3 已在 battle_wiring.rs 内实现，
无需越界改 game.rs / exec.rs / db.rs。

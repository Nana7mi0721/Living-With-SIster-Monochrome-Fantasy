## 0. 结论速览（TL;DR）

| 项 | 结论 | 置信度 |
|---|---|---|
| 指令码 | 102，argc **恒为 1**，stringArgs 个数 **恒等于选项数** | 【已验证】495/495 |
| args[0] | 低 4 位 = 选项数 n（1..8）；bit4 = **取消不可**；bit5/bit6 各 1 例，含义未知 | 低 4 位【已验证】、bit4【高置信推断】 |
| 执行 | **阻塞**：画出选择窗口，等玩家用方向键/鼠标移动光标、确认/取消后才返回 | 【高置信推断】 |
| 分支 | 401 ChoiceCase 的 args[0] 是 **2..n+1**（不是 1..n！）；421 的 args[0] 恒为 0；选择块内 **没有 420** | 【已验证】495/495 |
| 窗口位置 | 系统变量 **sys3 = X、sys4 = Y**（屏幕绝对像素，左上角）；sys14 = 是否显示（1=ON），本作从不关 | 【已验证】/【高置信推断】 |
| 窗口外观 | SystemFile/WindowBase.png，18×18、3×3 九宫格、每格 6px | 【已验证】 |
| 原版到底画不画窗 | **画**。标题画面看不到是因为它把 sys4 设成 1000（屏幕高 576，坐标在屏幕外） | 【已验证】 |
| 返回值 | 系统变量 **sys20 = 光标当前位置**（确认后 = 选中项下标；取消 = -1） | 【高置信推断】 |

### 0.1 给移植实现的三条硬要求

1. **选项 i（1-based）跳转到「args[0] == i + 1 的那个 401」的下一条指令**。若按 == i 查找，
   整个游戏的每一次选择都会错位一格（选第 1 项执行第 2 项的分支）。详见 §3.3。
2. **必须按 sys3/sys4 画窗口**，并且当窗口矩形完全落在 1024×576 视口外时自然不画
   （标题画面就是这个机制，不需要额外特判）。
3. 取消（Esc / 右键）在 bit4 置位时**必须被忽略**（该块没有 421，取消分支不存在）。

### 1.3 stringArgs = 选项文本（原样，未做任何转义展开）

选项文本可以包含与 101 相同的转义序列，本作实测出现的有：
\cself[n]（自身字符串变量）、\c[n]（颜色）、\f[n]（脸图）、\E。
本作 **没有任何一条**选项使用 \img[...]（全库搜索 0 条），但引擎支持
（work/yado2.txt:546-556）。

真实样例（动态文本最典型的一条）：

```
ev359「■お風呂覗き」pc1684  args=[117]  strings=["继续偷窥      ", "\cself[8]", "\cself[6]", "\cself[5]", "\cself[9]"]
```

它前面的 pc1676-1681 用 122 把 cself8/cself9 拼成「屏住呼吸」/「离开」或空串 —— 这是
WOLF 里做「选项条数固定、内容按状态变化」的标准手法，窗口必须能容纳**缩短到空串**的选项。
【已实测】

## 2. 执行语义

### 2.1 状态机

【高置信推断】（依据：WOLF 引擎性质 + sys20/sys3/sys4 的大量读写 + 本作 79 个「有可读选项但块内
没有任何 150」的块必须由运行时绘制）

1. **进入**：若 sys14 != 0（默认 1=ON），按 sys3/sys4 画选择窗口，逐项绘制 stringArgs；
   把光标放到 sys7（選択肢次回初期位置，本作从不写）或 0。
2. **阻塞**：本命令**不推进指令指针**，直到玩家确认或取消。解释器在该事件上挂起
   （本作 108 个 parallel_process 自动事件仍继续跑，见 docs/OPCODE_SPEC.md 的协程模型）。
3. **输入**：↑↓ 移动光标（sys15/sys16 方向键重复间隔）；确认 = sys17 的 SE，移动 = sys18，
   取消 = sys19（本作分别设为 0/1/2，见 ev48 pc112-114）。鼠标输入受 sys73 控制
   （本作设置过：work/_yado_0610.txt:280）。
4. **返回**：
   - 确认第 i 项（1-based）⇒ 指令指针跳到 401(args[0] == i+1) 的下一条；
     若 i = n 则跳到最后一个 401 之后（因为 n 项只发 n 个 401：2..n+1，见 §3）。
   - 取消 ⇒ 跳到 421 的下一条；若该块没有 421（bit4 置位）⇒ **取消被吞掉，不返回**。
   - sys20（選択肢カーソル現位置）随之更新：确认后 = 选中下标，取消后 = -1。
5. **收尾**：所有分支最后汇合到 499 BranchEnd（缩进回到 102 的层）。

### 2.2 与 101 Message 的关系

【未验证】WOLF 的 102 执行时通常先等待当前消息窗口的显示完成（101 的"等待点击"部分）。
本作大量块是「101 提示语 → 102 选项」，若移植版不等待，选项窗口会盖在还在打字的文本上。
建议实现里让 102 开头调用一次 flush_message()。

## 3. 分支结构：401 / 420 / 421 / 499

### 3.1 实测骨架（【已验证】，ev245 pc470）

```
pc470  102  bd3  a=[2]         s=["硬来", "算了"]      ← args[0]=2 ⇒ n=2，bit4=0 ⇒ 可取消
pc471  401  bd3  a=[2]                                ← 【选项 1】"硬来" 的 body 从这里开始
pc472  ...   bd4  （选项 1 的内容）
pc475  401  bd3  a=[3]                                ← 【选项 2】"算了" 的 body 从这里开始
pc476  ...   bd4
pc480  421  bd3  a=[0]                                ← 【取消分支】body 从这里开始
pc481  ...   bd4
pc485  499  bd3  a=[]                                 ← 结束
```

对 8 个选项的块（ev246 pc1，args=[6]）实测 401 的位置：pc2、pc123、pc226、pc337、pc451、pc556，
args[0] 依次为 2、3、4、5、6、7 —— 严格连续。

### 3.2 全量统计（495 条 102，【已验证】）

对每条 102，从它开始向下扫描同 indent 的 401/420/421，直到同 indent 的 499：

| 检查项 | 结果 |
|---|---|
| 401 的 args[0] 集合 == {2, 3, ..., n+1} | **495 / 495 全部成立** |
| 401 的条数 == n | **495 / 495** |
| 块内出现 420（ElseCase） | **0 / 495**（选择块永远没有 else） |
| 块内出现 421（CancelCase） | 153 条块有；**恰好 == bit4 为 0 的块数（153）** |
| 421 的 args[0] | **恒为 0** |
| 421 的位置 | 恒在**最后一个 401 之后**、499 之前（取消分支是最后一段） |

> 早期探针（work/_probe102_d.py 第一版）曾报告「3 条 bit4=0 但无 421」的例外，
> 那是块边界判定 bug（没有用 indent 配对）。改用 indent 配对后 **153/153 与 342/342 完全干净**，
> 不存在例外。这条修正过的结论请以此为准。

### 3.3 args[0] 的偏移（最容易踩的坑）

**401 的编号从 2 开始，不是 1。** 也就是说：**选项 i（1-based）对应的 401 的 args[0] 是 i+1**。

为什么？从字节码形态推断：WOLF 把 401 args[0]==1 预留给了「102 之后、第一个 401 之前的那个
空槽」（本作 495 条全部为空），真正的选项 1 的 body 从 401 args[0]==2 之后开始。

**对照**：111 VariableCondition 的 401 则从 **1** 开始（抽样验证，例：ev278 pc140
111 … → pc141 401 a=[1]；ev319 pc43 111 … → pc44 401 a=[1]）。所以两种块的编号规则**不同**，
不能共用一套 case_id == option_index 的映射。

### 3.4 预编译成跳转表（加载期）

推荐在 program.rs 的 compile 阶段对每个 102 块产出：

`````
struct ChoiceBlock {
    pc: usize,               // 102 的指令下标
    option_count: u8,        // args[0] & 0x0F
    cancel_disabled: bool,   // args[0] & 0x10 != 0
    targets: Vec<usize>,     // 长度 n；targets[i] = 选项 i+1 的第一条指令
    cancel_pc: Option<usize>,// 421 的下一条；无 421 则 None
    end_pc: usize,           // 配对 499 的下一条（所有分支完成后跳这里）
}
````

构建算法（单趟 + 栈即可，O(指令数)）：

````
压栈时（102）：ChoiceBlock { pc, n = a0 & 0xF, cancel_disabled = a0 & 0x10 != 0, targets: vec![0; n], ... }
遇到 401 且栈顶是 ChoiceBlock：
    id = args[0];            // 实测 2..n+1
    i  = id - 2;             // ← 减 2，不是减 1
    if i < n { targets[i] = pc + 1 }
遇到 421 且栈顶是 ChoiceBlock：cancel_pc = Some(pc + 1)
遇到 499：end_pc = pc + 1，弹栈并写入该块的跳转表
```

如果现有实现里写的是 cases.push((arg(cmd,0), pc+1)) 然后在运行时用
cases.iter().find(|(id,_)| *id == i) 查表（i 从 1 开始），**必须改成 *id == i + 1**，
否则本作 495 条选择全部错位一格。这条建议已单独报给 lead。

### 3.5 最后一个选项没有 401 收尾

最后一个 401（args[0]==n+1）之后的 body 一直延伸到 421/499。即"最后一个选项"没有
显式的结束标记，靠 499/421 收尾。【已验证】形态上成立；运行时若靠"下一个 401"判断段尾，
必须额外处理"没有下一个 401"的情况。

## 5. 决定性判定：原版到底画不画选择窗口？

**结论：画。** 6 条独立证据收敛，且能解释"为什么标题画面看不到窗口"。

### 5.1 证据链

| # | 证据 | 说明 |
|---|---|---|
| 1 | **sys3/sys4 被写 89 次，且几乎总是紧邻一条 102** | 给一个不画的窗口设坐标毫无意义 |
| 2 | **79 个 bit4=1 的块有 ≥2 个可读日文选项，块内 150 数量为 0** | 例：ev246 pc1504 ["射在脸上","让她咽下去"]、ev278 pc134 ["好的","还是算了"]、ev319 pc27 ["淋上去","算了"]、ev315 pc132 等 22 处 ["再找找其他的","不找了"]。这些块里既没有 150 画的菜单图，也没有其他绘制指令 ⇒ 只能由运行时画 |
| 3 | **SysDatabase「ウィンドウ画像」第 2 行 = ×選択肢ウィンドウ画像 = SystemFile/WindowBase.png**，并注明「選択肢ウィンドウは 3x3 に分割されて使用される」 | 引擎专门给选择窗口配了皮肤 |
| 4 | **sys14（選択肢ウィンドウ表示する?）全库 0 次写入** | 从不关闭 ⇒ 默认（ON）生效 |
| 5 | **官方手册的例子**：Sys4 = 40 紧跟「■文章選択肢:【1】白色 /【2】黒色 /…」 | 选项是普通可见文本，窗口按 sys4 定位（work/_yado_0610.txt:280-283） |
| 6 | **实机截图**：work/out/ScreenShot_2026_1028_21_21_35.png 底部有运行时绘制的消息窗口（白字黑底、无外框），证明该引擎在本作里就是用 WindowBase.png 画窗口的 | 见 §6.4 |

### 5.2 反证：标题画面的窗口去哪了？

ev42「オリジナルタイトル画面Ａ」：

````
pc111  121  [9000003, 512, 0, 0]      ; sys3 (选择窗口 X) = 512
pc112  121  [9000004, 1000, 0, 0]     ; sys4 (选择窗口 Y) = 1000   ← 屏幕高只有 576！
pc113  102  [19]  ["1", "2", "3"]     ; 选项文字是占位符
```

玩家看到的是脚本用 150 画的标题菜单，选项文字是 "1"/"2"/"3" 占位符，而且**窗口被故意挪到
y=1000（屏幕外）**。这解释了全部现象，也证明 **bit4 不是"隐藏窗口"开关**——它是"取消不可"。

**实现含义**：不需要任何"标题特判"。按 sys3/sys4 老老实实画，窗口矩形完全在视口外时
（y > 576 或 x > 1024 或 x+w < 0 或 y+h < 0）跳过绘制即可，标题自然看不到窗口。

### 5.3 线索 B 的统计结果（**否证了"0x10 组是占位文本"的假说**）

| 分组 | 选项字符串总数 | 日文 | \cself[n] | ASCII | 纯数字 |
|---|---|---|---|---|---|
| bit4 = 0 | 406 | 344 (84.7%) | 49 (12.1%) | 13 (3.2%) | 0 |
| bit4 = 1 | 604 | **561 (92.9%)** | 34 (5.6%) | 6 (1.0%) | 3 (0.5%) |

两组都主要是**正常可读日文**（bit4=1 组比例还更高）。全库只有 5 个块的选项完全不可读：

```
ev42  pc113   ["1","2","3"]                                   ← 标题（自己画菜单）
ev281 pc259   ["\cself[5]","\cself[6]","\cself[7]"]
ev315 pc1009  ["\cself[5]","\cself[6]","\cself[7]"]
ev322 pc1096  ["\cself[5]","\cself[6]","\cself[7]"]
ev328 pc579   \f[20]\cself[...] 三项
```

所以 **bit4 ≠ "选项是占位符"**。

### 5.4 线索 A 的交叉表

| bit4 | 块内 150 个数 = 0 | 块内 150 > 0 | 块内 101 = 0 | 块内 101 > 0 |
|---|---|---|---|---|
| 0 | 94 | 59 | 7 | 146 |
| 1 | **232** | 110 | 159 | 183 |

608 个块里没有任何 150，其中 232 个是 bit4=1。**"bit4=1 的块普遍不用 150 画菜单"这个假说被否证**
（110 个 bit4=1 的块确实有 150，但那是背景/立绘，不是菜单）。

### 5.5 bit4 到底是什么

**最可能：取消不可（キャンセル無効）。** 理由：

- 与 421 的互斥是 **153 vs 342 零例外**（有 421 ⇔ bit4=0）。这是全库最强的相关性。
- 语义自洽：不能取消，编辑器就不生成取消分支。
- bit4=0 的 153 个块全部有 421，包括只有 1 个选项的 3 个块（"只有'确定'一个选项 + 可取消"，
  这在 WOLF 里是正常写法）。

**仍存疑**：bit5/bit6 只在 ev359 pc1684（args[0] = 117 = 5 | 0x70）出现一次，无法反推。
该条是一个 5 选项的偷窥事件，2/3/4/5 项都是 \cself[n]，可能是"动态选项"相关的标志位（【未验证】）。
实现时建议：**bit5/bit6 忽略**，只解 bit0-3 与 bit4。

## 7. 实现建议（伪代码）

`````
fn exec_choice(vm: &mut Vm, blk: &ChoiceBlock) -> Next {
    // 0) 先把当前消息窗口的显示/打字等完（未验证但必要）
    vm.flush_message();

    // 1) 读窗口参数
    let visible = vm.sys(14) != 0;                 // 本作 = 1
    let (x, y)  = (vm.sys(3), vm.sys(4));          // 屏幕绝对像素
    let n       = blk.option_count as usize;
    let texts: Vec<Text> = vm.cur_cmd().strings.iter().map(parse_escapes).collect();

    // 2) 布局
    let pad_x = vm.sys(26).max(0) as i32;          // 默认值未知，先用 8
    let pad_y = vm.sys(27).max(0) as i32;
    let line_h = vm.line_height();                 // 未验证，用 ceil(sys8*1.35)
    let w = texts.iter().map(|t| t.width(vm)).max().unwrap_or(0) + CURSOR_W + 2*pad_x;
    let h = (n as i32) * line_h + 2*pad_y;

    // 3) 离屏裁剪（标题画面靠这个自然消失）
    let onscreen = visible && x + w > 0 && y + h > 0 && x < vm.screen_w() && y < vm.screen_h();

    // 4) 光标初值：sys7 若被写过用 sys7，否则 0；脚本写 sys20 时以 sys20 为准
    let mut cur = clamp(vm.sys(7).max(0), 0, n-1);
    vm.set_sys(20, cur);

    // 5) 阻塞循环
    loop {
        if onscreen { draw_nine_patch(WindowBase, x, y, w, h);
                      for (i,t) in texts.iter().enumerate() { draw_text(t, x+pad_x+CURSOR_W, y+pad_y+i*line_h) }
                      draw_cursor(x+pad_x, y+pad_y+cur*line_h) }
        match wait_input() {
            Up   => { cur = (cur+n-1)%n; vm.set_sys(20, cur); play_se(vm.sys(18)) }
            Down => { cur = (cur+1)%n;   vm.set_sys(20, cur); play_se(vm.sys(18)) }
            Ok   => { play_se(vm.sys(17)); vm.set_sys(20, cur); return blk.targets[cur] }
            Cancel => {
                if blk.cancel_disabled { continue }        // 取消被吞掉
                play_se(vm.sys(19)); vm.set_sys(20, -1);
                return blk.cancel_pc.unwrap_or(blk.end_pc)
            }
            MouseMove/MouseClick => { /* sys73 != 0 时按 sys73 处理 */ }
        }
    }
}
```

### 7.1 如果选择"干脆不画窗口"

只有在**确定要放弃原作观感**时才可行，而且会立刻暴露：

- 79 个 bit4=1 的块、91 个 bit4=0 的块：选项文字只存在于 stringArgs 里（块内无 150）
  ⇒ 不画就**玩家完全看不到选项**，游戏卡死（无法知道有几个选项、该按什么）。
- 标题画面（sys4=1000）不画反而是对的 —— 但这由"离屏裁剪"自动解决，不需要特判。

**结论：必须画。** 唯一可以商量的只是皮肤/字号/余白，而不是"画不画"。

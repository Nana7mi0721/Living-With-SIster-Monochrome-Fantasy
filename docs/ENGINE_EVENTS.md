## 1. 结论摘要

**结论 1（已验证）**：`work/yado.txt` 全文只有**一处**「引擎点名某公共事件」—— `063`。
`grep -n "コモンイベント\[" work/yado.txt` 的全部命中是 62 / 69 / 337 / 635 / 645 / 646 / 679 行，其中
62、69 是同一句式（分别在系统变量 1/2 与 5/6 的说明里），其余 5 处都不是引擎调用陈述
（337 是 self 变量编号换算示例，635/645/646/679 是改造指南）。
⇒ `41/213/214/224/225/261/269/270/271` **一个都没被 yado 点名**。
但 yado **只覆盖「引擎隐式调用」这一种机制**，不覆盖启动条件 —— 所以「yado 没提」不等于「引擎不启动」。

**结论 2（已验证 · 机制）**：引擎启动公共事件有**两条互不替代的通道**：

| 通道 | 机制 | 本作命中 | 证据 |
|---|---|---|---|
| (a) 隐式调用 | 引擎内部某功能执行时去跑某个定编号公共事件 | **仅 063**（每次【文章の表示】） | `work/yado.txt:61-63`、`:67-69` |
| (b) 启动条件 | 事件头 1 字节低 4 位 = `run_condition` | 11 个（run=3 十个 + run=1 一个） | `docs/ARCHITECTURE.md:340-347`、`_wolfref/commonevent_dat.ksy:13-17` |

**结论 3（已验证）**：本作 108 个 `run != 0` 事件分布 = `{1: 1, 2: 97, 3: 10}`（C4）。
当前代码只启动 `[48, 63]`（`crates/wolf-game/src/game.rs:55` 的 `ENGINE_EVENTS`）⇒
**漏启动 9 个 run=3（41 / 213 / 214 / 224 / 225 / 261 / 269 / 270 / 271）+ 1 个 run=1（241）**。
63 是 `run=0`，属通道 (a)，加它是对的；48 是 run=3，属通道 (b)。

**结论 4（已验证）**：97 个 run=2 **不该**进「开机无条件启动」集合，它们的语义是「条件成立时创建、失效时销毁」。
开局（全部变量为 0）条件为真的只有 2 个：`ev38`（`v160 <= 2`）与 `ev43`（`v0 == 0`）。
★已实测纠正：本任务早期记录说「43 / 216 / 217 / 343 的条件变量 W=0（无人写）」，其中
**216/217 的条件变量 `2000003` 有 1 处写者**（`SampleMapA` 地图事件 0 第 215 槽），
**43 的条件变量 `2000000` 有 2 处写者**（`Map003` ev1 第 11 槽、`TitleMap` ev2 第 108 槽）；
真正 W=0 的只有 **343（`2000158`）**与 **270（`2700020`，全库 0 次出现）**，而 270 是 run=3，条件字节不参与判定。

**结论 5（已验证 · 标题菜单收尾时修正）**：`ev43 ┗オリジナルタイトル画面Ｂ` 不是死代码，而是**标题三行菜单的渲染器**。
作者注释自述「タイトル画面用のマップのイベントで呼び出してください。イベント起動条件は「並列実行」に設定してください」，

它画的 `Picture/menu1_b.png` / `menu2_b.png` / `menu3_b.png`（240×52，高亮态 `menu*_a.png`）
与参考截图 `010_标题_三行菜单.png` 的三行「开始了呦！！！！！ / 那就继续做吧！！ / 果然还是停下吧……」逐一对应，

关于「图片号 3/4/5 会被 pic 12000 遮挡」：该结论只在旧的 `number >= 12000 ⇒ 全屏 backdrop` 规则下成立，
该规则已删除（见 commit 4e46498），图片现在按 WOLF `Picture::destination` 原生尺寸缩放层级合成。
⇒ 移植端口（`godot/core_cs/GameSession.cs` 的 `SetTitleMenuVisible` / `RestartTitleMenu`）在标题选择框打开期间

**结论 6（已验证 · 风险分档）**：10 个 run=3 按「启动后是否可能改变屏幕像素」分三档：

| 档 | 事件 | 依据 |

## 2. `run_condition` 的语义与判定

### 2.1 位序（已验证）

事件头的条件字节是一个打包字节，**WolfTL / Kaitai 的位序是反的**，已由 `docs/FORMAT_SPEC.md:323-334` 实测纠正：

```rust
run_condition      = raw & 0x0F     // 低 4 位
condition_operator = (raw >> 4) & 0x0F
```

依据：550 个事件低 4 位的直方图恰好是 `{0: 442, 1: 1, 2: 97, 3: 10}`（C6）；
若取高 4 位会得到 `{1: 83, 2: 465, 3: 1, 6: 1}`，作为 run_condition 无意义。
代码侧对应 `crates/wolf-format/src/commonevent.rs:75 run_condition()` 与 `:81 condition_operator()`。

### 2.2 四种取值与调度语义（已验证 · 文档依据）

| run_condition | 数量 | 何时创建 | 何时销毁 | 每帧推进 | Kaitai 名 |
|---|---|---|---|---|---|
| `auto_start(1)` | **1** | 游戏启动 | 事件自行结束 | 是 | `auto_start` |
| `parallel_process(2)` | **97** | 满足启动条件时 | 触发条件失效时 | 是 | `parallel_process` |
| `parallel_process_always(3)` | **10** | 无条件常驻 | 从不（除非 EndGame） | 是 | `parallel_process_always` |
| `call_only(0)` | **442** | 被 `210` 主动调用 / 被 `211/300` 预约 | pc 走到事件末尾 | 仅有栈帧时 | `call_only` |

★**关键点（容易被误判）**：run=3 与 run=1 的事件在事件头里**也带着条件变量与值**（例如
`224` 是 `2000001 / 1`、`270` 是 `2700020 / 3`、`241` 是 `2000350 / 2`），但**引擎不据此 gate** ——
那个字节是 WOLF 编辑器 UI 的残留（它总是把同一组字段序列化），只有 `run=2` 才参与判定。
证据：run=3 的 10 个事件里条件变量的写者分布极不均匀（`2700020` 全库 0 次出现、`2000158` 0 次），
而它们却是「常时」事件；若引擎真按条件 gate，270 会永远不跑，这与作者把 270 标成「常时」矛盾。

### 2.3 实测分布（已验证，C4 / C5）

- **条件运算符**：只统计 run=2 的 97 个 ⇒ `{1 (>=): 77, 2 (==): 19, 3 (<=): 1}`（另有 run=1 的 241 是 `2 (==)`、run=3 的 270 是 `6 (bitwise_and)`，均不参与判定）。
- **条件变量段**：108 个的 condvar **全部**落在 `2000000..2999999`（普通变量段），无一落在 self / 字符串 / 系统变量段 ⇒ 引擎只需一个「普通变量数组」就能求值。
- **run=2 的 condvar 去重 84 个**，被多个事件共享的 6 组：`v2→[236,237]`、`v3→[216,217]`、`v62→[335,352,357]`、`v99→[348,353]`、`v149→[355,356]`、`v616→[514..521]`。
- **开局（全 0）真值**：只有 `ev38`（`v160 <= 2` ⇒ 0<=2 真）与 `ev43`（`v0 == 0` ⇒ 真）成立，其余 95 个 run=2 全部为假。
- **尾部指令**（说明它们是循环协程）：108 个事件的「最后一条真实指令」直方图 = `{499 LoopEnd: 81, 180 Wait: 9, 498 LoopStart: 8, 150 Picture: 5, 121 SetVar: 4, 103 Comment: 1}`，**107/108 含 499** ⇒ 绝大多数是 `498…499` 无限循环 + 内部 `Wait` 的常驻协程；少数（216/217/236/237/269/270/271/241 等）是线性体跑到末尾，由引擎下一帧重入。

### 2.5 我们代码的缺口（已验证 · grep 证据）

```bash
grep -rn "run_condition\|is_background\|condition_operator" crates/wolf-vm/src crates/wolf-game/src crates/wolf-cli/src
```

只命中三处，**没有一处在做调度**：

- `crates/wolf-game/src/game.rs:49/52` —— `ENGINE_EVENTS` 的文档注释；
- `crates/wolf-cli/src/main.rs:326` 与 `:1122 fn run_condition_label` —— `verify` 子命令的直方图统计。

也就是说：**VM 与 Game 目前完全没有 run_condition 驱动的自动启动逻辑**，只有硬编码的两个事件。
结构上还差两块：

1. `crates/wolf-vm/src/program.rs:203 pub struct Program` 的字段里**没有** `run_condition`（也没有条件变量/值），
   所以 VM 自己无法决定「这个程序该不该起」；
2. `crates/wolf-game/src/game.rs` 的 `Game::new` 里 `read_events(...)` 返回的 `CommonEventData`
   **之后没有留在 Game 里**（只留下 `ProgramSet`）⇒ 现在也拿不到 run_condition。

## 7. 判定表

**谁启动**一列的含义：

- **引擎/常时** = 通道 (b) 的 `run=3`，引擎无条件常驻（本文 §2.2）；
- **引擎/自动** = 通道 (b) 的 `run=1`，游戏启动时跑一次；
- **引擎/隐式** = 通道 (a)，yado 记载的功能性调用（本作只有 063）；
- **引擎/条件** = 通道 (b) 的 `run=2`，引擎每帧按条件变量启停；
- **脚本** = 只能被 `210/211/300` 显式调用；
- **无人** = 本作既不满足条件、也无人调用。

| 事件ID | 名称 | 触发条件 | 谁启动 | 证据 | 建议 |
|---|---|---|---|---|---|

## 8. 给 `Game::start_engine_events` 的推荐

### 8.1 分三期，不要一次全上

| 期 | 内容 | 风险 | 验收 |
|---|---|---|---|
| **P1（本文）** | 把 `ENGINE_EVENTS` 扩成三组常量，按依赖顺序启动 11 个引擎常驻 + 保留 63 | 只有一个事件（225）可能改像素 | §8.3 的 A/B 协议 |
| **P2（下一次）** | 实现 `run=2` 的 run_condition 驱动器 | 会**一次性**唤醒最多 97 个协程，必须限流与观察 | 变量快照 + 像素 + `StepReport` 统计 |
| **P3（后续）** | 在消息渲染里消费 sysstr 26/27（`文章表示追加 先頭/最後尾`） | 会改变所有消息的排版 | `docs/TEXT_SPEC.md` 的排版用例全跑 |

**P1 的收益**：让「引擎常驻服务」这一层与原版对齐；代价是每帧约 +300 条指令（§6），可忽略。
**P1 的风险**：225 会把鼠标光标画成图片（§5.5）。这是唯一可能立刻改变屏幕像素的事件。

### 8.2 代码骨架（可直接落地；文件属于 Lead 的写权限）

```rust
// crates/wolf-game/src/game.rs

/// Events the engine starts **unconditionally** because their header says
/// `parallel_process_always(3)`. The condition byte they also carry is an editor
/// artefact: e.g. `270` names variable `2700020`, which never appears anywhere in
/// the 550 common events or the 7 map resources (docs/ENGINE_EVENTS.md §2.2).
/// Order matters: 261 must precede 270 (270 reads `2700000..2700005`), and 269
/// must precede 270 (270 tests the flag `1600099` that 269 sets).
pub const ENGINE_ALWAYS: &[u32] = &[
    48,  // X[共]基本システム自動初期化 — system variables first
    261, // ×◆座標変数初期化      — writes 2700000..2700005 for 270
    269, // ×┣[メッセ—ジ]初期化·設定 — sets self 1600099 for 270
    270, // ×┣[メッセ—ジ]表示処理
    271, // ×┗[メッセ—ジ]オートスキップ — writes sysstr 26/27
    224, // ウィンドウ処理         — needs 225's Sys71/72 + other events' picture numbers
    225, // フィールド上処理         — publishes Sys71/72, draws the picture cursor
    213, // クリックエフェクト        — needs 225's Sys71/72
    214, // 健康監視
    41,  // マウス感知コモン
];

/// `auto_start(1)`: run once at game start. It clears its own condition variable
/// (slot 628 writes `v350 = 0`) and ends, so it never becomes a resident coroutine.
pub const ENGINE_AUTO_START: &[u32] = &[241];

/// Started by an engine *feature* rather than by `run_condition`: YADOT-WOLF
/// documents that every 【文章の表示】 executes 063 (work/yado.txt:61-63 / :68-70),
/// and no script anywhere targets 500063.
pub const ENGINE_IMPLICIT: &[u32] = &[63];

impl Game {
    /// Start the events the engine owns. Idempotent.
    pub fn start_engine_events(&mut self) -> usize {
        if self.engine_events_started {
            return 0;
        }
        self.engine_events_started = true;
        ENGINE_ALWAYS
            .iter()
            .chain(ENGINE_AUTO_START)
            .chain(ENGINE_IMPLICIT)
            .filter(|id| self.start_event(**id))
            .count()
    }
}
```

**为什么保留 `engine_events_started` 幂等标志**：`start_engine_events` 同时被 `boot()`（`game.rs:273`）与
`start_map_event_by_name`（`game.rs:315`）调用，后者在切图时也会走 ⇒ 没有标志会重复启动。

**为什么分成三个常量而不是一个大数组**：三组的**生命周期语义不同**（常驻 / 一次性 / 功能性），
将来实现 `EndGame` 或读档重开时，只有 `ENGINE_ALWAYS` 需要重建，另两组不需要。这也让文档与代码一一对应。

### 8.3 验收协议（每加一个事件都要跑）

我们现在**没有**「额外启动某公共事件」的 CLI flag（`wolf-cli capture --help` 只有
`--frames / --out / --answer / --filter / --until / --menu-only / --hold-message / -m / --boot / --root`），
所以 A/B 有两种做法：

1. **推荐**：给 `wolf-cli` 加一个 `--engine-events <id,id,…>`（对 `capture` 与 `run` 生效），
   覆盖 `ENGINE_ALWAYS`。这样不必反复改 `game.rs` 就能做逐事件 A/B；
2. **退路**：改 `ENGINE_ALWAYS` 后重编译，逐次对比。

每次对比的命令：

```bash
./target/debug/wolf-cli.exe capture --frames 716 --out work/out/ab_a.png
# 改启动集
./target/debug/wolf-cli.exe capture --frames 716 --out work/out/ab_b.png
cargo run -q -p wolf-render --example imgdiff -- work/out/ab_a.png work/out/ab_b.png
```

判定：

- **`identical: true`** ⇒ 该事件在当前实现下零可见影响，可以放心留用；
- **有像素变化** ⇒ 记下 `mean abs / max / psnr / 变化像素数`，并回答：这些像素是「零售也有的」还是「我们多画的」？
  前者说明我们之前漏画了（要补），后者必须回退。

基准数值（C2，当前状态，未启动那 10 个）：`14319 instruction(s) / 10 picture op(s) / 36 db access(es) / 0 warning(s)`，
`rendered 1024x576, 538282/589824 non-black`，与零售截图 mean abs 0.012 / max 1 / psnr 67.20 dB。

### 8.5 P2：`run=2` 驱动器（真正的缺口）

现在 `Program` 里没有 run_condition（§2.5），所以要分两处改：

```rust
// crates/wolf-vm/src/program.rs —— 让程序自带自己的启动条件
pub struct Program {
    // …既有字段…
    /// `run_condition` byte (low nibble) from the event header.
    pub run_condition: u8,
    /// `condition_operator` (high nibble): 0 > / 1 >= / 2 == / 3 <= / 4 < / 5 != / 6 bitand.
    pub condition_operator: u8,
    /// `2000000 + N` magic for the variable slot.
    pub condition_variable: u32,
    pub condition_value: u32,
}

impl Program {
    /// Only `parallel_process(2)` is gated; `parallel_process_always(3)` and
    /// `auto_start(1)` are started by the engine regardless of this byte.
    pub fn is_gated(&self) -> bool {
        self.run_condition == 2
    }

    pub fn condition_holds(&self, vars: &Variables) -> bool {
        let index = (self.condition_variable - 2_000_000) as usize;
        let lhs = vars.get(index).max(0) as u32;
        let rhs = self.condition_value;
        match self.condition_operator {
            0 => lhs > rhs,
            1 => lhs >= rhs,
            2 => lhs == rhs,
            3 => lhs <= rhs,
            4 => lhs < rhs,
            5 => lhs != rhs,
            6 => lhs & rhs != 0,
            _ => false,
        }
    }
}
```

```rust
// crates/wolf-vm/src/exec.rs —— 每帧同步一次「该跑的并行事件」
impl Vm {
    /// Create gated background events whose condition just became true, and stop
    /// those whose condition went false. Returns (started, stopped).
    ///
    /// Runs before `run_instances` so a freshly satisfied gate gets a slice this
    /// same frame (the original engine behaves this way for the opening scene,
    /// where 「SampleMapA」 turns on `v3` and `216/217` start refreshing immediately).
    pub fn sync_gated_events(&mut self) -> (usize, usize) {
        let mut start = Vec::new();
        let mut stop = Vec::new();
        for program in self.programs.iter_gated() {
            let want = program.condition_holds(&self.vars);
            let live = self.instances().iter().any(|i| i.event == program.id && i.parent.is_none());
            match (want, live) {
                (true, false) => start.push(program.id),
                (false, true) => stop.push(program.id),
                _ => {}
            }
        }
        let started = start
            .into_iter()
            .filter(|id| self.start_event(*id).is_some())
            .count();
        let stopped = stop
            .into_iter()
            .filter(|id| self.stop_event_instances(*id) > 0)
            .count();
        (started, stopped)
    }
}
```

需要同步补的三处：

1. `ProgramSet` 要暴露一个**迭代器**（现在只有 `program.rs:442` 的按 id 取值 `event(id)`）；
2. `Program::compile`（`program.rs:240`）要接收 `&CommonEvent` 的 run_condition 四元组；
3. `Vm::stop_event_instances(event)` —— 现有 `stop_instance(InstanceId)`（`exec.rs:680`）是按实例停，
   按事件停要自己扫；注意它得连带唤醒被 `210` 阻塞的父协程（现有实现已经处理了这一点，见其注释）。

**限流建议**：P2 第一次上线时把每帧「新启动的 gated 事件数」限制在个位数，并在 `StepReport` 里加
`gated_started / gated_stopped` 两个计数，避免开局一瞬间 97 个协程同时抢预算。

### 10.3 271 曾经的 453 个像素（历史记录，已关闭）

`271` 本身 **0 条 150**，它画不出像素。像素连同 19 个窗口图片（`10225..10248`）一起出现，来自它的 `210 [600098, 16777217, 1, 1600091]` —— 调用事件 98，把第三方「高機能吹き出しメッセージ」库整套初始化。当时实测那 19 个控件里 `10235..10248` 全部落在 `[0,0,1600,72]` 这类位置并**可见**，于是标题左上角多出 453 个像素。

当时的判断是「这套库的图片号与坐标都在运行时算出来，我们尚未解开它的参数」。**事后证明那只是表象**：控件的落位来自库自己的 self 变量，而那些变量当时没拿到值（`210` 的实参还没进被调事件的 self 银行、`250` 数据库读取还没有应答）。这两件事修好后，同样的控件落到库自己的停车场 `(-2784, 2880)`，`picture::on_screen` 判定它们碰不到屏幕，于是不再产出 quad。

### 10.4 顺带修掉的相邻缺陷（已验证）

## 11. run_condition == 2 事件调度器（M3 第一步，已验证）

§2.2 说 `run_condition == 2` 是「条件满足时常驻」。在此之前只有 §8 的 12 个常量/隐式事件会被启动，97 个 `run=2` 事件全部不跑。`crates/wolf-game/src/auto_events.rs` 补上这个调度器。

### 11.1 规则

- 过滤：`run_condition() == 2` 且不在 `SKIPPED`（当前只有事件 43；它没有任何调用点，条件变量也没有写入者，属死代码）。最终跟踪 **96 个**。
- 边沿触发：`false -> true` 才调用 `Vm::start_event`；`true -> false` 才调用 `Vm::stop_instance`。条件一直为 true 时，协程自然结束后不会被调度器重启（常驻事件自己负责循环）。
- 条件比较：operator 1 = `>=`、2 = `==`、3 = `<=`；变量地址只接受 `VAR_BASE + 0..800`（通常变量 0..799）。
- 开关：`Game.auto_events.set_enabled(false)` 或 `wolf-cli capture --auto-events off` 可整体停用，用于 A/B。

### 11.2 启动时机（已验证）

`Game::new` 构建调度器；`Game::start_engine_events` 末尾同步一次（开局条件已成立的立即启动）；`Game::frame` 每帧最先同步一次，然后才处理输入和 `vm.step_frame`。

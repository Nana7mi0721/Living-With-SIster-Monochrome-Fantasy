# 未验证假设清单（UNVERIFIED）

本文件登记**已经写进代码、但证据不足以称为定论**的判断。每条给：假说、当前实现、支持证据、反证 / 未验证部分、以及「怎么才能证实」。

约定：一旦某条被证实或推翻，从这里删掉并写进 `docs/FORMAT_SPEC.md` / `docs/OPCODE_SPEC.md` 的对应小节（那两份是「已实测」文档，本文件是「待实测」文档）。

## H-PIC-1 负番号图片 = 全屏图层

**假说**：`150` 的图片番号为负数时（本作实测只有 `-2`），该图片是「全屏背景图层」：忽略 x / y / scale，直接铺满 1024×576。

**实现**：`crates/wolf-game/src/picture.rs` 的 `Picture::is_screen_layer` / `Screen::quads`：负番号 → src = 纹理全图，dst = (0,0,1024,576)。

**支持证据**：
- 标题画面第一条绘制 `ev42 pc20`：`[0,-2,30,1,1,1,255,0,0,100,0] str=SystemGraphic/TitleGraphic.jpg` —— 该 JPG 本身正好是 1024×576（逻辑屏尺寸），若按普通图片解释也会铺满，所以这条其实**无法区分**两种解释。
- 本作共出现 30 次负番号绘制，全部出现在标题/读档这类「整屏换图」的位置。

**未验证**：负番号的真实含义（WOLF 文档没有写）；`-1` 是否代表另一种哨兵；负番号是否允许动画/淡入。

★已解除：eval_num 曾把 MagicKind::Opaque 求值成 0，导致 -2 变成 0、本分支永远不命中（H-PIC-1 一度是死代码）。修复为「Opaque 返回原值」后该分支已在标题画面命中并通过像素对照。

**怎么证实**：找一个用了负番号且图片**不是** 1024×576 的场景，看游戏里是铺满还是按原尺寸画。

## H-PIC-2 图片字段布局（长格式槽位下标）

**假说**：`150` 长格式（argc ≥ 11）的槽位是 `[6]`=不透明度、`[7]`=X、`[8]`=Y、`[9]`=统一缩放%、`[10]`=混合模式、`[3]/[4]`=窗口宽高（只对 type 3/4），而 `[2]`、`[5]` 含义未知。

**实现**：`crates/wolf-game/src/picture.rs` 的 `mod field` 常量表 + `Screen::apply`（下标已相对 `raw[2..]` 减 2）。

**支持证据（大幅增强）**：
- 标题提示条 `SystemFile/Button01.png`（606×35）`ints=[4096,12001,0,1,1,1,255,512,520,100,0]`：按本布局得到 (512,520) 中心锚点 606×35，**与零售版 1024×576 截图逐像素吻合（mean abs 0.35/255，98.6% 像素差 ≤2）**；早期「`[2]`=X、`[4]`=scaleX」的布局会把同一张图画成 (30,1) 处的 1% 色块。
- 13,637 条长格式样本的取值分布全部自洽：`[6]` 以 255 为主（不透明度）、`[9]` 以 100 为主（缩放 100%）、`[10]` 只有 `0`/`-1000000`/`1250` 三个值（混合模式）、`[7]`/`[8]` 取值最多样且大量是 magic（坐标来自变量）。
- 窗口图片 `#12500` `[0,300,200,1,255,855,200,100,0,…]` → 300×200 窗口框；文字图片 `#12501` 得到 `[3]/[4]=1,1`（自适应框哨兵）。

**仍未验证**：`[2]`（31 个取值，`0`×9770 / `15`×1568 / `5`×481 / `30`×431 / `100`×242…，看着像角度或效果参数）与 `[5]`（`1`×12156 / `2`×559 / `3`×346 / `-1000000`×146…）的真实含义；本作渲染目前**忽略**这两个槽（已用像素对照证明忽略不影响标题画面）。

**怎么证实**：找一条 `[2]` 非 0 且画面可比的指令（例如 `ev42 pc20` 的 `30`），在零售版里看它是否造成旋转/闪烁；或反编译 `Game.exe` 的 `150` 处理函数。

## H-ANC-1 锚点位 0x2000..0x6000 的含义

**假说**：`150` 头字位 bits 12..14 是锚点，`0x1000` = 中心（两轴）；其余 `0x2000/0x3000/0x4000/0x5000/0x6000` 是别的锚点（右/上右/下右/上中/下中之类），但**证据不足**。

**实现**：`crates/wolf-game/src/picture.rs` 的 `place()`：只有 `ANCHOR_CENTRE(1)` 会减去半宽半高，其余一律按左上角处理。

**支持证据**：`0x1000` 组 4,393 条的 X 集中在 512、Y 集中在 288（正好屏幕中心），并且标题提示条的像素级对照证实了两轴都居中。

**未验证**：其余 6 个 nibble 共 333 条样本，X/Y 分布分别偏向 `384`/`1000`/`1024`/`800` 等值，但**没有任何一张图能证明它到底指哪个角**，因此一律当左上角（`0x0000` 同款）实现——只影响这 333 条（占 2.4%），且都不在标题/读档路径上。

**怎么证实**：挑一条 `0x4000` 且 x=1024、y=570 的（事件层面能定位到具体事件），在零售版里看它是否贴右下角；或者用 `0x6000`+x=800,y=576 那条。

## H-WIN-1 窗口图片的皮肤与九宫格

**假说**：`150` 的 type 3（WindowFile）/ type 4（WindowString）会在内容下方画一块 UI 面板，皮肤来自 `SystemGraphic/WindowBase.png`（18×18），框厚 3 px，中间行/列拉伸。

**实现**：`crates/wolf-game/src/window.rs`（`nine_slice` + `SKIN`/`CORNER`），由 `Atlas::sprites` 在内容之前、同番号位置插入 9 个四边形。

**支持证据**：
- `WindowBase.png` 逐像素测量：第 0/17 行列为 `0x424242` 外框，第 1 行列为 `0xefefef` 高光，第 2 行列为 `0x424242` 内线，3..14 为深蓝渐变且 alpha=0xcc —— 结构上就是 3 px 框 + 拉伸体。
- 本作窗口图片的框确实由 args[1]/args[2] 给出（`#12500` = 300×200），与「面板尺寸来自指令」一致。

**未验证 / 已知矛盾**：
- type 3 的 `#12005` 框是 0×0（继承内容尺寸），我们**不画面板**（没有框尺寸就无法九宫格），只画内容。
- **矛盾点**：CN 汉化补丁的公告是两条独立图片——文字 `#12501` 在 (715,115) 自适应排到约 309×461，窗口 `#12500` 在 (855,200) 300×200，两者**不嵌套**且窗口右缘 1155 超出 1024 被裁。按脚本忠实执行的结果是「文字压在插画上、右边缘一块半透明蓝板」；这很像补丁作者的排版失误，但我们**没有**原版实机截图可以判定，故按脚本原样渲染，不改坐标、不做自动嵌套。

**怎么证实**：在原版游戏里截一张标题画面（本机 PowerShell 抓屏 / PrintWindow 都只抓到开场过场，游戏不接受合成按键），或用修改器把 `#12500`/`#12501` 的坐标打印出来。

## H-KEY-2 键码模型与 `123` 掩码语义（H-KEY-1 已作废）

**结论（已实测）**：`123` 写进目标变量的是**键码**（10 決定 / 11 キャンセル / 12 サブ / 2·4·6·8 小键盘方向），不是位掩码。
旧假说 H-KEY-1（`key_bits & mask`）**已作废**：那个值永远不等于脚本比较的常量，标题菜单一个分支都进不去。
证据见 `docs/OPCODE_SPEC.md` §5.13（全部来自本作 `103` 调试注释：事件 108 / 65 / 118 / 510）。

**实现**：`crates/wolf-vm/src/exec.rs` 新增 `Host::key_code(mask) -> i32`（默认 0），`123` 分支写它；`crates/wolf-game/src/key.rs` 维护端口内部位布局与 `code()` 映射。

**仍未解（两条）**：
1. **`arg[1]` 掩码的语义** —— 一次轮询能返回六种键码（事件 108 掩码 177：先得 10/11/2，else 再得 8/4/6），所以不是「一位一键」。
   当前实现接受掩码但忽略它，回答「当前按下的键的键码」；对全库所有 `!= 0` / `== 10` 形式的比较都成立。若将来出现「同一次轮询要区分 Alt/方向组合」的脚本，就必须把掩码真正解开。
2. **未命名的键码** 13 / 14 / 20 / 100 / 300 —— 出现在比较里，本作没有注释能说明它们的来源（鼠标键？手柄？滚轮？）。
   目前已按「永不返回」处理（端口不会产生这些码），一旦有脚本依赖它们就会走进 else 分支。

**怎么证实**：原版实机按 F 系列的 info 键或直接在标题菜单试上下+決定，比对光标行为；或反编译 `Game.exe` 里读取 `GetKeyState`/DirectInput 的那一小段。

## H-PRNG-1 随机数流

**假说**：`121` 的 `0x6000` 算子 = `rand(min,max)`（闭区间）。**这一条已经证实**（1,101 处，见 OPCODE_SPEC §3.2），这里登记的是它的**实现**不确定性：

**实现**：`crates/wolf-vm/src/rng.rs` 用 xorshift32 播种自 `Game.dat` 的 `random_a/random_b`（本作 22227 / 25684），并按 `static_randoms` 表逐次异或一个字节。

**未验证**：WOLF 的真实 PRNG 序列（`docs/vendor` 里的 `_wolfref/game_dat_random.c` 线索）没有移植，因此**同一存档重放不会得到同一随机序列**。本作依赖随机的部分（战斗命中、掉落）在 M2 才会影响可玩性。

**怎么证实**：把 `game_dat_random.c` 的算法移植后，用「同一存档 + 同一输入序列」对拍原版输出。

## H-MENU-1 选择肢（102）的可视化责任归属

**假说**：`102` 的选项字符串由**运行时**（不是脚本）画出选择窗口；本作标题菜单的选项串是 `["1","2","3"]`，而玩家真正看到的菜单文字是脚本用图片画出来的，所以忠实移植必须**同时**做两件事：脚本图片照画 + 运行时选择窗口照画。

**实现**：`crates/wolf-game/src/game.rs` 只把选项收进 `Game::choices` 并在按下 OK 时回填索引；**尚未绘制**运行时选择窗口（`wolf-cli capture` 里看不到 "1/2/3"）。

**未验证**：WOLF 选择窗口的默认位置/边框/字体（没有文档，也没有实机截图；合理猜测是屏幕居中、宽度按最长选项、用同一块 WindowBase 皮肤）。

**怎么证实**：原版实机进入一个有选择肢的对话，量出窗口矩形。

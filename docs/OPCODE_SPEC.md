> 目标：为 Rust 重写《Living With Sister Monochrome Fantasy》（Steam appid 2429860）提供一份**可直接照着实现**的字节码语义文档。

## 1. 指令的二进制布局

### 1.1 `Command::Init`（`Command.hpp:706-767`）

每条指令的字节流：

```
u1  paramCount       ; = intArgs.size() + 1
u4  commandType      ; 0x00 时是空指令，后面没有参数区
s4  intArgs[paramCount-1]   ; 小端有符号 32 位，注意 (paramCount-1) 可能为 0
u1  indent           ; 缩进深度（0..91），不是执行语义，只用于还原块结构
u1  stringCount
t_str stringArgs[stringCount]   ; u4 字节长度 + UTF-8 + 0x00 填充到 4 字节对齐
u1  terminator
      0x00 -> 普通结束
      0x01 -> Move 特化：再读 5 个未知字节 + u1 flags + u4 routeCount + RouteCommand[routeCount]
      其他 -> 抛 "Unexpected command terminator"
```

`t_str` 定义（`_wolfref/common.ksy`）：`u4 len` + `len` 字节 UTF-8 + 若干 `0x00` 补到 4 字节边界。

**Rust 实现要点**
- `paramCount` 是 u1，**含 commandType 本身**。所以 intArgs 长度 = `paramCount - 1`；`paramCount == 0` 时该 slot 是空指令（code=0，无参数区）。
- `Command::IsUpdatable()`（`Command.hpp:254-257`）= `!m_stringArgs.empty()`，只影响编辑器显示，不影响执行。
- `indent` 必须保留：分支链/循环的配对**不能只靠 indent**（实测有跨级 case），但它是还原树结构的主要线索（见 §4）。
- **不要用 WolfTL 导出的 JSON**：它丢了 `run_condition` 且指令数少 11%（124,204 vs 139,273）。

### 1.2 事件头（CommonEvent.dat）

```
文件头 15 字节
每个事件：
  u1  0x8E 标记
  u4  cid
  u1  condByte   ; run_condition = condByte & 0x0F, op = (condByte>>4)&0x0F
  u4  condVar    ; 启动条件变量（magic number）
  u4  condVal
  u1  argn       ; 形参槽上限（**不是实际形参个数**，见 §6.3）
  u1  argsn
  t_str title
  u4  lineCount
  Command[lineCount]
  ... 事件尾部（字符串变量名表、可変DB 定义、系统变量表等，见 work/parse_ce.py:50-67）
```

`run_condition` 实测分布：`0 call_only` 442 / `2 parallel_process` 97 / `3 parallel_process_always` 10 / `1 auto_start` 1。
**108 个事件是每帧并行跑的后台协程** ⇒ 解释器必须是多任务调度，不能是单调用栈。

## 2. 魔法数字寻址体系（121 / 122 / 124 / 250 / 150 / 210 全都在用）

WOLF 用**一个 int32 同时编码「值的来源」和「目标槽位」**，WolfTL 把这种值叫 magic number。
权威注释在 `Command.hpp:27-73`。

### 2.1 四个值域（`Command.hpp:27-73`，`GetID()` 在 `:678-679`、`:649-650`）

| 区间 | 含义 | 取值公式 |
|---|---|---|
| `0 .. 999999` | **字面量** | 直接用 |
| `1000000 .. 1999999` | **Ev Self（事件局部变量）** | 索引 = `v - 1000000` |
| `2000000 .. 2999999` | **普通变量（可変DB[0] 通常変数）** | `SetVariable::GetID()` = `v - 2000000` |
| `3000000 .. 3999999` | **字符串变量**（122/112 用） | `SetString::GetID()` = `v % 1000000` |
| `9000000 .. 9999999` | **系统变量（系统DB[14]）** | 索引 = `v - 9000000` |

本游戏实测区间（`work/vm_a1.txt`）：

- Self：min 1000000 / max 1600099 / distinct 105（`1000000`、`1100000`、`1100004..6`、`1600000..1600099`）。
- 普通变量：min 2000000 / max 2700005 / distinct 578。
- 字符串变量：3000000..3219201 / distinct 30。
- 系统变量：9000000..9900033 / distinct 65 ⇒ **注意系统变量段不止 9000000+n，还有 99000xx 子段**（`9900025`/`9900026` 出现在 op122/op112）。`9900000` 段的语义 **未确认**。

### 2.2 `SetVariable::GetID()` 的两套编号视图（`Command.hpp:62-66` 注释）

```
V0    - V18    = id value
V1-0  - V9-0   = (id / 100000)
```

也就是说 2000000 段内部既有「扁平 0..N」的视图，也有「第 x 组第 y 个」的视图。本游戏里 `2000000` 与 `2000014`、`2000302` 等并存，**扁平视图即可覆盖全部实测样本**；分组视图的换算规则 **TODO/未确认**（WolfTL 没有实现，只留了注释）。

### 2.3 高阶寻址（本游戏实测到，但位义未确认）

除上述四段，实测还出现 `0x1/0x2/0x3 << 28` 的高位标志：

| 高位 | 次数 | 出现位置 |
|---|---|---|
| `0x10000000` | 56 | `112` 的 `arg[1]`（52 次）、`126` 的 `arg[0]`（4 次） |
| `0x20000000` | 25 | `125` 的 `arg[0]`（20 次）、`112`（5 次） |
| `0x30000000` | 34 | 全在 `112` 的 `arg[1..4]` |

这些**只出现在 `112 StringCondition` 与 `125/126` 输入掩码**，从不出现在 121/122。合理推断是「字符串/特殊寻址标志」，但具体位义 **TODO/未确认**。
**实现策略：遇到 112/125/126 里的高位 magic 时按「原始 32 位比较」处理即可跑通本作**，因为条件比较与掩码比较都是拿两个同构的 magic 值直接比。

### 2.4 哨兵值

| 值 | 含义 | 实测 |
|---|---|---|
| `-1000000` | 「该字段不更新」/「清除」 | op150 的 `arg[5]`(146)、`arg[6]`(127)、`arg[9]`(474)、`arg[10]`(166)；op240 的 `chipset_id == -1000000` 表示 reset |
| `-1` | 视命令而定：位置=不变、ID=不变、方向=不变 | op130 `arg[0]`、op160 `arg[0]`、op201 `arg[0]` |
| `-2` | op150 的图片编号：特殊动作（见 §5.11） | `ev42 pc17 ints=[0,-2,30,...]` |
| `4294967295 (0xFFFFFFFF)` | SysDatabase 里「无」 | `sys.txt` 里 BGM番号 = 4294967295 |

## 3. 运算符表（`Command.hpp:27-73`，权威）

### 3.1 复合赋值运算符：`intArgs[3]` 的 **bit8-11**，作用于 `intArgs[0]`（写入目标）

> **掩码是 `arg[3] & 0x0F00`，不是 `& 0x0FFF`。** 2026-xx 实测（`cargo run -p wolf-cli -- run` 跑了真实事件后回头统计）发现
> **194 / 17,258 条 `121` 的低 8 位是非零的**（`0x104`、`0x3302`、`0x20`、`0x4`、`0x2108`、`0x1301`），
> 分布 `0x02:95 / 0x04:36 / 0x01:32 / 0x20:18 / 0x10:12 / 0x08:1`。若按 `& 0x0FFF` 取运算符，
> 这 194 条会落进 `_` 分支被当成**纯赋值**（`0x104` 本该是 `+=`），即 1% 的赋值悄悄写错。
> 编辑器显然把这 8 位当另一种标志位用，含义仍未知，但**必须在掩码时丢掉**。

| `arg[3] & 0x0F00` | 语义 | 本作实测次数（17,258 条全量） |
|---|---|---|
| `0x000` | `arg0 = <结果>` | 10658 |
| `0x100` | `arg0 += <结果>` | 5054 |
| `0x200` | `arg0 -= <结果>` | 557 |
| `0x300` | `arg0 *= <结果>` | 462 |
| `0x400` | `arg0 /= <结果>` | 228 |
| `0x500` | `arg0 %= <结果>` | 59 |
| `0x600` | `arg0 = floor(arg0)` | 157 |
| `0x700` | `arg0 = ceil(arg0)` | 61 |
| `0x800` | `arg0 = abs(arg0)` | 22 |
| `0x900` | `arg0 = Angle(x10) <- Slope` | 0 |
| `0xA00` | `arg0 = sin[x1000] <- 角度 x10` | 0 |
| `0xB00` | `arg0 = cos[x1000] <- 角度 x10` | 0 |
| `0xC00` | `arg0 = sqrt[x1000]` | 0 |

> ⚠️ 本文档早期版本给的次数（`0x000:17064 / 0x100:32 / 0x200:95 …`）是**错的**（当时把二元运算的位也混进了统计），
> 以上表格才是按 `& 0x0F00` 的全量统计。`0x900`-`0xC00` 在本作中确实**一次都没出现**，属于「按 WolfTL 注释实现但没有实测样本」的一档。

### 3.2 二元运算符：`intArgs[3]` 的**bit12 以上**，作用于 `arg[1]` 与 `arg[2]` 之间

| `arg[3] >> 12` 的高位段 | 语义 | 本作实测次数（`arg[3]` 的 bit12-15） |
|---|---|---|
| `0x0000` | `arg1 + arg2` | 14932 |
| `0x1000` | `arg1 - arg2` | 214 |
| `0x2000` | `arg1 * arg2` | 469 |
| `0x3000` | **`arg1 / arg2`（整除；除零时保留 arg1）** | 435 |
| `0x4000` | **`arg1 % arg2`（取余；除零时保留 arg1）** | 107 |
| `0x5000` | `arg1 & arg2` | 0 |
| `0x6000` | **`arg1`..`arg2` 之间的随机整数 `rand(min,max)`**（见下方修正） | 1101（**本作第三高频**） |
| `0x7000` | `arg1 | arg2` | 0 |
| `0x8000` | `arg1 ^ arg2` | 0 |
| `0x9000` | `arg1 << arg2` | 0 |

> **★已实测纠正（`0x3000` / `0x4000` 互换了）**：WolfTL 的 `Command.hpp` 注释把 `0x3000` 记成取余、`0x4000` 记成按位非，但 WolfTL 自己从不解释运算符，这张表从没被数据检验过。三条独立证据：
> 
> 1. `CE48 pc30` `121 [1600025, 9000116, 32, 12288]` = `Sys116 / 32`，Sys116 是屏宽 1024，结果必须是**坐标倍率 32**（`docs/OPCODE_101.md` 独立推出 rateX = 32 / rateY = 24）；若按取余 `1024 % 32 = 0`，整个 UI 会塌成 0。
> 2. `CE63 pc46` `121 [9000002, 1600089, 10, 12544]` = `Sys2 = 17*rateY + rateY / 10 = 408 + 2 = 410`，与 `OPCODE_101.md` 的独立结论一致；取余会得 412。
> 3. `CE74 pc148` `121 [1600043, 1600044, 100, 13058]`（bin 3、复合 `*=`）= `self43 *= self44 / 100`，百分比缩放只能是除法。
> 
> 反过来 `0x4000` 必须是取余：`CE48 pc172` `self20 = self20 % 10000`（坐标回卷后再 +20000 重新打包物品 ID）、`CE86 pc44` `self15 = self27 % 10000 / % 20000 / % 30000`。带第二操作数 `10000` 的按位非没有意义。
> 
> 实现位置：`crates/wolf-vm/src/exec.rs` `fn binary_op`（含逐条注释与单测）。

**`0x6000` 已确认 = 随机数区间 `rand(min, max)`**（推翻早期「右移/除法」的猜测）。

WolfTL 的运算符表在 `0x5000` 与 `0x7000` 之间是空的，本作却有 1,101 条（占 121 的 6.4%）。
判据来自**操作数本身**，不是猜：把这些指令的 `arg[1]/arg[2]` 打出来看，全都是「区间」形状，而不是「被移动的值 + 位移量」：

| 事件 | 指令 | 直读 |
|---|---|---|
| ev37 pc25 | `[v, -20000, 20000, 0x6000]` | 对称区间（伤害浮动） |
| ev42 pc60 | `[v, 1, 10]` | 标题画面的 1..10（随机演出） |
| ev42 pc63 | `[v, 1, 5]` | 1..5 |
| ev119 pc128 | `[v, 0, v]` | 0..某计数器 |
| ev137 pc132 | `[v, 0, 99, 0x6200]` | 0..99 且复合运算是 `-=`（`r = rand(0,99); v -= r`） |
| ev90 pc491 | `[v, 5, 20]` | 5..20 |
| ev97 pc16 | `[v, 0, 1600088]` | 0..Self 变量 88 的值 |

位移`>>`或整数除法作用在这些操作数上没有任何语义（`-20000 >> 20000` 恒为 -1），
而「随机取值再按权重挑分支」正是 WOLF 里做**加权随机/伤害浮动**的标准写法，且能在 `111` 条件链里直接被判定。
⇒ 实现：`arg0 = rand(eval(arg1), eval(arg2))`（含端点、上下界反了要交换、区间为 0 返回下界）。
实现在 `crates/wolf-vm/src/rng.rs`（`WolfRng`）：现已按 `_wolfref/game_dat_random.c` 移植零售 MSVC C 运行时 LCG
（`state = state*0x343FD + 0x269EC3` mod 2^32，输出 `(state>>16)&0x7FFF`，本作种子 `random_a=22227`），
旧 xorshift32 替身已移除；范围归约 `range()` 的乘法高位细节仍是推断（见 `docs/research/M7_PRNG.md`）。

## 4. 控制流：扁平字节码 → 跳转表

WOLF 的字节码是**扁平的线性数组**，`if/elseif/else`、`loop` 全靠「头指令 + 尾指令」配对。加载期必须把它们**预编译成跳转表**，否则每帧线性扫描会慢到不可用（139,273 条指令 × 108 个并行协程）。

### 4.1 分支链的配对算法（实测验证）

```
栈 stack: Vec<BlockId>
BlockId { kind: Branch(111/102) | Loop(170/176/179), cases: Vec<usize> }

遇到 111 VariableCondition / 102 Choices:
    新建 Block，push 到 stack
遇到 401 ChoiceCase:
    block = stack.top()  // 若 stack 为空 → 见 4.3 容错
    block.cases.push(pc)
遇到 420 ElseCase / 421 CancelCase:
    同样挂到 stack.top()（420 只挂 111 父块，421 只挂 102 父块）
遇到 499 BranchEnd:
    弹栈（若栈空 → 见 4.3 容错）
```

**实测挂载关系统计**

| (父块, case) | 次数 |
|---|---|
| (111, 401) | 17457 |
| (111, 420) | 3246 |
| (102, 401) | 1003 |
| (102, 421) | 150 |
| 栈空时遇到 401/420/421 | **131** |

### 4.2 case 编号的**两套不同起点**（最容易踩的坑）

- **111 的 `401.arg[0]` 从 1 开始**：条件数 1 → 只有 id=1；条件数 2 → id=1,2；条件数 3 → id=1,2,3。
- **102 的 `401.arg[0]` 从 2 开始**：`id = 选项序号 + 1`，即 `id=2` 对应第 1 个选项。实测 `102(argc=1) cond_count=1 → id=2`（157 次）、`=2 → id=2,3`（268/187）。
- 所以 `ChoiceCase.arg[0]` 的语义是「**1-based 分支序号**」，而 `ElseCase`/`CancelCase` 的 `arg[0]` **恒为 0**（实测 420 全 0、421 全 0）。

### 4.3 容错（必须实现，否则加载就崩）

实测存在：
- **131 条 case 指令在栈空时出现**（多半是块跨事件/被截断的产物）；
- **123 条 499 在栈空或无同 indent 块时出现**（多余/占位 `BranchEnd`）。

⇒ 加载期建树必须**宽容**：栈空时遇到 401/420/421 就丢弃（或挂到一个 dummy 块），栈空时遇到 499 就忽略。**绝不能 panic**。

### 4.4 indent 的作用与不可靠性

indent 分布：0:17225, 1:39687, 2:33567, 3:25600, 4:17842, 5:10814, 6:6369, 7:4139, 8:2194, 9:1466, 10:1093，之后骤降（15 以上各约 15 条）。

case 相对父块头部的 indent 差：

| 指令 | 差 0 | 差 1 | 差 2 | 差 3 | 其它 |
|---|---|---|---|---|---|
| 401 | 18366 | 66 | 25 | 2 | 差5×1 |

### 4.5 分支链的执行语义

```
  全假则跳到 420 ElseCase 分支体（若存在），否则跳到 499 之后。
  注意 arg[0] 高 4 位实测出现 1,17,18,19,20（0x11/0x12/0x13/0x14）——
  只有「use_else_branch」一位被 ksy 建模，其余位 TODO/未确认。
```

### 4.6 循环结构

| 头指令 | 次数 | 尾 | 语义 |
|---|---|---|---|
| `170 StartLoop` | 182 | `498 LoopEnd` | 无限循环，靠 `171 BreakLoop` 退出 |
| `176 StartLoop2` | 54 | `498 LoopEnd` | **多条件循环头**：其 `498` 的 indent 比头部**浅 1~7 级**（实测差 -7,-6,-5,-4,-3,-2），会把外层若干层一起回卷 |

配对实测：

- `170` 与匹配 `498` 的 indent 差**恒为 0**（173 次），body indent = 头 + 1。

### 4.7 字符串标签跳转（212 / 213）——**不是整数索引**

- `212 SetLabel`：606 条，`argc=0`，**1 个字符串 = 标签名**。定义跳转锚点，本身不推进语义（PC 照常 +1）。
- `213 JumpLabel`：1543 条，`argc=0`，1 个字符串 = 标签名。跳到同事件内最近的同名 `212` 之后。

**致命坑点：标签名是带变量插值的字符串，不能当静态常量表。**

实测 1543 条 `213` 里有 **5 条标签名在事件内找不到同名 `212`**，但**只有前 3 条含 `\cself[n]` 转义**（后 2 条是纯静态名却仍找不到，是编辑器允许的「悬空标签」）：

| 事件 | 213 里的标签字符串 | 该事件实际定义的 212 |
|---|---|---|
| ev31 ◆[戦闘用]ダメージ処理 | `単体ダメージ処理終了\cself[29]` | 単体ダメージ処理終了1 / 2 / 3 / 単体ダメージ処理 |
| ev63 X[共]メッセージウィンドウ | `戻り先\cself[40]` | ウィンドウ表示 / 戻り先1 / 戻り先2 / 文章表示位置設定 |
| ev86 X[移]┗ お店内部情報更新 | `計算戻り\cself[90]` | 装備可能者計算 / 計算戻り1 / 計算戻り2 |
| ev232 ステータス簡易表示 | `リフレッシュ表示` | （该事件 0 个 212） |
| ev308 | `1` | 外だし / 依頼トップ / 依頼キャンセル / 青姦終わり |

⇒ **跳转前必须先在运行时把 `\cself[n]` 等转义求值**（`単体ダメージ処理終了` + cself[29] 的值 → `単体ダメージ処理終了2`），再做字符串匹配。

**实现口径（`crates/wolf-vm/src/program.rs` + `exec.rs`，实测 3 动态 / 2 未解析）**

- 预编译期只统计、**不做静态解析**：`212` 的模板原文直接进 `HashMap<String, usize>`（target = 该 212 的下一条），
  `213` 的模板原文标记三种身份 —— `static`（表里直接命中）、`dynamic`（**含任何反斜杠 ⇒ 运行时必须先求值**）、`unresolved`（模板静态且表里没有）。
  实际计数（`wolf-cli precompile` 输出）：**`labels 606 defined / 1543 jump(s) / dynamic 3 / unresolved 2`** —— 与上表完全吻合
  （动态 = ev31 / ev63 / ev86；未解析 = ev232 的 `リフレッシュ表示`、ev308 的 `1`）。
- 执行期 `213` 一律「先 `expand()` 再查表」（对静态标签求值是恒等操作，代价可以忽略），
  **查不到就 `pc = program.len()` 结束协程 + 打 Warn**（绝不 panic、绝不原地跳 —— 原地跳会变成死循环）。
- `\v[n]` / `\sys[n]` 是否也支持：按 `work/yado2.txt` 的嵌套优先级规则**应当都支持**，但本作样本只实测到 `\cself`。**TODO/未确认**。

## 5. 逐条 opcode 规格

> 约定：`argc` = `intArgs` 个数（= `paramCount - 1`）；`strc` = `stringArgs` 个数。
> `magic` 表示「魔法数字」（§2），可能是字面量、Self、普通变量、系统变量。
> **优先级**：**M1** = 不做就跑不起来；**M2** = 影响观感/完整性；**M3** = 可以最后补。

### 5.1 `99` Checkpoint（チェックポイント）

### 5.2 `101` Message（文章の表示）
- **参数个数**：`argc = 0`，`strc = 1`（实测 12,027 条全部如此）
- **intArgs**：无
- **stringArgs[0]**：显示文本，**含转义序列**（见 §5.2.1）
- **语义**：打开消息窗口并逐字显示，**阻塞**——协程挂起到玩家按键/点击/自动关闭。显示期间其他并行协程继续跑（它们只被 `105 ForceStopMessage` 影响）。
- **本作**：12,027 条。样例 `ev0 pc30 strs=['@1\n得到了「\cself[8]」。']`
- **难度**：3　**优先级**：M1
- **坑点**：
  1. **`\E` 不是表情**，是「**描边显示（縁取り）开启**」；`\N` 是描边关闭（恢复 `\E`/`\wE` 之前的状态）；`\wE[n]` 是描边粗细 1..5。
  2. **脸图（顔グラ）标记**：实测只有 **20 条**以 `@` 开头（如 `@1\n...`），其余 12,007 条无 `@`。`@n` 是「第 n 号脸图/说话者」前缀，`@` 后紧跟的 `\n` 才是换行。**不要把 `@1` 当成文本的一部分显示出来。**
  3. 文本是 **UTF-8 字节串**，不是 UTF-16；Rust 里直接 `String::from_utf8` 即可。
  4. `\cself[n]` / `\v[n]` / `\self[n]` 等**必须每次显示时求值**，且**嵌套优先级**是固定的（见 §5.2.1），不能简单地从头扫描替换。

- **intArgs[1 + 3i .. 3 + 3i]**：第 i 个条件的三元组 `[variable(magic), value(s4), operator]`
- **operator**：`0 >`、`1 >=`、`2 ==`、`3 <=`、`4 <`、`5 !=`、`6 按位与`；**17/18/19 超出枚举**（共 44 条，`TODO/未确认`）
- **语义**：顺序求值 `condCount` 个条件，**第一个为真**的对应分支体被执行，其余跳过；全假走 `420 ElseCase`（若有），否则跳到 `499` 之后。**不阻塞**。
- **本作**：10,743 条。完整真实样例 `ev0 pc6 ints=[3, 1600002,1,2, 1600002,2,2, 1600002,3,2]`（3 条件全 `==`）；`ev42 pc61 ints=[17, 1600010, 9, 1]`（`use_else_branch` 置位，单条件 `>=9`）。
- **难度**：3　**优先级**：M1
- **坑点**：
  1. **`arg[0]` 低 4 位是条件数**，用它算 `argc` 可以自校验：`argc == 1 + 3*(arg0 & 0x0F)`，**实测 100% 成立**，加载期请断言。
  2. operator 17/18/19 只有 44 条，**先按 `==` 兜底并打日志**，靠游戏行为反推。
  3. 分支体之间的 `401` 与父块 indent 可能不等（§4.4），**用栈配对**。

### 5.10 `112` StringCondition（文字列条件分岐）
- **参数个数**：`argc = 1 + condCount`（实测 `argc ∈ {2:93, 3:18, 4:8, 5:4}` ⇒ `condCount ∈ {1,2,3,4}`）；`strc = 4` **恒成立**（4 个字符串槽，多数是空串）
- **intArgs[0]**：同 111，**低 4 位 = 条件数**，bit4 起是标志。实测 `(arg0, argc)` 组合：`(1,2):63`、`(17,2):30`、`(2,3):13`、`(3,4):7`、`(2,4):1`、`(17,3):1`、`(20,5):3`、`(1,3):4` ⇒ **`argc == 1 + (arg0 & 0xF)` 成立**。
- **intArgs[1..]**：每个条件一个 magic（比较对象），**注意高位 `0x1/0x2/0x3 << 28` 会出现在这里**（§2.3）。
- **stringArgs[0..3]**：4 个比较用的字符串（可为空串，也可含转义）；`(arg0, strc)` 实测 `strc` 恒 4，但**有效槽位数与 `condCount` 有关，TODO/未确认**。
- **本作**：123 条。样例 `ev94 pc235 ints=[1,1600006] strs=['save1','','','']`（1 个条件 + 4 槽，只用第 0 槽）；`ev263 pc11 ints=[20, 806906373,806906373,806906373,806906373] strs=['0','1','2','3']`（`arg0=20=0x14` ⇒ 4 条件）；`ev421 pc114 ints=[3,1600005,1600005,1600005] strs=['1','2','3','']`。
- **难度**：4　**优先级**：M2（123 条，但都在存档/设置类路径上）
- **坑点**：**高位 magic 与 4 个字符串槽的对应关系是最大未知**。建议实现：`condCount` 个条件按序取 `stringArgs[i]` 与目标字符串变量比较，用 `arg[1+i]` 选目标。

### 5.11 `121` SetVariable（変数操作）—— **本作第二高频的「数值引擎」**
- **参数个数**：`argc ∈ {4:17022, 5:236}`；`strc = 0` 恒成立
- **intArgs 布局**

| 下标 | 含义 |
|---|---|
| `[0]` | **写入目标**（magic）。`2000000..2999999` ⇒ 普通变量 `id = arg0 - 2000000`；`1000000..1999999` ⇒ Ev Self；`9000000..9999999` ⇒ 系统变量；`0..999999` ⇒ **字面量目标（无意义，不应出现）** |
| `[1]` | 操作数 A（magic） |
| `[2]` | 操作数 B（magic） |
| `[3]` | **运算符位域**：低 12 位 = 对 `[0]` 的复合赋值；bit12 以上 = `[1]` 与 `[2]` 之间的二元运算；bit16 = 存在 `[4]` |
| `[4]` | 仅 `arg[3] & 0x10000` 置位时存在，是 **包含式末偏移（inclusive last offset）**：同一 compound 依次作用于 `arg[0] ..= arg[0] + arg[4]`，共 `arg[4] + 1` 个槽。已由 `Game.exe` opcode121 handler（VA `0x4aea70`，range 分支 `0x4af158`，循环 `0x4afd58` 的 `inc esi; cmp esi, arg4; jle`）反汇编确认；CE94 pc87 `[1600022,10,0,66560,3]` 即对 x/y/宽/高四槽 `1600022..=1600025` 同除以 10 |

- **执行语义（必须精确按这个顺序）**

```
let a = eval_magic(arg[1]);
let b = eval_magic(arg[2]);
let r = match (arg[3] >> 12) & 0xF {   // 二元运算，见 §3.2
    0x0 => a + b,
    0x1 => a - b,
    0x2 => a * b,
    0x3 => a % b,
    0x4 => !a,            // 按位非，arg2 通常为 0
    0x5 => a & b,
    0x6 => rand_range(a, b), // ★ 1101 次，已实测确认为随机区间，见 §3.2
    0x7 => a | b,
    0x8 => a ^ b,
    0x9 => a << b,
    _   => unreachable!(),
};
let cur = eval_magic(arg[0]);
write_magic(arg[0], match arg[3] & 0x0F00 {   // 复合赋值，见 §3.1（注意是 0x0F00！）
    0x000 => r,
    0x100 => cur + r,
    0x200 => cur - r,
    0x300 => cur * r,
    0x400 => cur / r,
    0x500 => cur % r,
    0x600 => cur.floor(),
    0x700 => cur.ceil(),
    0x800 => cur.abs(),
    0x900 => angle_from_slope(cur),   // 单位 x10
    0xA00 => (sin(r as f64 / 10.0) * 1000.0) as i32,   // 角度 x10 -> sin x1000
    0xB00 => (cos(r as f64 / 10.0) * 1000.0) as i32,
    0xC00 => (sqrt(cur as f64) * 1000.0) as i32,       // sqrt x1000
    _   => r,
});
// arg[3] & 0x10000 时额外循环：for offset in 0..=arg[4] { write(arg[0]+offset, compound(...)) }
PC += 1;   // 不阻塞
```

- **本作**：17,258 条。真实样例：
  - `ev4 pc17 ints=[1600010, -1, 0, 0]`（`arg3=0` ⇒ 直接赋值 `= -1`）
  - `ev4 pc19 ints=[1600010, 1, 0, 256]`（`256 = 0x100` ⇒ `+= 1`，配 `179 LoopTimes` 做计数器，**极典型**）
  - `ev5 pc? ints=[1600001, 1600001, 0, 2048]`（`2048 = 0x800` ⇒ `abs`）
  - `ev? ints=[1600010, 1600020, 1600021, 69632]`（`69632 = 0x11000` ⇒ 二元 `-`、复合 `=`）

- **难度**：4　**优先级**：M1（最高）
- **坑点**：
  1. **`arg[3]` 的两个字段必须分开解**：`& 0x0F00` 是复合赋值，`>> 12 & 0xF` 是二元运算。**混在一起解就全错**。
     特别注意低 8 位：194 条指令在那里放了 `0x01/0x02/0x04/0x08/0x10/0x20` 等未知标志，**必须掩掉**（§3.1）。
  2. `0x6000` 段 1101 次，**已实测确认为 `rand(min,max)`**（§3.2），不是右移 —— 早期按右移实现会让所有加权随机取到常量。
  3. `arg[3]` 的 bit16 = `0x10000` 标记 `arg[4]` 存在（236 次 = argc 5 的 236 条，**完全吻合**）。
  4. 除法/取模要**防 0**（WOLF 原版的行为未确认，建议除 0 时保持原值 + 打警告）。
  5. **三角函数与开方的单位是 x10 / x1000**（`angle x10`、`sin/cos/sqrt 结果 x1000`），不是弧度/浮点。

### 5.12 `122` SetString（文字列操作）
- **参数个数**：`argc ∈ {2:562, 3:464, 4:4}`；`strc ∈ {1:960, 0:66, 2:4}`
- **intArgs**

| 下标 | 含义 |
|---|---|
| `[0]` | **写入目标**（magic，字符串上下文）。实测多为 `1600009` 这类 Self 槽，也有 `3000000..3219201` 的字符串变量段 |

### 5.13 `123` InputKey（キー入力）
- **参数个数**：`argc ∈ {2:216, 3:2}`
- **intArgs**

| 下标 | 含义 |
|---|---|
| `[0]` | 存放按键**键码**的变量（magic，实测全是 `1600010`/`1600011`/`1600012`） |
| `[1]` | **输入查询位字段**（复合：读取大类、方向/决定/取消/副键复选、5 种取得时机；**不是允许键掩码**）。实测 20 种：`{1,7,16,17,32,33,48,49,64,144,145,160,176,177,183,184,241,257,512,771,784}` |
| `[2]` | 仅 2 条，**未确认**（疑为「是否等待/仅检测」） |

- **★★已实测纠正（H-KEY-2，推翻本文早期版本）**：写入 `arg[0]` 的是**键码**，不是位掩码。
  早期版本（旧 H-KEY-1）把 `[1]` 当位掩码、把结果写成 `key_bits & mask`，那样的值永远不可能等于脚本实际比较的常量，菜单因此一个分支都进不去。
  证据全部来自开发者自己留在数据里的 `103` 调试注释：
  - **事件 108 pc27**：一次轮询后依次比较 `== 10` / `== 11` / `== 2`，三个分支体注释分别是「決定キー」「キャンセルキー」「下キー」，else 分支再比较 `== 8`（注释「上キー」）。
  - **事件 65 pc83**：注释「左右キーを押したら終了する場合」，体里比较 `== 4` / `== 6`。
  - **事件 65 pc101 / 事件 108**：注释「サブキー…」，对应键码 12。
  - **事件 118 pc110**：注释「決定かキャンセルか、だけ受付する」，随后比较 `== 10` / `== 11`。
  - **事件 510 pc975**：图片注释 `EXIT "长按右键"`，掩码 32，结果与 `== 11` 比较。
- **键码表（已实测 / 部分推断）**：

| 键码 | 含义 | 状态 |
|---|---|---|
| 0 | 未按 | 已实测 |
| 2 / 4 / 6 / 8 | 下 / 左 / 右 / 上（小键盘编号） | 已实测（有注释佐证） |
| 10 | 決定（Enter / Z / Space） | 已实测 |
| 11 | キャンセル（Esc / X） | 已实测 |
| 12 | サブ（Shift / C） | 已实测 |
| 1 / 3 / 7 / 9 | 四个斜向（按小键盘编号推断） | 未验证，本作从不比较 |
| 13 / 14 / 20 / 100 / 300 | 出现在比较里但未命名 | **未解** |

- **语义**：**不阻塞地**轮询按键，把「当前按键的键码」写入 `arg[0]`，PC += 1。`!= 0` 读作「任意键」，与旧模型的用法兼容。
- **实现**：`crates/wolf-vm/src/exec.rs` 的 `123` 分支把 `arg[1]` 原样交给 `host.key_code_auto(mask, auto_keys)`，拿到标量键码后按当前输入权限 `filter_code`；C# `EventVm` 同构（`FilterKeyCode`）。`crates/wolf-game/src/key.rs` 在端口内部保留自己的位布局，对外只吐键码。无头宿主返回 0，等价于「没人碰键盘」。
- **未解的关键点**：`arg[1]` 的复合位字段具体如何选择读取源与时机。官方只公开“读取大类/键复选/取得时机”，未公开二进制位表；观测值只能按 byte 分组（`16/32/48/64` 与 `144/145/160/176/177` 等），不能直接套 `KeyCodes` 的位布局。一次轮询可返回六种键码（事件 108 的掩码 177），所以「一位一键」不成立。当前实现接受掩码、回答「当前按下的键的键码」并按 `126` 权限过滤，对本作全部 `!= 0` / `== 10` 比较成立；逐位语义仍见 `docs/UNVERIFIED.md` 的 H-KEY-2。
- **本作**：218 条；掩码频率 `{145:91, 16:10, 144:28, 176:20, 177:7, 49:3, 771:1, 784:1, …}`。
- **难度**：3　**优先级**：M1（已实现）
### 5.14 `124` SetVariableEx（変数操作（拡張））
- **参数个数**：`argc ∈ {3:174, 4:405}`
- **intArgs**

| 下标 | 含义 |
|---|---|
| `[0]` | 写入目标（magic） |
| `[1]` | **操作类型位域**。实测**只有 5 个值**：`4096(0x1000)`、`4608(0x1200)`、`12288(0x3000)`、`16384(0x4000)`、`17408(0x4400)` |
| `[2]` | 操作数（magic 或字面量） |
| `[3]` | 仅 `argc = 4`，含义 **TODO/未确认** |

- **本作**：579 条。样例 `ev36 pc193 ints=[1600041, 16384, 1600021, 3]`（`0x4000`）；`ev37 pc2 ints=[1600020, 4096, -2, 2]`（`0x1000`）；`ev41 pc12 ints=[1600010, 12288, 8]`（`0x3000` 短格式）；`ev63 pc145 ints=[1600010, 17408, 1600021, 2]`（`0x4400 = 0x4000 | 0x400`）。
- **难度**：5　**优先级**：M2（579 条，多在战斗/菜单数值路径上）

### 5.15 `125` AutoInput（自動入力）
- **参数个数**：`argc = 1`（98 条）
- **intArgs[0]**：实测集合 `{1,2,16,32,48,64,80,128,160,192,536870914}`（`0x20000002`）
- **语义**：向**下一帧**注入虚拟键鼠（「自動入力」），**不阻塞**。官方分 3 类：基本入力、键盘（物理键码）、鼠标；不含手柄/触控。
- **与 `126` 的关系**：`125` 选“键盘”时注入物理键码，可穿透 `126` 的设备禁止；选“基本入力”时不能穿透 `126` 的基本输入禁止（“移动时也禁止”会让自动基本输入失效）。本作当前只把 `arg[0]` 当 `auto_keys` 注入。
- **本作**：98 条。样例 `ev41 pc20 [2]`、`pc23 [1]`、`pc26 [64]`、`pc35 [16]`、`pc41 [128]`。
- **难度**：2　**优先级**：M3（本作只用于标题/调试的自动推进）
- **坑点**：`536870914 = 0x20000002` 带高位标志（§2.3）。

### 5.16 `126` BanInput（入力禁止）
- **参数个数**：`argc = 1`（10 条）
- **intArgs[0]**：实测集合 `{240, 496, 752, 0x10000001, 0x10000101}`（旧文档的 `268435713 = 0x10000041` 是误值，实际为 `0x10000101`）
- **语义**：按**目标 + 权限状态**修改输入权限，**不阻塞**；不是“用位掩码清 held”，也不是一次清空全部。
  * **低分支（基本入力）**：`target = raw & 0xFF`（方向/决定/取消/副键位），`state = (raw >> 8) & 0x3`。`0` = 常に受け付ける（默认恢复）、`1` = 移動時禁止・キー入力時だけ許可、`2` = 移動時もキー入力時も禁止。未选中键保持不变，**没有自动清除**；恢复必须对同一目标再发 `state 0`。
  * **高分支（设备）**：`raw & 0x10000000` 置位时，`target = raw & 0xFF` 选择键盘/鼠标/手柄/全部设备，只有允许/禁止二态（`state != 0` 为禁止）。本作把非 0 目标折叠为单一 `device_deny`（无手柄），未按设备分槽；逐设备分离待编辑器差分。
  * 状态跨事件、跨地图持久保留；现代版本随存档保存/恢复（官方修过“禁止状态未入档”的 bug）。`126[0]` 是否清空全部、F12 回标题是否复位，官方无明文。
- **作用域**：基本入力三态同时约束地图移动、`123` 的基本键轮询和 `125` 的“基本入力”自动键；设备分支不约束 `125` 的键盘注入。`123` 的 mask 不参与权限判断（见 5.13）。
- **本作**：10 条。`ev126 pc41 [496]`/`pc45 [240]`/`pc76 [496]`/`pc80 [240]` 是“移动时禁方向 / 恢复”；`ev225 pc244 [752]`/`pc249 [240]` 是“全禁方向 / 恢复”；`ev232 pc691`、`ev234 pc654/656`、`ev328 pc3` 是高分支设备禁/恢复。
- **实现**：Rust `wolf-vm::exec::InputState`（`apply_permission` + `filter_code`，移动/选择分别读 `movement_deny`/`basic_all_deny`）与 C# `EventVm.ApplyInputPermission`/`FilterKeyCode` 同构；`GameSession.StartTitle`/`StartNewGameNow` 调 `ResetInputPermissions`。`cargo test -p wolf-vm` 95 passed；`VmTest` 覆盖三态、设备分支与 `125` 穿透。
- **难度**：3　**优先级**：M3（已实现，逐位表仍待编辑器差分）

### 5.17 `130` Teleport（場所移動）
- **参数个数**：`argc = 5`；**原始布局是 `target, x, y, map, options`（不是 map-first）**。已由 `wolfrpg-map-parser 0.4.1` 的 `TransferCommand::parse` 源码交叉确认。
- **`target`**：`0xffffffff`（按 i32 显示为 `-1`）= **主角**；`0xefd8ffff` = **从存档位置**（此时 `argc = 6`，在 target 后多一个 db_variable）；其余值为变量 id（坐标间接寻址）。
- **`x` / `y`**：目的地坐标。**`map`**：目标地图 id。**`options`**：bit0 = 精确坐标；bits4..7 = 过渡类型（0 无、1 无淡入、2 淡入）。
- **语义**：切换地图并把 target 角色放到 `(x, y)`，**阻塞**（切图有过渡）。

### 5.37 `210` CommonEvent（コモンイベント呼び出し）—— **本作最高频之一（18,468）**
- **参数个数**：`argc = 2 + nc + rv`，其中 `nc`/`rv`/`sc` 来自 `intArgs[1]` 的 `param_status` 位域
- **intArgs 布局**

| 下标 | 含义 |
|---|---|
| `[0]` | **公共事件 ID（带命名空间前缀）**：`500000 + n` ⇒ 公共事件 `n`；`600000 + n` ⇒ 也指向公共事件 `n`，但属**另一张调用表**；`< 500000` ⇒ 地图事件（后面跟的是 `page`） |
| `[1]` | **`param_status` 位域**（见下） |
| `[2 .. 2+nc)` | **参数值**（`nc` 个，每个是 magic number） |
| `[2+nc]` | 仅 `rv = 1` 时存在：**返回值写入目标**（magic number） |

- **`param_status` 位域解码**（`_wolfref/event_command.ksy`，**实测 100% 吻合**）

```
string_count         = (raw >>  4) & 0x0F;   // ★ 注意：实测与真实字符串个数无关，见下
number_count         =  raw        & 0x0F;   // = nc
return_value_enabled = (raw >> 24) & 0x01;   // = rv
string_N_enabled     = (raw >> (11+N)) & 1;  // N=1..5 ⇒ (raw>>12)&1 .. (raw>>16)&1
```

**关键实测结论**：`argc - 2 == nc + rv` **严格成立**（4709/2639/7057/100/8 条全部通过校验），但 **`string_count` 字段与真实 `strc` 不一致**（例如 `sc = 2` 却有 `strc = 3`）。
⇒ **`string_count` 不可靠，字符串个数必须直接用 `stringArgs.len()`**。

- **调用约定**

```
// 1. 解析目标
let target = match arg[0] {
    id @ 500000..=599999 => EventRef::Common(id - 500000),
    id @ 600000..=699999 => EventRef::CommonAlt(id - 600000),   // 见 §6.2
    id                    => EventRef::Map { event: id, page: arg[1] },  // 本作 0 条
};
// 2. 新开一个子协程（不是压栈！），把 nc 个参数绑定到子事件的形参槽，
//    把返回值槽记下来，等子事件 172/正常结束 时写回。
// 3. 父协程【阻塞】直到子协程结束。
```

- **本作**：18,468 条。`argc` 分布 `{7:8666, 6:4714, 3:2647, 4:1418, 5:579, 2:292, 9:152}`；`strc` 分布 `{0:11028, 3:7205, 2:235}`。
  - ID 空间实测：`500000..599999` 有 **18,427 条**；`>= 600000` 有 **41 条**；`< 500000` **0 条**。
  - 真实样例：`ints=[500132, 0]`（无参调用）、`ints=[500014, 1, -1]`（1 个参数）、`ints=[1600010, 0]`（**注意这里是 magic 变量作事件 ID！**）、`ints=[600100, 3, 1600000, 1600032, 1]`（`status=3` ⇒ `nc=3`，传 3 个参数）。
- **难度**：4　**优先级**：M1（最高）
- **坑点**：
  1. **`arg[0]` 是「500000 + id」，必须减 500000**。`500132` → 公共事件 **132**。忘记减就是全盘错位。
  2. **`arg[0]` 可以是 magic 变量**（`1600010`）⇒ **运行期才能知道调用哪个事件**。这类样本本作确实存在。
  3. `600000` 段**不是「另一套事件」**，减 600000 后 `94..106` 全是真实存在的公共事件（`X[移]` 系列菜单绘制事件），见 §6.2。
  4. **`string_count` 不可靠**，别用它分配字符串槽。
  5. 子事件是**新协程**而不是递归调用栈：本作有事件会**递归调用自己**（菜单类），用单栈实现会爆栈。

- **坑点**：`498` 也可能闭合 `179`（`ev245 pc453` 就是 `498` 出现在 `Choices` 之前）。**配对必须用栈**，且 `176` 的尾会**一次弹多层**。

### 5.56 `499` BranchEnd（分岐終端）
- **参数个数**：`argc = 0`（11,361 条）
- **语义**：分支/循环块的结束标记。执行到这里 = 继续往下（PC += 1）。加载期用于**回填所有分支的「跳到块尾」目标**。
- **本作**：11,361 条。配对实测：正常闭合 11,238 条，**孤儿 123 条**。
- **难度**：2　**优先级**：M1
- **坑点**：**123 条孤儿 `499`**（栈空或无同 indent 块）⇒ 加载期必须容错，**不能 panic**。

### 5.57 `1000` ProFeature（拡張機能）—— **只在公共事件侧**
- **参数个数**：`argc = 1`，`strc = 1`（24 条）
- **intArgs[0]**：**功能类型**（`Command.hpp:576-634`）：`0 = Screenshot(JPG)`、`1 = CreateFolder`、`2 = FileCopy`、`3 = FileDelete`、`4 = Screenshot(PNG)`、`5 = StopProcessing(ms)`、`6 = GameRestart`、`7 = SetWolfxKey`、`8 = UnsetWolfxKey`、`9 = VibrateGamepad`

- **语义**：扩展功能，多为**截图存档**。`type = 5` 会**阻塞** `arg[1]` 毫秒。
- **本作**：24 条。`arg[0]` 实测 `{0:23, 3:1}`。样例：`ev435 pc1 ints=[0] strs=['save/save1.jpg']`、`ev452 pc3174 ints=[0] strs=['Data/SC1.jpg']`、`ev131 pc223 ints=[3] strs=['Save/save\cself[12].jpg']`。
- **难度**：3　**优先级**：M3（截图存档，不影响主线）
- **坑点**：`ev131 pc223` 的 `arg[0] = 3` 是 `FileDelete`，但字符串看起来像截图路径 —— **`3` 与「删除」的对应关系 TODO/未确认**（也可能是本作把类型编号用偏了）。**建议：`0`/`4` 实现截图，其余先当 no-op + 打日志**。

### 6.2 ID 命名空间（**重要，不要弄错**）

```
arg[0] < 500000            => 地图事件（后面跟 page 字段）        ; 本作 0 条
500000 <= arg[0] <= 599999 => 公共事件 id = arg[0] - 500000        ; 18,427 条
600000 <= arg[0] <= 699999 => 公共事件 id = arg[0] - 600000        ; 41 条
```

**`600000` 段不是另一套事件空间**：实测 41 条的 `arg[0]` 是 `600094..600106`，**减 600000 后 `94..106` 全是真实存在的公共事件**，标题全是 `X[移]` 系列（`セーブ·ロード画面描画` / `システム画面描画` / `ダメージ·回復ポップアップ` / `指定キャラHP/SP回復表示` / `指定キャラ状態付与表示` / `ミニウィンドウ表示` / `メニュー時文章表示` / `上部ステータス描画` / `■■【メニュー内部処理】■■` / `選択位置主人公ID設定` / `選択箇所装備コード取得`）。

⇒ **实现建议：把 `600000` 段当作「第二张调用表」的语法糖，最终都解析成同一个 `EventId = arg[0] % 100000`。**

```rust
fn resolve_common_event_id(raw: i32) -> Option<EventId> {
    match raw {
        500_000..=599_999 => Some(EventId((raw - 500_000) as u16)),
        600_000..=699_999 => Some(EventId((raw - 600_000) as u16)),
        _ => None,   // 地图事件路径
    }
}
```

**校验说明**：曾尝试用「目标事件头部的 `argn`/`argsn` 是否等于 `param_status` 的 `nc`/`sc`」来验证参数个数，**只 8/33 条匹配 ⇒ 校验不成立**。事件头的 `argn` 分布 `{(0,0):278, (1,0):96, (2,0):59, (3,0):48, (4,0):46, ...}` 说明 `argn` 更像是**形参槽上限**而非实际形参个数。**不要用它做校验。**

### 6.3 形参绑定

子事件里的形参通过 `1000000` 段（Ev Self）访问：调用时把 `nc` 个参数写进子事件 Self 的 `[0 .. nc)` 槽（具体槽号映射 **TODO/未确认**，但本作 `1600000` 是最高频的 Self 槽，疑为「第 0 个形参/返回值」）。

## 7. 协程语义

### 7.1 为什么必须是多协程

`run_condition` 实测：`0 call_only` 442 / `2 parallel_process` 97 / `3 parallel_process_always` 10 / `1 auto_start` 1。
**108 个事件是每帧并行跑的后台协程**（97 + 10 + 1）。这些事件做的是：BGM 淡入淡出、窗口动画、伤害数字飘字、菜单重绘、计时器…… 如果用单调用栈，它们会互相阻塞，画面直接卡死。

```
Runtime
 ├─ Vec<Coroutine>            // 每个协程 = { event_id, pc, wait_until_frame, call_depth, self_vars, label_map }
 ├─ 每帧：for co in coroutines { if !co.blocked { co.step() } }
```

### 7.5 控制流小结（含 §4.7 的字符串标签结论）

加载期一次性完成四件事，运行期就只剩「查表 + 跳」：

1. **分支链 → 跳转表**：`111`/`102` 压栈，`401`/`420`/`421` 挂栈顶，`499` 弹栈。每个块记录 `cases: Vec<usize>` 和 `end_pc`。**容错**：栈空时丢弃（131 条）、孤儿 `499` 忽略（123 条）。
2. **循环 → 回跳表**：`170`/`176`/`179` 与 `498` 用栈配对。**`176` 的尾 indent 比头浅（实测 -7..-2），`498` 会一次弹多层**。
3. **`212` 标签 → 名字表**：`HashMap<String, usize>`，但 **key 存的是「模板串」**。
4. **`213` 跳转 → 运行期求值后查找**：

```rust
// ★ 这是全文档最容易漏的一条：标签名是带变量插值的模板，不是常量。
fn jump_label(co: &mut Coroutine, raw_label: &str) -> Result<usize> {
    let label = eval_escapes(co, raw_label)?;   // 単体ダメージ処理終了\cself[29] -> 単体ダメージ処理終了2
    co.labels.get(&label).copied().ok_or(Error::LabelNotFound(label))
}
```

**证据**：1,543 条 `213` 里有 **5 条**标签名在事件内找不到同名 `212`，且这 5 条**全部含 `\cself[n]`**：

| 事件 | `213` 的标签模板 | 该事件定义的 `212` | 求值后应命中 |
|---|---|---|---|
| `ev31 ◆[戦闘用]ダメージ処理` | `単体ダメージ処理終了\cself[29]` | `単体ダメージ処理終了1/2/3`、`単体ダメージ処理` | `単体ダメージ処理終了2`（当 `cself[29] == 2`） |
| `ev63 X[共]メッセージウィンドウ` | `戻り先\cself[40]` | `ウィンドウ表示`、`戻り先1`、`戻り先2`、`文章表示位置設定` | `戻り先1` / `戻り先2` |
| `ev86 X[移]┗ お店内部情報更新` | `計算戻り\cself[90]` | `装備可能者計算`、`計算戻り1`、`計算戻り2` | `計算戻り1` / `計算戻り2` |
| `ev232 ステータス簡易表示` | `リフレッシュ表示` | （0 个 `212`） | **无目标** ⇒ 需容错 |
| `ev308` | `1` | `外だし`、`依頼トップ`、`依頼キャンセル`、`青姦終わり` | **无目标** ⇒ 需容错 |

⇒ **如果按「纯静态 `HashMap<String, usize>`」实现，这 3 条会 `LabelNotFound` 直接崩游戏**（`ev31`/`ev63`/`ev86` 都是战斗/消息的核心路径）。
`\v[n]` / `\sys[n]` 是否也参与标签插值：按 `work/yado2.txt` 的嵌套优先级规则**应当支持**，但本作样本只实测到 `\cself`。**TODO/未确认**。
